## 1. 선곡자(누가 이 곡을 넣었는지) 표시

### 1.1 왜 중요한가

기획 산출물(`04-playlist.md` US-304)의 핵심 요구사항이자, "함께 만드는 플레이리스트"라는 제품 정체성의 표현이다. 단순히 "정보를 표시"하는 게 아니라, **참여의 흔적을 눈에 띄게 남겨 애착을 만드는 것**이 목적이다.

### 1.2 컴포넌트: 선곡자 배지 (Picker Badge)

기본 형태:

```
🅢 지은
```

- 아바타(원형, 프로필 이미지 또는 이니셜) + 닉네임 텍스트의 조합.
- 아바타에는 참여자별로 고유하게 배정된 **컬러 링**을 두른다(예: 지은=코랄, 민준=앰버, 수아=틸). 세션 참여 시 참여자 순서/해시 기반으로 자동 배정, 사용자가 바꿀 수는 없음(MVP 범위에서 단순화).
- 같은 컬러 링이 참여자 목록(2.12), Now Playing의 "이 곡은 ○○님이 선곡"(2.10a), 플레이리스트 각 항목(2.10b)에서 **일관되게** 재사용되어, 사용자가 "이 색 = 이 사람"을 학습하게 한다.

### 1.3 배치 위치별 상세

| 화면 | 표시 방식 |
|---|---|
| 플레이리스트 리스트(2.10b) | 각 곡 항목 하단에 작은 아바타(16–20px) + 닉네임 텍스트. 리스트가 길어질 걸 감안해 닉네임은 8자 내외로 말줄임 처리 |
| Now Playing(2.10a) | "◐ 이 곡은 민준님이 선곡" 형태의 한 줄 — 곡 제목/아티스트 바로 아래, 진행바보다 위에 배치해 곡 정보와 강하게 묶어 보이게 함 |
| 곡 추가 직후 | 방금 추가된 곡이 리스트에 나타날 때 아바타가 살짝 튀어 오르는 마이크로 애니메이션(짧고 절제됨) — "내가 방금 이걸 넣었다"는 행위에 대한 즉각적 긍정 피드백 |
| 자동 다음 곡 전환 알림(US-502, `[P2]`) | 향후 "다음 곡은 ○○님이 고른 곡이에요" 같은 푸시/토스트로 확장 가능하도록, 배지 컴포넌트 자체를 알림에도 재사용 가능한 독립 단위로 설계 |

### 1.4 엣지 케이스

- **본인이 선곡한 곡**: "나(수아)"처럼 표기해 본인 기여임을 강조(리스트에서 자기 것 찾기 쉽게).
- **탈퇴/추방된 참여자가 선곡한 곡**: 닉네임은 유지하되 아바타는 회색 처리("(나감)" 같은 보조 텍스트) — 이미 재생목록에 남은 기여 기록은 삭제하지 않는다는 원칙.
- **삭제된 곡**: `04-playlist.md`에서 "누가 삭제했는지는 굳이 노출하지 않아도 됨"으로 정리됨 — UI에서도 삭제자는 노출하지 않는다(서버 로그로만 보관, 이 결정은 이미 확정된 사항이므로 재검토하지 않음).

## 2. 재생 동기화 상태 표시

### 2.1 왜 중요한가

`01-user-stories.md` US-404: "참여자로서, 현재 동기화 상태(정상/지연 n초/재동기화 중)를 화면에서 확인하고 싶다." 이 앱의 존재 이유가 "같은 순간을 공유하는 것"이므로, 그 상태를 사용자가 매 순간 확인할 수 있어야 신뢰가 생긴다. 반대로 상태를 숨기면 "어긋난 것 같은데 왜 아무 설명이 없지?"라는 불신으로 이어진다(`05-sync-architecture.md`가 강조한 "체감상 맞는 수준"이라는 목표와도 연결 — 완벽하지 않을 수 있음을 인정하고 투명하게 보여주는 편이 오히려 신뢰를 준다).

### 2.2 상태 정의 (4단계 제안)

기획 문서(US-404)는 "정상/지연 n초/재동기화 중"을 언급했다. 디자인 단계에서 이를 사용자 친화적 언어의 4단계로 구체화한다(내부 로직의 실제 임계값은 구현/검증 단계에서 실측 후 확정 — `05-sync-architecture.md` 참고, 여기서는 UI 상태만 정의):

| 상태 | 사용자向 라벨 | 색(01 스타일가이드 참고) | 아이콘 | 발생 조건(개념적) |
|---|---|---|---|---|
| 정상 | "동기화됨" | Sync Green | 정적인 점 | 드리프트가 임계값 이하 |
| 맞추는 중 | "맞추는 중..." | Warm Amber | 펄스 애니메이션 점 | 곡 전환 직후, late join 직후, 또는 드리프트 보정 중인 짧은 순간 |
| 지연 | "N초 지연" | Amber Alert | 시계 아이콘 | 특정 참여자의 네트워크 지연으로 보정이 지연되고 있음(수 초 단위로 눈에 띄는 경우) |
| 끊김 | "연결 끊김 · 재접속 중" | Muted Red | 끊긴 선 아이콘 | 실시간 채널 연결 유실, 재접속 시도 중 |

전환 규칙(개념):
- "정상" ↔ "맞추는 중"은 곡 전환·late join·일상적 드리프트 보정 시 짧게(수백ms~수 초) 오갈 수 있음 — 너무 잦으면 오히려 불안해 보이므로, 아주 짧은 보정은 상태 텍스트를 바꾸지 않고 점 아이콘만 살짝 반응하는 정도로 절제(구체적 임계값은 구현 단계에서 실측 기반으로 조정).
- "지연"은 특정 참여자 기준일 수도, 전체 세션 기준일 수도 있음 — 2.3에서 두 레벨을 구분해 표시.
- "끊김"은 항상 명확하게 별도 오버레이(00 문서 2.14)와 함께 노출.

### 2.2a YouTube "광고 재생 중" 상태 처리 (2026-07-23 신규, US-105b/US-406, `03-youtube-integration.md` 8절 근거)

**결정: 신규 5번째 상태를 추가하지 않고, 기존 "맞추는 중" 상태를 재사용한다.** 다만 원인을 알 수 있도록 배지에 괄호 보조 텍스트를 덧붙인다 — 예: `🟡 맞추는 중... (광고 재생 중)`.

**판단 근거**:
1. **사용자 관점에서 본질이 같다.** "맞추는 중"이 전달하려는 메시지는 "지금 잠깐 어긋나 있지만, 곧 자동으로 맞춰진다"이다. 광고 구간에서 벌어지는 일(서버 기준 위치로의 seek을 일시 보류했다가 광고가 끝나면 재동기화)도 사용자 입장에서는 정확히 같은 경험이다 — "잠깐 어긋났다가 곧 맞는다". 굳이 별도 상태로 분리하면 사용자가 "이건 또 무슨 새로운 문제인가"라고 오해할 위험이 있다.
2. **감지 신뢰도가 아직 검증되지 않았다.** `03-youtube-integration.md` 8-3절은 "정확한 상태 코드/감지 방법은 구현 단계에서 실기기로 확인"이 필요하다고 명시한다. 감지가 100% 신뢰할 만하다고 검증되지 않은 신호에 새로운 전용 색상/아이콘 슬롯을 만들면, 감지 오류(예: 광고가 아닌데 광고로 오판) 시 사용자에게 혼란을 주는 새로운 실패 지점이 하나 더 생긴다. 반면 기존 "맞추는 중" 상태에 보조 텍스트로만 얹으면, 감지가 틀리더라도 최악의 경우 보조 텍스트만 어색할 뿐 핵심 상태 판단(정상/맞추는 중/지연/끊김)은 영향받지 않는다.
3. **상태 배지의 인지 부하를 늘리지 않는다.** US-404가 요구하는 것은 "정상/지연/재동기화 중" 3~4단계의 단순한 이해다. 서비스(Spotify/YouTube)에 따라 상태 배지의 종류 자체가 달라지면, 두 서비스를 오가며 쓰는 사용자(전환 기능 자체가 이번에 추가됨, US-105b)가 매번 다른 상태 체계를 새로 학습해야 하는 부담이 생긴다. 보조 텍스트 방식은 배지 체계(4단계 + 색/아이콘)를 서비스와 무관하게 동일하게 유지하면서, 원인 설명만 상황에 맞게 얹는 방식이라 이 일관성을 지킨다.
4. **접근성 원칙과의 정합성.** 5절 접근성 메모("색상에만 의존하지 않고 아이콘 모양 + 텍스트 라벨 병행")를 그대로 지키려면 새 상태를 추가할 때 새 색상과 새 아이콘 모양까지 고안해야 한다. 광고 상태는 본질적으로 "맞추는 중"의 원인 중 하나일 뿐이므로, 기존 Warm Amber 색 + 펄스 점 아이콘을 그대로 쓰고 텍스트만 보강하는 편이 접근성 일관성을 해치지 않는다.

**표시 규칙**:
- 배지 텍스트: `맞추는 중... (광고 재생 중)` — 괄호 안 보조 텍스트는 원인이 명확히 감지됐을 때만 표시하고, 감지가 불확실하면 그냥 `맞추는 중...`만 표시한다(잘못된 원인 정보를 단정적으로 보여주는 것보다 안전).
- 색/아이콘은 "맞추는 중" 상태와 완전히 동일(Warm Amber, 펄스 애니메이션 점) — 신규 색상/아이콘을 만들지 않는다.
- 참여자별 상세 상태(00문서 2.12)에서도 동일 원칙 적용: 특정 참여자만 광고를 보고 있다면 그 사람 항목에 "🟡 맞추는 중 (광고)"처럼 축약 표시.
- 이 판단은 실기기 검증 결과에 따라 재조정될 수 있다(예: 광고 구간이 예상보다 훨씬 길거나 잦다면, 사용자 기대치 관리를 위해 결국 별도 상태로 승격하는 안을 재검토할 수 있음 — `00-ux-flow.md` 4절 후속 논의 항목 참고).

### 2.3 표시 레벨 두 가지: 세션 전체 vs 개인

1. **세션 전체 상태 배지** (Now Playing 화면 하단, 상시 노출)
   ```
   🟢 동기화됨 · 3명 함께 듣는 중
   ```
   - 세션 참여자 전체 중 가장 안 좋은 상태를 대표로 보여준다(예: 1명이라도 "지연"이면 전체 배지가 "지연"으로 표시) — 낙관적으로 숨기지 않는다.
   - 탭하면 2번(참여자별 상세)로 드릴다운.

2. **참여자별 상세 상태** (참여자 목록, 00문서 2.12)
   ```
   [아바타] 지은 (호스트) 🟢 정상
   [아바타] 민준        🟡 지연 1.2초
   ```
   - 개인 단위로 어떤 사람이 어긋나 있는지 보여줘서, "내 문제인지 상대 문제인지"를 사용자가 이해할 수 있게 한다(오해로 인한 상대방 탓하기 방지, 특히 연인/친구 앱이라는 맥락에서 중요).

### 2.4 마이크로 카피 원칙

- 기술 용어(드리프트, ms, 오프셋 등)를 그대로 노출하지 않는다. "맞추는 중...", "곧 다시 맞아요" 같은 일상어로 번역.
- 부정적 상태(끊김)일 때도 불안을 조장하지 않는 톤: "연결이 잠시 불안정해요, 자동으로 다시 연결할게요" 같은 안심시키는 문구를 제안(정확한 카피는 추후 확정, 여기서는 톤 방향만 제시).
- 상태가 "정상"으로 돌아왔을 때는 굳이 팡파레를 울리지 않는다(과한 축하 애니메이션은 오히려 "그동안 문제였다"는 걸 강조하게 됨) — 조용히 초록으로 복귀.

### 2.5 호스트 마이그레이션과의 관계

- `05-sync-architecture.md`가 채택을 제안한 "서버 기준 시계" 모델에서는 호스트 이탈이 재생 자체의 연속성을 깨지 않으므로, 마이그레이션 발생 시 동기화 상태 배지는 영향받지 않는 것을 기본으로 한다(배지는 그대로 "동기화됨" 유지). 대신 별도의 짧은 토스트(00문서 2.14)로 "호스트가 바뀌었다"는 사실만 알린다 — 두 정보(동기화 상태 vs 호스트 변경)를 같은 배지에 섞지 않는다.

## 3. 두 패턴의 상호작용

Now Playing 화면에서 "선곡자 배지"와 "동기화 상태 배지"는 의도적으로 같은 세로 축 근처에 배치해, "누가 골랐고 / 우리가 지금 같이 듣고 있다"는 두 메시지를 한 시야에서 동시에 전달한다(00문서 2.10a의 레이아웃 참고). 이 둘이 이 제품의 정체성을 시각적으로 압축한 지점이라고 판단한다.

## 4. 컴포넌트 설계 공통 원칙 — YouTube 광고 UI 비간섭 (2026-07-23 신규)

> 이 절은 특정 화면 하나가 아니라, YouTube 세션에서 만들어지는 **모든 컴포넌트에 적용되는 제약 원칙**이다. `00-ux-flow.md` 0절의 설계 원칙 7과 2.10c(YouTube Now Playing)에서 이미 언급했으나, 구현 에이전트가 컴포넌트 단위로 참고할 수 있도록 이 문서에도 명시적으로 정리한다.

### 4.1 근거

`03-youtube-integration.md` 5절(Required Minimum Functionality)과 8-2절(YouTube API Services Developer Policies 재확인)이 확인한 제약:
- **Section III.I.5**: API/데이터/플레이어에 실리는 광고를 수정·간섭·대체·차단하는 행위 일체 금지.
- **Section III.I.6**: YouTube 플레이어의 어떤 부분/기능이든 수정·변형·차단 금지.
- Required Minimum Functionality: YouTube 컨트롤 위에 자체 UI를 겹쳐 가리면 안 됨. 커스텀 재생 버튼은 허용되나 탭 시 반드시 실제 재생을 트리거해야 함.

### 4.2 컴포넌트 설계 규칙

1. **레이어링 금지**: 어떤 컴포넌트(배지, 토스트, 오버레이, 로딩 스피너 등)도 WebView/IFrame Player가 렌더링되는 영역 **위에 절대 배치하지 않는다**. 우리 UI 요소는 항상 플레이어 영역의 바깥(위/아래)에만 위치한다.
2. **정보성 표시는 허용, 조작성 표시는 금지**: "광고 재생 중" 같은 상태 텍스트(2.2a)는 플레이어 영역 바깥의 동기화 상태 배지에만 노출한다 — 광고 자체에 대한 스킵/음소거/타이머 등 조작 가능한 커스텀 컨트롤은 절대 만들지 않는다. YouTube가 이미 그 안에 표준으로 제공하는 컨트롤을 그대로 신뢰하고 노출한다.
3. **명령 억제 원칙**: 광고 재생 상태가 감지되면(2.2a), 동기화 엔진이 보내는 seek/재생 관련 명령을 해당 클라이언트가 일시적으로 무시하도록 설계한다 — 이는 UI 컴포넌트 자체의 규칙이라기보다 "UI가 보여주는 상태와 실제 클라이언트 동작이 일치해야 한다"는 원칙이다(배지가 "맞추는 중"이라고 보여주면서 실제로는 광고 위로 seek를 강행하는 모순이 없어야 함).
4. **커스텀 재생 버튼의 실동작 원칙**: Now Playing(2.10c)의 ⏮⏯⏭ 버튼처럼 우리가 만드는 커스텀 컨트롤은 장식이 아니라 실제로 IFrame Player API를 호출해 재생/일시정지/곡 전환을 트리거해야 한다(Required Minimum Functionality 요구사항).
5. **최소 크기 준수**: WebView 플레이어 영역은 어떤 레이아웃 변형(작은 화면, 접힌 미니플레이어 등)에서도 200×200px 이상을 유지하도록 컴포넌트 최소 크기 제약을 건다.

이 원칙들은 카피/톤의 문제가 아니라 **정책 준수(ToS/Developer Policies) 문제**이므로, 구현 단계에서 임의로 완화하지 않아야 한다. 의문이 있으면 리더에게 보고할 것을 제안한다.

## 5. 매칭 확인 카드 (Match Confirmation Card) — 혼합 모드 전용 (2026-07-23 신규)

> 근거: `docs/specs/09-cross-platform-mixed-mode.md` "결정 갱신 (2026-07-23)" 절(결정 2), `docs/specs/01-user-stories.md` US-105d/US-309/US-310, `docs/specs/04-playlist.md` "혼합 모드 플레이리스트 구조" 절. 화면 배치/흐름은 `00-ux-flow.md` 2.11a~2.11d에서 다뤘고, 이 절은 그 안에 실제로 들어가는 **컴포넌트 상세 스펙**을 1·2절(선곡자 배지, 동기화 상태 배지)과 같은 수준으로 정리한다.

### 5.1 왜 중요한가

혼합 세션(Spotify 참여자 + YouTube 참여자 공존, US-105d)에서 곡 매칭은 근본적으로 완전할 수 없다 — YouTube가 ISRC 등 업계 표준 식별자를 노출하지 않아, 매칭은 제목 유사도 + 아티스트 일치 + 재생 길이 오차를 조합한 **휴리스틱**에 의존한다(`09-cross-platform-mixed-mode.md` 1·2절). 사용자는 이번 결정에서 이 불완전성을 "없애는 것"이 아니라 "숨기지 않고 드러내는 것"으로 리스크 대응 전략을 정했다. 매칭 확인 카드는 그 전략을 실제 화면으로 구현하는 지점이며, **선곡자 배지("누가 골랐는가")·동기화 상태 배지("지금 같이 듣고 있는가")에 이어 이 앱의 세 번째 핵심 차별 UI**라고 판단한다 — "내가 듣는 이 곡이 정말 맞는 곡인가"를 참여자가 항상 확인할 수 있게 하는 신뢰 장치이기 때문이다.

이 컴포넌트가 없다면(자동 매칭 후 조용히 재생) 벌어질 수 있는 최악의 시나리오: 함께 듣기로 한 곡이 사실은 다른 에디션(라이브 버전, 리믹스, 커버 등)이어서 "같은 순간을 공유한다"는 핵심 가치 자체가 깨지는데, 사용자는 원인을 전혀 알 수 없다. 매칭 확인 카드는 이 실패를 "설명 가능한 실패"로 바꾸는 역할을 한다.

### 5.2 컴포넌트 구조

매칭 확인 카드는 하나의 매칭 결과 단위를 아래 요소로 구성한다(`00-ux-flow.md` 2.11b 참고):

| 요소 | 설명 |
|---|---|
| 썸네일 | 매칭된 트랙/영상의 앨범아트 또는 영상 썸네일 |
| 제목 | 매칭된 트랙의 실제 제목(공통 식별자의 제목과 다를 수 있음 — 예: "(Live)", "(Remastered)" 등 에디션 표기가 붙을 수 있음) |
| 아티스트/채널 | Spotify는 아티스트명, YouTube는 채널명(공식 채널이 아닐 경우 신뢰도에 감점 요인이 될 수 있음, 5.3 참고) |
| 재생 길이 | mm:ss 형식. 공통 식별자의 대표 길이와 함께 비교해 오차를 사용자에게 설명(ⓘ 안내문) |
| **플랫폼 배지** | "🎧 YouTube" 또는 "🟢 Spotify"처럼 이 매칭이 어느 서비스에서 이뤄졌는지 명시 — 참여자 각자 자신의 플랫폼에서만 매칭되므로, 이 배지는 항상 "나의" 플랫폼을 가리킨다 |
| **일치율/신뢰도 배지** | 5.3절 참고 |
| 액션 3종 | 확정하기 / 다른 결과 보기 / 직접 검색하기 (5.4절 참고) |

### 5.3 일치율/신뢰도 표시

`09-cross-platform-mixed-mode.md` "결정 2"는 "수치 또는 등급" 표시를 요구했다. 이 문서는 **수치(%)와 등급(높음/중간/낮음)을 함께 표시**하는 것을 제안한다 — 수치는 세밀한 비교(대체 후보 목록에서 후보 간 우열을 가릴 때 유용)를, 등급은 즉각적 직관(색+아이콘으로 한눈에 판단)을 각각 담당하게 하기 위함이다.

| 등급 | 아이콘 | 색(제안, `01-style-guide.md` 참고) | 버튼 강조 방식 |
|---|---|---|---|
| 높음 | ✅ 체크 | Sync Green 계열(동기화 "정상"과 톤 통일 — 단, 동일 색 재사용이 오히려 "동기화 상태"로 오인될 위험이 있어 실제 HEX는 구현 단계에서 재검토 필요) | "확정하기"를 1차 강조 버튼으로 배치 — 그대로 써도 안전하다는 뉘앙스 |
| 중간 | ❓/⚠ 물음표·주의 아이콘 | Amber 계열 | "확정하기"와 "다른 결과 보기"를 시각적으로 대등한 비중으로 배치(기본 강조를 어느 한쪽에 주지 않음) — 사용자가 판단해야 함을 알림 |
| 낮음 / 불확실 | ⚠ 경고 아이콘 + 카드 상단에 "확인 필요" 강조 배지 | Amber Alert/Muted Red 계열(단, 동기화 상태 배지의 "지연"/"끊김" 색과는 다른 채도·명도를 써서 혼동을 피할 것 — `01-style-guide.md` 6절의 YouTube 브랜드 컬러 혼용 금지 원칙과 같은 취지) | "확정하기"는 outline(2차 버튼)으로 톤을 낮추고, "다른 결과 보기"/"직접 검색하기"를 1차 버튼처럼 강조 — 다만 확정 자체를 막지는 않는다(강제 차단 아님, `09` 문서 "결정 2"는 "확인 필요 문구 강조"만 요구했지 확정을 차단하라고 하지 않았음) |

- **정확한 %/등급 산출 알고리즘·임계값은 이 문서에서 정하지 않는다.** `09-cross-platform-mixed-mode.md` "결정 4"가 명시한 대로 실측 스파이크(다양한 곡 표본으로 매칭 성공률/오매칭률 측정) 이후 구현 단계에서 확정하는 것이 원칙이다 — 이 컴포넌트 스펙은 "값이 주어졌을 때 어떻게 보여줄지"만 정의한다.
- **길이 오차 안내**: 매칭된 트랙 길이와 공통 식별자의 대표 길이 차이가 일정 수준 이상이면(임계값 미정) "라이브 버전/리믹스일 수 있어요" 같은 원인 추정 문구를 카드에 보조로 노출한다(`09` 문서 2절의 "길이 임계값을 신뢰도 점수의 한 축으로 재사용" 아이디어를 사용자 카피로 번역).
- 접근성: 1·2절과 동일 원칙 — 색상에만 의존하지 않고 아이콘 모양 + 텍스트 라벨(등급명, %)을 항상 병행한다.

### 5.4 세 가지 액션과 참여자별 독립성

1. **확정하기** — 표시된 매칭을 그대로 채택. 이 참여자에게는 이 트랙이 이후 재생/동기화 대상이 된다.
2. **다른 결과 보기** — 자동 매칭 로직이 계산한 차순위 후보 목록(`00-ux-flow.md` 2.11c)을 연다. 후보가 없으면 곧바로 "직접 검색하기"로 안내.
3. **직접 검색하기** — 참여자가 직접 키워드를 바꿔 재검색(`00-ux-flow.md` 2.11 재사용)해 스스로 원하는 트랙을 지정.

**참여자별 독립성 원칙(반드시 지킬 것, `09` 문서 결정 2-3)**: 이 카드는 항상 "나"의 화면에서 "내" 매칭 결과만 보여주고, 내 확정/재검색 행위는 다른 참여자의 매칭 상태에 어떤 영향도 주지 않는다. 두 사람이 같은 곡에 대해 서로 다른 트랙(예: 스튜디오 버전 vs 라이브 버전)을 확정해도 이는 시스템 오류가 아니라 혼합 모드가 구조적으로 허용하는 정상 상태다.

- (제안, 확정 아님) 카드 하단에 "민준님은 이미 확인했어요" 같은 작은 사회적 신호를 보조 정보로 덧붙일 수 있으나, 이것이 "그러니 나도 그냥 확정해도 된다"는 압박으로 읽히지 않도록 톤에 유의해야 한다. 다른 참여자의 확인 상태가 내 판단에 영향을 주는 문구(예: "2명이 이미 확정했어요, 당신도 확정하시겠어요?")는 지양한다.

### 5.5 예외 상태: 매칭 실패

검색 결과가 아예 없거나 있어도 신뢰도가 극히 낮아 "매칭"으로 볼 수 없는 경우, 카드 대신 빈 상태(`00-ux-flow.md` 2.11d)를 보여준다 — 썸네일 대신 "찾지 못함" 아이콘, "이 곡을 [플랫폼]에서 찾지 못했어요" 텍스트, [직접 검색해서 찾기]/[이 곡 없이 넘어가기] 두 액션. "이 곡 없이 넘어가기"를 선택한 참여자는 해당 곡 재생 구간 동안 자신의 Now Playing에서 "매칭 실패" 상태를 계속 보게 되며(`00-ux-flow.md` 2.10d), 이는 그 사람에게만 한정된 상태로 다른 참여자의 재생에는 영향을 주지 않는다.

### 5.6 다른 컴포넌트와의 관계

- **선곡자 배지(1절)와의 관계**: 매칭 확인 카드는 "누가 이 곡을 골랐는지"(선곡자)와 "내가 이 곡을 어떤 트랙으로 맞췄는지"(매칭)를 의도적으로 분리해 보여준다 — 카드 상단에는 필요 시 "◐ 지은님이 선곡" 배지를 함께 노출해도 되지만, 이는 매칭 자체의 신뢰도 판단과는 무관한 별개 정보임을 레이아웃상 구분한다(예: 선곡자 배지는 카드 헤더 영역, 매칭 정보는 카드 본문 영역).
- **동기화 상태 배지(2절)와의 관계**: 매칭이 미확인/실패 상태인 참여자의 동기화 상태 배지는 "정상"이 아니라 개인화된 문구("내 매칭 확인 필요" 등, `00-ux-flow.md` 2.10d)로 바뀌는 것을 제안한다 — 다만 신규 색상/아이콘을 추가하지 않고 기존 4단계 배지 체계(2.2절) 안에서 텍스트만 다르게 표시하는 방향을 제안한다(2.2a의 "광고 재생 중" 처리와 같은 절제 원칙 재사용 — 신규 상태를 남발하지 않는다).
- **참여자 목록(00문서 2.12)과의 관계**: 참여자별 매칭 대기/실패 건수를 참여자 목록에서도 보조 텍스트로 노출해, "왜 저 사람만 재생이 안 되는지"를 다른 참여자가 이해할 수 있게 한다.

### 5.7 엣지 케이스

- **한 곡에 여러 참여자가 동시에 매칭을 확인하는 경우**: 서버 관점에서는 각 참여자의 확정/재검색이 독립된 이벤트이므로 충돌이 없다(플레이리스트 항목 자체의 동시 편집 충돌과는 다른 성격, `04-playlist.md` "동시 편집 처리" 절 참고).
- **재확인/재매칭**: 참여자가 확정한 뒤에도 다시 카드를 열어 재검색으로 바꿀 수 있는지(예: 참여자 목록이나 플레이리스트 항목에서 "매칭 변경" 진입점을 상시 제공할지)는 이번 설계에서 다루지 않았다 — 필요 시 후속 논의 대상으로 `00-ux-flow.md` 4절에 남긴다.
- **대량 추가(개인 플레이리스트 Import, `04-playlist.md` 기능 목록 7번, `[P2]`) 시 매칭 확인 부담**: 곡 수백 개를 한 번에 Import하면 매칭 확인 큐(2.11a)가 한꺼번에 쌓일 수 있다 — 이 경우 큐를 일괄 처리하는 UI(예: "높음 등급은 일괄 확정, 중간/낮음만 개별 확인")가 필요할지는 Import 기능 자체가 P2인 점을 감안해 지금은 설계 범위 밖으로 남긴다.

## 6. 역할 배지 (Role Badge) — 방장/관리자/일반사용자 (2026-07-24 신규)

> 근거: `docs/specs/04-playlist.md` "권한 체계 — 방장/관리자/일반사용자 3단계" 절, `docs/specs/01-user-stories.md` US-210("참여자로서, 세션 화면에서 각 참여자의 역할(방장/관리자/일반사용자)을 배지 등으로 구분해 보고 싶다"). 화면 배치는 `00-ux-flow.md` 2.6(정원과 함께 세션 생성), 2.12(참여자 목록), 2.13(세션 설정)에서 다룬다.

### 6.1 왜 중요한가

3단계 권한 체계는 오직 "서비스 전환" 기능에만 적용되는 게이트다(`04-playlist.md` "기존 정책과의 정합성" 절 — 곡 추가/삭제/순서변경은 여전히 전원 가능). 그럼에도 사용자가 "누가 이 권한을 가졌는지"를 즉시 알아야, 방장이 관리자를 위임할 대상을 고를 수 있고, 일반사용자는 왜 전환 버튼이 막혀 있는지 납득할 수 있다. 이 배지는 **선곡자 배지(1절)와 다른 정보 축**이다 — 선곡자 배지는 "누가 이 곡을 골랐나"(참여자 고유 컬러 링), 역할 배지는 "이 사람이 세션에서 어떤 권한을 가졌나"(아이콘+라벨)를 나타내므로, 시각적으로 명확히 분리해 혼동을 피한다.

### 6.2 컴포넌트 구조

| 역할 | 아이콘 | 라벨 | 노출 조건 |
|---|---|---|---|
| 방장 (host) | 👑 | "방장" | 세션당 1명, 항상 노출 |
| 관리자 (admin) | 🛡 | "관리자" | 방장이 임명한 인원(상한 미정, 6.4절 참고), 항상 노출 |
| 일반사용자 (regular) | 없음 | 없음(배지 미표시) | 기본 상태 — 별도 배지를 붙이지 않는 것 자체가 "일반사용자"를 나타낸다(정보 과밀 방지) |

- 색상은 `01-style-guide.md` 7절(신규, 역할 배지 컬러) 참고. 선곡자 배지의 참여자별 컬러 링(1.2절)과는 다른 색 체계를 쓴다 — 아바타 링은 그대로 두고, 역할 배지는 아바타 오른쪽 위 코너의 작은 아이콘 오버레이 또는 이름 옆 텍스트+아이콘 pill로 병기한다.
- 접근성: 아이콘 모양 + 텍스트 라벨을 항상 병행(01문서 5절 접근성 원칙 재사용). 일반사용자에게 배지가 없다는 사실 자체가 정보이므로, 스크린리더 등 보조기술에는 "역할: 일반 참여자"를 명시적으로 읽어주는 것을 제안한다(시각적으로는 배지 없음, 접근성 레이어에서는 명시적 라벨).

### 6.3 배치 위치별 상세

| 화면 | 표시 방식 |
|---|---|
| 참여자 목록(`00-ux-flow.md` 2.12) | 이름 옆에 아이콘+라벨 인라인. 기존 연결 상태(정상/지연) 배지와는 시각적으로 구분되는 위치(줄 바꿈 또는 좌우 분리)에 배치해 혼동 방지 |
| 곡 항목의 선곡자 배지(1절) | 기본은 미노출(정보 과밀 방지) — 필요 시 곡 항목 탭 시 상세 정보에서만 역할을 부가 표시하는 것을 제안(확정 아님) |
| Now Playing 하단 참여자 아바타 스택(2.10a/c/d) | 방장 아바타에만 작은 왕관 아이콘을 겹쳐(overlay) 표시 — 관리자/일반사용자는 스택 뷰에서 생략하고, 탭 시 참여자 목록(2.12)에서 전체 확인 |
| 세션 설정(2.13) | "내 역할: 방장/관리자/일반 참여자" 한 줄로 본인 역할을 항상 인지할 수 있게 표시 |

### 6.4 관리자 임명 UI (2026-07-24 확정으로 단순화됨 — 임명권자는 방장, 세부 흐름은 여전히 UI 자리만)

> `04-playlist.md` "권한 체계" 절 "(2026-07-24 확정) 관리자 임명 방식 — 임명권 주체" — **관리자 임명·해제 권한은 방장이 갖는다**는 점이 리더 전달 사용자 결정으로 확정됐다(해석의 여지 없음). 이전 라운드에서는 "누가 임명권을 갖는지"조차 미확정이라 진입점만 잠정적으로 방장 전용으로 가정해뒀는데, 이번 확정으로 그 가정이 그대로 맞아떨어져 **구조 변경 없이 확정 사실만 반영**하면 된다. 다만 "확인 필요" 1번(임명 취소 절차, 관리자 스스로 사임 가능 여부)·2번(인원 상한)은 여전히 미확정이므로, 그 부분은 계속 **진입점(entry point) 수준**으로만 다룬다.

- 참여자 목록(2.12)에서 **방장에게만(확정)** 각 참여자 항목에 오버플로우 메뉴(⋮) 또는 롱프레스 메뉴를 노출하고, 그 안에 "관리자로 임명" / (이미 관리자인 경우) "관리자 해제" 메뉴 항목을 둔다. 관리자 본인이나 일반사용자에게는 이 메뉴 자체가 노출되지 않는다.
- 선택 시 확인 다이얼로그("OO님을 관리자로 임명할까요? 관리자는 서비스 전환 권한을 갖게 돼요")를 거치는 것을 제안하나, 임명 취소(해제) 시 확인 절차·즉시 반영 여부, 관리자 스스로 사임 가능한지 등은 여전히 확정 전이므로 다이얼로그의 정확한 문구·버튼 구성은 이번 설계에서 확정하지 않는다.
- 관리자 인원 상한이 없거나(제안) 향후 정해질 경우를 모두 수용할 수 있도록, 메뉴 자체는 상한 도달 여부와 무관하게 항상 노출하고, 상한 초과 시에는 별도 UI 변화 없이 에러 토스트로만 처리하는 방향을 제안한다(구체 상한값이 미정이므로 UI가 "상한까지 N명 남음" 같은 정보를 미리 표시하지는 않는다).
- 호스트 마이그레이션 발생 시 이 메뉴의 노출 권한이 새 방장에게 자동 이전되는 것은 자연스러운 연장이나, 기존 관리자 목록 유지 여부(`04-playlist.md` 확인 필요 3번)는 이 UI 설계에 영향을 주지 않는다 — 목록이 유지되든 재구성되든 "방장만 이 메뉴를 본다"는 원칙은 동일하게 적용 가능하다.

### 6.5 엣지 케이스

- 방장이 세션을 나가 호스트 마이그레이션이 발생하면 새 방장의 배지가 👑로 바뀐다. 기존 방장이 관리자로 강등되는지, 세션을 완전히 떠나는지는 `04-playlist.md` 확인 필요 3번이 미확정이다 — 이 문서는 "역할이 바뀌면 배지가 바뀐다"는 일반 원칙만 반영하고 구체 승계 로직에는 관여하지 않는다.
- Free 계정 사용자도 역할(방장/관리자/일반사용자)을 가질 수 있다 — 역할 배지와 Free 계정 배지(9절)는 서로 독립적인 축이므로 동시에 표시될 수 있다(예: "🛡 관리자 · Free · 재생 불가").

## 7. 세션 정원 설정 컴포넌트 (Capacity Stepper) (2026-07-24 신규, 2026-07-24 갱신 — 기본값 2명 확정으로 단순화됨)

> 근거: `docs/specs/04-playlist.md` "세션 정원" 절, US-207. 배치는 `00-ux-flow.md` 2.6(세션 생성 화면). **(2026-07-24 확정)** 정원 기본값이 2명으로 확정되어, 이전에 "값을 아예 지정하지 않은 초기 상태"를 별도로 대비하던 서술은 필요 없어졌다(이력은 아래에 보존).

### 7.1 컴포넌트

```
정원
[ − ]   2명   [ + ]
2명 ●───────────── 12명
```

- 스테퍼(−/+) + 현재 값 숫자 표시를 기본으로 하고, 보조로 슬라이더 트랙을 함께 노출해 전체 범위(2~12) 대비 현재 값을 직관적으로 보여준다(둘 중 하나만 써도 무방 — 구현 단계에서 스테퍼 단독으로 단순화 가능).
- 범위: 최소 2명 ~ 최대 12명(절대 상한, `04-playlist.md` "세션 정원" 절).
- **(2026-07-24 확정) 기본값은 2명이다.** 화면 진입 시 스테퍼/슬라이더가 처음부터 "2명" 값으로 렌더링되고, 방장이 별도로 조작하지 않아도 그대로 "정원 2명"으로 세션이 생성된다. 방장은 여전히 +/− 또는 슬라이더 드래그로 2~12명 범위에서 원하는 값으로 자유롭게 조정할 수 있다.
  - 옛 서술(대체됨, 이력 보존): ~~기본값은 미정이므로(확인 필요 2번), 초기 노출 값을 강조 없이(굵게 표시하지 않는 등) 보여줘서 "방장이 아직 확정하지 않은 값"임을 시각적으로 암시하는 것을 제안한다.~~ 기본값이 확정된 지금은 "아직 정해지지 않은 값처럼 흐리게 보여줄" 필요가 없다 — 2명을 다른 값과 동일한 강조 톤(굵게 등)으로 명확히 표시해도 된다.
- 세션 생성 후 정원 변경 가능 여부(확인 필요 1번)는 이 컴포넌트가 "생성 화면 전용"인지 "세션 설정에도 재사용 가능"인지를 결정한다 — 현재는 **생성 화면 전용**으로만 배치하고, 추후 변경 가능 정책이 확정되면 `00-ux-flow.md` 2.13(세션 설정)에도 같은 컴포넌트를 재사용해 추가하는 것을 제안한다(컴포넌트 자체는 화면에 독립적으로 재사용 가능하도록 설계).

### 7.2 정원 초과 대응 UI 자리

- 정원이 가득 찬 세션에 참여 코드/딥링크로 진입 시도할 경우를 대비해, `00-ux-flow.md` 2.8(세션 참여) 화면에 "이 세션은 정원이 가득 찼어요(8/8)" 같은 인라인 오류 상태를 추가하는 것을 제안한다(이번 갱신에서 신규 반영).
- 정원이 참여 인원 기준인지 재생 인원 기준인지가 확정되지 않았으므로(확인 필요 3번), 이 오류 문구도 "정원"이라는 중립 단어만 쓰고 어느 쪽으로도 특정하지 않는다.

## 8. 참여 인원 vs 재생 인원 표시 (Flexible Count Display) (2026-07-24 신규, 2026-07-24 갱신 — 항상 필요할 수 있는 기본 컴포넌트로 격상)

> 근거: `docs/specs/04-playlist.md` "Free 계정 처리" 절 확인 필요 3번, "디자인 에이전트 전달 사항" 3번. **(2026-07-24 확정)** Free 계정 세션 참여는 해석 A(참여는 항상 허용, 재생만 제한)로 확정됐다 — 이에 따라 "정원 12명이 참여/재생 중 무엇을 가리키는지"는 여전히 확인 필요 상태로 남아 있지만, **"참여 인원 ≥ 재생 인원 상황이 실제로 발생한다"는 사실 자체는 이제 확정적**이다(Spotify 세션에 Free 계정 참여자가 한 명이라도 있으면 반드시 발생). 그래서 이 패턴은 더 이상 "혹시 몰라 대비하는 선택적 확장"이 아니라, **Free 계정 참여자가 있는 세션(특히 Spotify 세션)이라면 항상 실제로 쓰이는 기본 컴포넌트**로 격을 올려 다룬다. "정원이 참여/재생 중 무엇을 기준으로 하는지"가 확정되기 전에도, 아래 조건부 렌더링 방식 자체는 그대로 유효하다(정원 표시(7절)와는 별개 컴포넌트).

### 8.1 기본 형태 (두 숫자가 같을 때)

```
🟢 동기화됨 · 3명 함께 듣는 중
```

- 기존 패턴(2.3절)을 그대로 유지한다 — 세션에 Free 계정 참여자가 없는 경우(또는 YouTube 세션처럼 Free 여부와 무관하게 전원 재생 가능한 경우) 이 단일 숫자 형태로 충분하다.

### 8.2 확장 형태 (두 숫자가 다를 때, 실제로 자주 쓰이는 형태)

```
🟢 동기화됨 · 5명 참여 중 (재생 3명)
```

- "참여 인원"을 기본 숫자로 유지하고, 재생 인원이 참여 인원보다 적을 때만 괄호로 보조 표기를 덧붙인다 — 두 숫자가 같으면 괄호를 아예 노출하지 않아(8.1 형태로 자동 축약) 정보 과밀을 피한다.
- 탭하면 참여자 목록(`00-ux-flow.md` 2.12)으로 드릴다운되고, 거기서 각 참여자가 Free 계정으로 인해 "재생 불가" 상태인지 개별적으로 확인할 수 있다(9절 Free 계정 배지와 연결).
- 이 패턴은 **조건부 렌더링 컴포넌트**로 설계한다 — "참여 인원 = 재생 인원"이면 8.1 형태, 다르면 8.2 형태로 자동 전환된다. **(2026-07-24 확정)** Spotify 세션에 Free 계정 참여자가 섞여 있으면 8.2 형태가 노출되는 것이 확정된 시나리오이므로, 구현 단계는 이 컴포넌트를 "선택적으로 켤 수도 있는 부가 기능"이 아니라 참여자 목록/Now Playing 상태 바의 **기본 렌더링 로직**으로 취급해야 한다.

### 8.3 참여자 목록에서의 표시

```
참여자 (5) · 재생 3명
```

- 참여자 목록 헤더도 동일한 조건부 원칙을 따른다(두 숫자가 같으면 "참여자 (N)"만 표시).

## 9. Free 계정 안내 UI (2026-07-24 신규, 2026-07-24 갱신 — 해석 A 확정으로 단순화됨, 해석 B 대비 시나리오는 이력 보존)

> 근거: `docs/specs/04-playlist.md` "Free 계정(무료 등급) 처리" 절, US-106. **(2026-07-24 확정)** Free 계정 사용자의 세션 참여 자체는 항상 허용된다(해석 A 확정, 해석 B는 폐기) — 세션 진입을 막는 시나리오는 더 이상 그릴 필요가 없고, "세션 안에서 재생만 제한된다"는 **단일 시나리오**로 이 절의 범위를 좁힌다. 다만 **경고문 노출 여부가 세션의 활성 서비스에 따라 시스템이 자동으로 결정하는 조건부 로직**은 반드시 유지해야 한다(Spotify=표시 / YouTube=미표시, 방장이 켜고 끄는 토글이 아님). 화면 배치는 `00-ux-flow.md` 2.4b(신규)에서 다룬다.

### 9.1 실제로 쓰이는 형태 — 인라인 배너 + 참여자 목록 배지

**(2026-07-24 확정)** 아래 1·2번(인라인 배너 + 참여자 목록 배지)이 이번에 확정된 유일한 형태다. 3번(세션 진입을 막는 모달)은 해석 B가 폐기되면서 더 이상 쓰이지 않는다 — 설계 이력 보존 차원에서 9.1z에 원문 그대로 남겨둔다.

1. **인라인 배너 (Spotify 세션에서만 노출)**: Now Playing 화면 상단 또는 재생 컨트롤 영역에 상시 노출되는 얇은 배너.

```
⚠ Free 계정으로는 곡 재생(동기화 재생)에 참여할 수 없어요
[ Premium 알아보기 ]
```

2. **인라인 배지 (참여자 목록 항목, 서비스와 무관하게 항상 노출)**: 참여자 목록(2.12)의 해당 참여자 항목에 "Free · 재생 불가" 라벨을 작게 병기한다 — 다른 참여자들도 "왜 이 사람은 재생 인원에서 빠졌는지" 이해할 수 있게 한다(8절과 연결). 이 배지는 세션의 활성 서비스가 Spotify든 YouTube든 상관없이 Free 계정 참여자 본인에게는 항상 유효한 사실을 나타내는 것이라 조건부 로직 없이 항상 노출한다(9.2 조건부 로직은 1번 배너에만 적용되고, 2번 배지에는 적용되지 않음에 유의).

```
[아바타] 민준  Free · 재생 불가
```

### 9.1z 폐기된 형태 — 참여 차단 모달 (이력 보존, 더 이상 사용하지 않음)

> 아래는 해석 B(참여 자체 제한)가 폐기되기 전, "두 해석 모두 대비"하던 라운드에서 설계했던 형태다. **2026-07-24 확정으로 폐기됐다** — 세션 참여는 항상 허용되므로 이 화면으로 분기하는 경로 자체가 없다. 향후 정책이 다시 바뀌지 않는 한 새로 그릴 필요가 없으며, 오직 과거 설계 의도를 추적하기 위한 이력으로만 남긴다.

- ~~모달 (해석 B 대응 — 참여 자체를 제한하는 경우): 세션 참여/생성 시도 시점에 Free 계정임이 감지되면 기존 2.4(Premium 아님 안내) 화면과 동일한 레이아웃을 재사용하되, 카피만 "Free 계정으로는 이 세션에 참여할 수 없어요"로 교체한다.~~

### 9.2 경고문 노출 조건 — 세션 활성 서비스에 따른 자동 판단 (2026-07-24 확정, 필수 로직)

> 이 절이 이번 갱신에서 가장 중요하게 유지해야 할 부분이다 — "형태를 단순화한다"는 것이 "조건 분기 자체를 없앤다"는 뜻이 아니다.

- **Spotify 세션**: 9.1의 인라인 배너를 표시한다 — Spotify Free는 재생 제어 API 제약으로 동기화 재생이 불가능하기 때문이다(`04-playlist.md` 근거, `02-spotify-integration.md` 참고).
- **YouTube 세션**: 인라인 배너를 표시하지 않는다 — YouTube는 Premium 여부와 무관하게 이용 가능하다는 기존 결정(US-103)과 동일한 기조다.
- **판단 주체**: 방장이 켜고 끄는 별도 토글이 아니라, 세션의 활성 서비스 타입을 시스템이 읽어 자동으로 배너 노출 여부를 결정한다. 구현 단계는 이 배너 컴포넌트를 세션의 `activeService` 상태를 구독하는 조건부 렌더링으로 설계해야 한다(방장 UI에 "Free 안내 배너 켜기/끄기" 같은 별도 설정 항목을 만들지 않는다).
- **혼합(Mixed) 세션**: 참여자 개인이 실제로 매칭·재생에 사용하는 플랫폼(Spotify 또는 YouTube, `00-ux-flow.md` 2.6c)을 기준으로 개인별로 판단하는 것이 자연스러운 확장이나, `04-playlist.md`가 이 적용을 명시적으로 확정하지 않았으므로 구현 착수 전 재확인이 필요하다(임의로 확정하지 않음).
- 서비스명 노출 범위: 위 배너/배지 카피에 "Spotify Free 계정"처럼 서비스명을 명시할지, "Free 계정"이라고 범용적으로 쓸지는 확정된 바 없다 — Spotify 세션에서만 노출되는 조건이 이미 서비스를 특정하고 있으므로 범용 카피("Free 계정으로는...")를 그대로 써도 문맥상 자연스럽다는 점을 참고용으로 남긴다.

### 9.3 톤

- 01 스타일가이드의 "부정적 상태도 안심시키는 톤" 원칙(2.4절과 동일 기조)을 따른다 — Free 계정 사용자를 배제하는 느낌보다 "지금은 재생만 제한, 다른 건 다 할 수 있다"는 뉘앙스를 유지한다(해석 A가 확정된 지금 이 톤 원칙은 선택이 아니라 실제로 적용해야 하는 유일한 시나리오다).

## 10. 서비스 전환 버튼의 권한별 노출 상태 (2026-07-24 신규)

> 근거: `docs/specs/04-playlist.md` "권한 체계" 절, US-208. 배치는 `00-ux-flow.md` 2.13(세션 설정), 2.10b(플레이리스트 탭 서비스 칩).

### 10.1 세 가지 상태

| 사용자 역할 | 버튼 상태 | 표시 |
|---|---|---|
| 방장/관리자 | 활성 | 기존과 동일, `[ 전환하기 ▸ ]` 탭 가능 |
| 일반사용자 | 비활성(disabled) + 안내 문구 | 버튼은 회색 톤으로 표시되고 탭해도 동작하지 않으며, 바로 아래 보조 텍스트로 "방장 또는 관리자만 전환할 수 있어요" 노출 |
| (참고) 혼합 세션 | 버튼 자체 미노출 | 기존 정책(`00-ux-flow.md` 2.13) 그대로 유지 — 이번 갱신과 무관 |

```
🎧 음악 서비스: Spotify
   [ 전환하기 ▸ ]  (비활성, 회색)
   ⓘ 방장 또는 관리자만 전환할 수 있어요
```

- 버튼을 완전히 숨기지 않고 "비활성 + 사유 안내"를 채택한 이유: `04-playlist.md` "제안" 절이 "일반사용자에게 전환 UI를 숨기거나 비활성화하는 것을 제안"이라고 두 옵션을 열어뒀으나, 이 문서는 **비활성화 쪽을 채택**한다 — 완전히 숨기면 일반사용자가 "이 기능이 원래 없나 보다"고 오해할 수 있고, 권한 체계 자체를 학습할 기회를 잃는다. 비활성화+문구는 US-210(역할 가시성)과도 정합적이다.
- **중요(구현 유의)**: `04-playlist.md` "제안" 절이 명시한 대로, 이 UI 상태는 **클라이언트 측 표시일 뿐**이며 실제 권한 검증은 서버(Cloud Functions) 측에서 강제돼야 한다 — 이 문서(디자인)는 화면 표시만 다루고, 권한 우회 방지는 구현 단계의 책임임을 명시한다.
- 같은 원칙을 플레이리스트 탭 상단의 서비스 칩(`00-ux-flow.md` 2.10b, 전환 단축 진입점)에도 동일하게 적용한다 — 일반사용자에게는 칩을 탭해도 전환 다이얼로그(2.13a)로 진입하지 않고, 동일한 안내 토스트("방장 또는 관리자만 전환할 수 있어요")만 노출한다.

### 10.2 역할 배지(6절)와의 관계

- 이 버튼 상태는 6절의 역할 배지와 항상 정합적이어야 한다 — 예를 들어 참여자 목록에서 자신이 🛡 관리자 배지를 달고 있는데 세션 설정에서 전환 버튼이 비활성으로 보이는 모순이 없어야 한다(권한 변경 시 실시간 반영 필요, 구현 단계 유의 사항).
