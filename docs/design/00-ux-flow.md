## 0. 이 문서의 설계 원칙

1. **투명성 우선(US-406)**: "우리 서버가 음악을 스트리밍하는 게 아니라, 각자의 Spotify 앱이 로컬로 재생하고 우리는 그것을 맞춰준다"는 사실을 사용자가 오해하지 않도록 온보딩과 세션 화면 곳곳에서 반복적으로, 그러나 부담스럽지 않게 노출한다.
2. **선곡자 가시성**: 협업 플레이리스트의 모든 곡에 "누가 넣었는지"가 항상 보여야 한다 (`02-key-ui-patterns.md`에서 상세).
3. **동기화 상태 가시성**: 사용자가 "지금 다들 같은 곳을 듣고 있는지"를 언제나 한눈에 확인할 수 있어야 한다 (`02-key-ui-patterns.md`에서 상세).
4. **Premium 게이팅과 앱 설치 요건을 조기에, 친절하게 안내**: `02-spotify-integration.md`의 제약(전원 Premium, Spotify 공식 앱 설치 필수)을 사용자가 세션에 깊이 들어가기 전에 알게 해서, 나중에 좌절하지 않게 한다.
5. **최소 탭 구조**: MVP 범위가 크지 않으므로 화면 계층을 얕게 유지한다 (하단 탭 없이, 스택 기반 네비게이션 + 세션 내부만 2탭 정도).
6. **(2026-07-23 신규) 서비스 전환은 "숨겨진 설정"이 아니라 "안심시키는 이벤트"로 다룬다**: 세션 도중 Spotify ↔ YouTube 전환(US-105b)은 재생이 끊기는 부담스러운 동작이므로, 전환 전에는 확인 다이얼로그로 결과를 예고하고, 전환 중에는 무슨 일이 벌어지는지 설명하며, 전환 후에는 "이전 서비스 쪽 플레이리스트는 사라지지 않았다"(US-105c/US-308)를 반드시 재확인시킨다.
7. **(2026-07-23 신규) YouTube 플레이어 UI는 가리지 않는다**: YouTube 세션에서는 우리 앱 안에 실제 영상 재생 영역(WebView + IFrame Player)이 노출된다. YouTube가 그 위에 그리는 네이티브 컨트롤·광고 스킵 버튼·타이머 등은 우리 UI 요소로 덮거나 대체하지 않는다(`03-youtube-integration.md` 5절·8-2절, YouTube API Services Developer Policies III.I.5/6 근거). 이 원칙은 화면 설계뿐 아니라 컴포넌트 설계 시에도 반드시 지켜야 한다(`02-key-ui-patterns.md` 참고).
8. **(2026-07-23 신규) 혼합 모드의 매칭은 절대 "조용히" 확정되지 않는다**: 혼합 세션(Spotify 참여자와 YouTube 참여자가 동시에 공존, US-105d)에서 곡마다 각 참여자의 기기가 자신의 플랫폼에서 벌이는 매칭은 근본적으로 불완전할 수 있다(`09-cross-platform-mixed-mode.md` 1·2절 — YouTube가 ISRC 등 표준 식별자를 노출하지 않아 매칭이 제목/아티스트 유사도 기반 휴리스틱에 의존). 이 불완전함을 감추지 않고, 참여자 각자가 매칭 결과를 직접 확인하거나 수정할 수 있는 화면(2.11a~2.11d, 신규)을 반드시 거치게 한다. 이 확인은 참여자별로 독립적이며, 한 사람의 확인이 다른 참여자에게 자동 적용되지 않는다(US-309/US-310, `09` 문서 "결정 2").

> **(2026-07-23 갱신 메모)** 최초 온보딩 흐름(A~H, Spotify OAuth 로그인)은 기존처럼 Spotify를 예시로 유지했다. YouTube 계정(Google 로그인)은 온보딩 시점에 강제로 요구하지 않고, "세션 생성/참여/전환 시점에 실제로 그 서비스가 필요해지는 순간"에만 연동을 요구하는 **지연 연동(lazy connect)** 방식으로 설계했다 — Spotify만 쓰고 싶은 사용자에게 불필요한 YouTube 로그인을 강제하지 않기 위한 디자인 판단이다. 최초 온보딩에서 두 서비스를 한꺼번에 선택하게 할지는 리더/기획 재확인이 필요하면 후속 논의 대상으로 남긴다(4절 참고).
> **(2026-07-23 추가 메모)** 혼합 세션은 "지연 연동" 원칙을 참여자 개인 단위로 한 번 더 적용한다 — 세션이 혼합 모드라는 사실 자체는 세션 생성/참여 시점에 정해지지만, "나 개인이 Spotify로 참여할지 YouTube로 참여할지"는 그 세션에 실제로 들어가는 순간(2.6c)에만 묻는다. 곡 매칭 확인(2.11a~2.11d)은 반대로 "묻지 않고 넘어가는" 지연이 허용되지 않는다 — 이 둘의 차이(참여 방식 선택은 마찰을 줄이기 위해 최초 1회로 최소화, 매칭 확인은 신뢰 문제라 생략 불가)를 설계 시 구분해서 다뤘다.

## 2. 화면별 상세

### 2.1 스플래시 (Splash)

- 로고 + 앱 이름만 짧게. 아래에 "장거리에서도, 같은 순간에" 같은 한 줄 태그라인(카피는 추후 확정, 여기선 톤 예시).
- 목적: Spotify 연동 상태 확인 + 세션 재접속 여부 체크하는 동안의 로딩 화면.

### 2.2 온보딩 (최초 실행 시, 3컷 카드형, US-601)

```
┌─────────────────────────┐
│        [일러스트]         │
│                          │
│  "같은 곡을, 같은 순간에"   │
│  멀리 있어도 함께 듣는 방을  │
│  만들어보세요              │
│                          │
│   ● ○ ○        [다음]    │
└─────────────────────────┘
```

- 1컷: 핵심 가치("같은 곡을 같은 순간에 함께").
- 2컷: 협업 플레이리스트("누구나 곡을 추가하고, 누가 골랐는지 표시돼요").
- 3컷: **투명성 카드(US-406 대응)** — "재생은 각자의 Spotify 앱에서 이뤄져요. feel_music_share는 그걸 맞춰주는 역할이에요." + 아이콘으로 "서버가 오디오를 흘려보내지 않음"을 시각화(예: 두 스마트폰이 나란히, 각자 스피커 아이콘 + 가운데 동기화 화살표).
- 마지막 컷 CTA: "Spotify로 시작하기".

### 2.6 세션 생성 (US-201, US-105) (2026-07-23 갱신: YouTube 라디오 옵션 활성화, 혼합 옵션 신규 추가 / 2026-07-24 갱신: 정원 설정 UI 추가)

```
┌─────────────────────────┐
│  ← 세션 만들기            │
│                          │
│  세션 이름                │
│  [ 우리 둘의 플레이리스트 ] │
│                          │
│  음악 서비스               │
│  ( ● ) Spotify            │
│  ( ○ ) YouTube            │
│  ( ○ ) 혼합 (Mixed)        │  ← (2026-07-23 신규, US-105d)
│                          │
│  정원                     │  ← (2026-07-24 신규, US-207)
│  [ − ]    8명    [ + ]    │
│  2명 ──────●──────  12명  │
│                          │
│  ⓘ 이 방은 Spotify 전용이  │
│  에요. 참여자 모두 Spotify  │
│  Premium이 필요해요.       │
│  (나중에 세션 설정에서       │
│  YouTube로 전환할 수 있어요)│
│                          │
│  [   세션 만들기   ]       │
└─────────────────────────┘
```

- US-105(한 세션은 한 번에 하나의 서비스로만 재생) 정책을 라디오 버튼 + 안내 문구로 명확히 표현하는 기본 구조는 유지한다.
- **(2026-07-23 갱신)** YouTube가 MVP로 승격되면서 라디오 버튼의 "준비 중" 비활성 처리를 해제했다. 두 옵션 모두 실제로 선택 가능하다.
- **(2026-07-23 신규)** 세 번째 옵션 "혼합(Mixed)"이 추가됐다(US-105d, `09-cross-platform-mixed-mode.md` "결정 갱신" 절) — 참여자마다 각자 자신이 로그인한 플랫폼(Spotify 또는 YouTube)으로 참여하는 세션 유형이다. 멜론/지니뮤직은 이 옵션을 골라도 여전히 참여할 수 없다(`08-korean-services-melon-genie.md` 결론, 재검토 대상 아님) — 실질적으로 "Spotify 참여자와 YouTube 참여자의 공존"을 뜻한다.
- **(2026-07-23 갱신)** 안내 배너(ⓘ)는 선택된 라디오에 따라 동적으로 문구가 바뀐다:
  - Spotify 선택 시: "이 방은 Spotify 전용이에요. 참여자 모두 Spotify Premium이 필요해요."
  - YouTube 선택 시: "이 방은 YouTube 전용이에요. YouTube 정책상 무광고가 보장되지 않아 광고가 보일 수 있어요." — US-103, `03-youtube-integration.md` 3절·7절·8절이 확인한 광고 리스크를 세션 생성 시점에도 반복 고지한다(US-406과 같은 취지의 투명성 원칙).
  - **(2026-07-23 신규) 혼합 선택 시**: "이 방은 혼합 모드예요. 참여자마다 자신이 쓰는 서비스(Spotify 또는 YouTube)로 각자 참여해요. 곡을 추가하면 각자의 플랫폼에서 자동으로 찾아드리고, 맞는지 항상 확인을 받을게요." — "서비스 전환" 문구 대신 매칭 확인이라는 혼합 모드 고유의 신뢰 장치를 생성 시점부터 예고한다.
- **(2026-07-23 신규)** 두 경우(Spotify/YouTube) 모두 배너 마지막 줄에 "나중에 세션 설정에서 전환할 수 있어요"를 덧붙인다 — 이 선택이 영구 고정이 아니라는 사실(US-105b)을 생성 시점부터 알려서, 사용자가 "잘못 고르면 못 바꾸는 결정"이라고 오인해 부담을 느끼지 않게 한다. **혼합 선택 시에는 이 문구를 노출하지 않는다** — 혼합 모드에는 US-105b(서비스 전환) 자체가 적용되지 않기 때문이다(`09` 문서 "결정 3"). 대신 "혼합 여부는 세션 생성 후 다른 유형으로 바꿀 수 없어요"라는 문구가 필요할지는 확정하지 않았다(제안 단계, 4절 후속 논의 참고).
- 방 생성 직후, 선택한 서비스에 따라 분기한다:
  - Spotify 선택: 기존과 동일하게 Spotify 앱 미설치 감지 시 2.6a로 분기.
  - **(2026-07-23 신규)** YouTube 선택: YouTube 계정(Google 로그인) 미연동 감지 시 2.6b로 분기.
  - **(2026-07-23 신규)** 혼합 선택: 호스트 자신도 이 세션의 참여자이므로, 먼저 호스트 본인이 참여할 플랫폼을 선택/확인하는 화면(2.6c)을 거친 뒤, 선택된 플랫폼에 따라 기존 2.6a/2.6b 흐름으로 자연스럽게 이어진다.
- **(2026-07-24 신규) 정원 설정**: 방장이 세션 생성 시 **2~12명** 범위에서 정원을 직접 지정한다(US-207, `04-playlist.md` "세션 정원" 절). 스테퍼(−/+)와 슬라이더 트랙을 함께 노출해 절대 범위(2~12) 대비 현재 값을 직관적으로 보여주는 것을 제안한다 — 컴포넌트 상세 스펙(초기값 처리, 세션 생성 후 화면 재사용 가능성 등)은 `02-key-ui-patterns.md` 7절 참고.
  - **미확정 사항을 UI가 함부로 단정하지 않는다**: (1) 기본값(방장이 값을 지정하지 않았을 때 무엇을 보여줄지)이 아직 정해지지 않았으므로, 이 화면은 임의의 초기 노출 값(예시상 "8명")을 강조 없이 보여주되 방장이 명시적으로 조정하지 않아도 되는 "제안값"으로 취급한다. (2) "정원 12명"이 참여 인원 전체를 가리키는지, Free 계정을 제외한 재생 인원만 가리키는지도 확인 필요 상태이므로, 이 화면의 라벨은 의도적으로 "정원"이라는 중립적 단어만 쓰고 "참여 정원"/"재생 정원" 어느 쪽으로도 특정하지 않는다(확정되면 라벨만 조정).
  - 세션 생성 후 정원 변경 가능 여부도 확인 필요 상태다 — 이번 설계에서는 이 컴포넌트를 세션 생성 화면 전용으로만 배치했다(가능해지면 2.13 세션 설정에도 동일 컴포넌트를 재사용해 추가하는 것을 제안).

```
┌─────────────────────────┐
```

```
│                          │
│  이 방은 혼합 모드예요.     │
│  당신이 사용할 플랫폼을      │

│                          │

│  ( ○ ) YouTube로 참여      │
│                          │

│  있으면 자동으로 선택돼요.   │
│  다음에 이 방(또는 다른      │
│  혼합 방)에 들어올 때도      │

```

- 이 화면은 두 진입 경로에서 재사용된다: (1) 호스트가 혼합 세션을 생성한 직후(2.6에서 "혼합" 선택, mermaid의 I0m→I1m), (2) 참여자가 혼합 세션에 코드/딥링크로 참여할 때(2.8, mermaid의 J1b→J3m). 두 경로 모두 "이 계정으로 최초 1회만" 선택하면 되고, 이후에는 자동으로 이전 선택을 재사용하는 것을 제안한다(매번 재차 묻지 않음 — 매칭 확인처럼 매번 확인시켜야 하는 것과는 성격이 다르다고 판단, 세션 참여 자체의 마찰을 줄이기 위함).
- 선택 후에는 선택한 플랫폼에 따라 기존 2.6a(Spotify 앱 설치 유도)/2.6b(YouTube 로그인 유도) 화면으로 자연스럽게 이어진다(조건이 이미 충족돼 있으면 곧바로 통과해 대기실/세션메인으로 진입).
- **(2026-07-23 신규)** 이 선택은 "세션 전체가 어떤 서비스로 재생될지"를 정하는 게 아니라, **"나 개인이 어떤 서비스로 참여할지"**를 정하는 것이다 — `09-cross-platform-mixed-mode.md` "결정 3"이 강조한 대로, 혼합 세션에는 세션 전체 차원의 "전환" 개념이 없다. 다른 참여자는 이 화면에서 다른 선택을 할 수 있고, 그것이 정상적인 상태다.
- 참여자가 이 화면에서 내린 선택은 참여자 목록(2.12)과 Now Playing(2.10d)에서 서비스 아이콘으로 다른 사람에게도 드러난다.
- 참여자가 세션 도중 자신의 개인 참여 플랫폼을 재선택(변경)할 수 있는지는 이번 설계 범위에서 확정하지 않았다 — 4절 후속 논의 참고.

### 2.10 세션 메인 화면 (핵심 화면)

두 개의 하위 뷰를 스와이프/탭으로 전환하는 구조를 제안: **Now Playing** / **플레이리스트**. (둘 다 항상 필요하지만 화면 밀도상 완전 통합보다 분리 후 상단 미니 플레이어로 연결하는 편이 낫다고 판단.)

**(2026-07-23 갱신)** Now Playing의 실제 화면 구성은 **현재 세션의 유형이 무엇인지에 따라 달라진다**(US-105b/US-105d):
- Spotify 전용 세션 → 2.10a (참여자 각자의 공식 Spotify 앱을 원격 제어하는 구조 — 우리 앱 화면에는 앨범 아트/메타데이터만 표시).
- YouTube 전용 세션 → **2.10c(신규)** — 우리 앱 안의 WebView + IFrame Player 영역이 실제로 화면에 보이는 구조.
- **혼합 세션 → 2.10d(신규, 2026-07-23)** — 참여자마다 자신이 선택한 플랫폼(2.6c)에 따라 2.10a 또는 2.10c의 레이아웃을 그대로 물려받되, "지금 나와 다른 참여자가 서로 다른 서비스를 쓰고 있다"는 사실을 드러내는 요소가 추가된다. 혼합 세션에는 US-105b(세션 도중 서비스 전환)가 애초에 적용되지 않는다(`09-cross-platform-mixed-mode.md` "결정 3").

플레이리스트 탭(2.10b)은 세 세션 유형에서 레이아웃 골격은 같지만, **지금 보고 있는 것이 어느 서비스의 플레이리스트인지**를 상단에 항상 명시한다(US-105c/US-308 대응 — 상세는 2.10b 갱신 내용 참고). 다만 혼합 세션은 애초에 플레이리스트가 서비스별로 나뉘지 않고 하나뿐이므로(`04-playlist.md` "혼합 모드 플레이리스트 구조" 절), 2.10b의 "서비스 칩"은 혼합 세션에서는 표시되지 않는다 — 대신 곡별 매칭 확인 상태(2.11a~2.11d)가 그 자리를 대체한다.

#### 2.10a Now Playing 탭

```
┌─────────────────────────┐
│ 우리 둘의 플레이리스트 ▾  ⋮│
│                          │
│         [앨범 아트]        │
│                          │
│   곡 제목이 들어갑니다      │
│   아티스트 이름            │
│                          │
│   ◐ 이 곡은 민준님이 선곡   │  ← 선곡자 배지 (02 문서 참고)
│                          │
│  ─────●───────────────  │
│  1:32              3:45 │
│                          │
│   ⏮      ⏯      ⏭      │
│                          │
│  🟢 동기화됨 · 3명 함께 듣는 중│  ← 동기화 상태 (02 문서 참고)
│                          │
│  [프로필][프로필][프로필]  │  ← 참여자 아바타 스택 (탭 시 목록)
└─────────────────────────┘
```

- 재생 컨트롤은 US-405가 P2로 미뤄졌으므로 MVP에서는 전원에게 동일하게 노출(권한 제한 없음).
- 하단 "동기화됨 · 3명 함께 듣는 중"이 상시 노출되는 상태 바 — 앱의 핵심 가치를 계속 체감시키는 장치.
- **(2026-07-23 갱신)** 이 화면은 **Spotify 세션 전용**이다. YouTube 세션의 Now Playing 화면은 구조가 달라 별도로 2.10c에서 다룬다.
- **(2026-07-24 신규)** Free 계정 참여자가 있어 "참여 인원"과 "재생 인원"이 달라질 수 있는 경우, 이 상태 바는 "5명 참여 중 (재생 3명)" 형태로 자동 확장된다 — 두 숫자가 같으면 위 예시처럼 단일 숫자만 표시한다. 조건부 렌더링 상세는 `02-key-ui-patterns.md` 8절 참고.

#### 2.10b 플레이리스트 탭 (2026-07-23 갱신: 서비스 표시 칩 추가)

```
┌─────────────────────────┐
│ 우리 둘의 플레이리스트 ▾  ⋮│
│ 🟢 Spotify 플레이리스트 ▸  │  ← (2026-07-23 신규) 지금 보고 있는 서비스 명시 + 전환 진입점
│  Now Playing 미니바        │  ← 탭 전환해도 재생 상태 계속 보이도록 sticky
│  [앨범아트 소] 곡제목  ▶︎/⏸ │
│                          │
│  다음 곡들                 │
│  ┌──────────────────┐   │
│  │▶ 곡 A — 아티스트     │   │
│  │  🅢 지은            │   │ ← 재생 중 표시 + 선곡자
│  ├──────────────────┤   │
│  │  곡 B — 아티스트     │   │
│  │  🅜 민준        ⠿   │   │ ← 드래그 핸들
│  ├──────────────────┤   │
│  │  곡 C — 아티스트     │   │
│  │  🅢 지은        ⠿   │   │
│  └──────────────────┘   │
│                          │
│  재생 완료 (2곡) ▾ 접힘    │  ← 이미 재생된 곡은 기본 접힘
│                          │
│           [ + 곡 추가 ]    │
└─────────────────────────┘
```

- **디자인 결정(기획 04번 문서에서 "디자인 단계 결정"으로 위임된 사항)**: 이미 재생 완료된 곡과 대기 중인 곡을 시각적으로 분리한다.
  - "다음 곡들" 섹션만 드래그로 순서 변경 가능(드래그 핸들 ⠿ 노출).
  - "재생 완료" 섹션은 기본 접혀 있고, 펼쳐도 순서 변경 불가(읽기 전용 히스토리) — 이미 지나간 순서를 바꾸는 것은 사용자에게 혼란을 줄 수 있다고 판단.
  - 현재 재생 중인 곡은 "다음 곡들" 리스트 맨 위에 별도 강조(▶ 아이콘, 드래그 핸들 없음 — 재생 중인 곡을 실수로 옮기는 것을 방지).
- 곡 삭제는 각 항목 스와이프 또는 롱프레스 메뉴로 제공(실수 삭제 방지를 위해 확인 다이얼로그를 곁들이는 것을 제안 — 04문서의 "삭제 남용" 리스크 완화).
- **(2026-07-23 신규) 서비스 칩(예: "🟢 Spotify 플레이리스트")**: 헤더 바로 아래 상시 노출한다. US-105c/US-308(서비스별 플레이리스트 독립 보존) 정책을 사용자가 오해하지 않도록 하기 위한 핵심 장치다 — "지금 보이는 목록이 세션 전체의 유일한 목록이 아니라 이 서비스만의 목록"임을 항상 인지시킨다.
  - 칩을 탭하면 세션 설정의 서비스 전환 화면(2.13a)으로 바로 이동하는 단축 진입점으로 겸용한다.
  - (제안, 선택 개선안) 비활성 서비스 쪽에도 곡이 쌓여 있다면 칩 옆에 작은 보조 텍스트로 힌트를 줄 수 있다 — 예: "Spotify 플레이리스트 · YouTube에 3곡 대기 중". 이는 US-105c가 강조하는 "보존되고 있다"는 사실을 플레이리스트 화면에서도 한 번 더 체감시키는 장치이나, 정보 밀도가 높아질 수 있어 필수는 아니고 제안 단계로 남긴다.

### 2.10c Now Playing — YouTube 세션 전용 (2026-07-23 신규, US-105b/US-406)

```
┌─────────────────────────┐
│ 우리 둘의 플레이리스트 ▾  ⋮│
│                          │
│ ┌──────────────────┐   │
│ │                    │   │
│ │  [WebView 영상 영역] │   │  ← IFrame Player 실제 렌더링(최소 200×200px 이상)
│ │  (광고 구간에는 YouTube│   │
│ │   자체 스킵버튼/타이머 │   │
│ │   이 여기 그대로 노출) │   │
│ │                    │   │
│ └──────────────────┘   │
│                          │
│   곡(영상) 제목            │
│   채널명                  │
│                          │
│   ◐ 이 곡은 민준님이 선곡   │
│                          │
│   ⏮      ⏯      ⏭      │  ← 우리 앱 컨트롤(플레이리스트 이동/재생 트리거용)
│                          │
│  🟡 맞추는 중... (광고 재생 중)│ ← 동기화 상태 (02문서 2.2 갱신 참고)
│  [프로필][프로필][프로필]  │
└─────────────────────────┘
```

- 이 화면의 핵심 차이(2.10a Spotify 대비): 영상/오디오가 **우리 앱의 WebView 안에서 직접 렌더링**된다(`03-youtube-integration.md` 2절, IFrame Player API). Spotify처럼 "각자의 공식 앱이 알아서 재생"하는 구조가 아니라, 재생 자체가 이 화면 안에 보이는 구조다 — US-406(투명성) 문구도 이 차이를 반영해 서비스별로 달라져야 한다(아래 참고).
- **YouTube Required Minimum Functionality 정책 준수(`03-youtube-integration.md` 5절)**:
  - WebView 플레이어 영역은 최소 200×200px 이상 크기를 유지한다.
  - YouTube가 그 위에 표시하는 네이티브 컨트롤(재생바, 볼륨, 광고 스킵 버튼/카운트다운 등)을 우리 UI로 겹쳐 가리지 않는다 — 우리의 커스텀 컨트롤(⏮⏯⏭)은 플레이어 영역 **바깥**(아래쪽)에 배치하고, 플레이어 영역 위에 오버레이하는 자체 UI 요소를 두지 않는다.
  - 우리 커스텀 재생 버튼(⏯)은 탭 시 반드시 IFrame Player의 실제 재생(`playVideo()` 등)을 트리거해야 한다(장식용 버튼 금지 — 정책상 요구사항).
- **광고 재생 중 상태 처리(2026-07-23 신규, `03-youtube-integration.md` 8절)**: 신규 5번째 상태를 만들지 않고 **기존 "맞추는 중" 상태를 재사용**하기로 판단했다(판단 근거는 `02-key-ui-patterns.md` 2.2절 갱신 내용 참고). 다만 원인을 알 수 있도록 배지에 괄호로 보조 텍스트("광고 재생 중")를 덧붙이는 것을 제안한다.
  - 광고 재생이 감지된 클라이언트는 서버가 보내는 seek 등 동기화 명령을 일시적으로 무시한다(`03-youtube-integration.md` 8-3절) — 이는 광고를 건너뛰려는 시도로 오인될 수 있는 명령(seek)을 광고 구간에 보내지 않기 위함이며, YouTube API Services Developer Policies III.I.5/6(광고·플레이어 변조 금지) 위반을 피하기 위한 조치다.
  - 광고의 스킵 버튼/카운트다운 타이머는 YouTube가 그리는 그대로 노출하며, 우리 UI가 이를 가리거나 대신 조작하는 요소(예: 자동 스킵 버튼, 광고 위 오버레이)는 만들지 않는다.
  - 광고 시청 여부는 참여자마다 다를 수 있어(같은 영상이라도 광고 삽입/길이가 시청자별로 다를 수 있음), "누구는 광고를 보고 누구는 본편을 듣는" 상태가 한동안 공존할 수 있다 — 참여자별 상세 상태(2.12)에서도 이 차이가 드러날 수 있음을 전제로 한다.
- US-406(투명성) 대응: YouTube 세션 최초 진입 시 1회성 안내 배너/토스트로 "이 방은 앱 안에서 영상이 직접 재생돼요. YouTube 정책상 광고가 보일 수 있어요"를 노출하는 것을 제안(Spotify의 온보딩 3컷 투명성 카드·2.6 안내 배너와 대칭되는 위치, 세션별 서비스가 다르므로 세션 진입 시점에 다시 확인시키는 것이 자연스럽다고 판단).
- Late join(US-402)/재접속 시에도 화면 구조는 동일 — WebView가 다시 로드된 뒤 서버 기준 위치로 seek하고 재생을 재개한다.

### 2.10d Now Playing — 혼합(Mixed) 세션 전용 (2026-07-23 신규, US-105d/US-309)

```
┌─────────────────────────┐
│ 우리 둘의 플레이리스트 ▾  ⋮│
│                          │
│  (이 아래는 내가 선택한     │
│   플랫폼에 따라 2.10a      │
│   또는 2.10c 레이아웃과     │
│   동일 — 예시는 나=YouTube) │
│                          │
│ ┌──────────────────┐   │
│ │  [WebView 영상 영역] │   │
│ └──────────────────┘   │
│                          │
│   곡(영상) 제목            │
│   채널명                  │
│                          │
│   ◐ 이 곡은 민준님이 선곡   │
│                          │
│   ⏮      ⏯      ⏭      │
│                          │
│  🟢 동기화됨 ▶ 나: YouTube  │  ← (2026-07-23 신규) 내 플랫폼 아이콘 병기
│  [프로필🟢][프로필🎧]      │  ← (2026-07-23 신규) 참여자 아바타 옆 서비스 아이콘
└─────────────────────────┘
```

- 이 화면은 **완전히 새로운 레이아웃이 아니다** — 내가 이 혼합 세션에서 선택한 플랫폼(2.6c)에 따라 2.10a(Spotify) 또는 2.10c(YouTube) 레이아웃을 그대로 물려받는다. 추가되는 것은 "지금 나와 다른 참여자가 서로 다른 서비스를 쓰고 있다"는 사실을 드러내는 두 가지 요소뿐이다.
- **(2026-07-23 신규) 동기화 상태 배지 옆 "내 플랫폼" 표시**: 기존 동기화 상태 배지(`02-key-ui-patterns.md` 2.3절) 바로 옆에 내가 지금 재생에 쓰고 있는 서비스의 작은 아이콘 + 이름을 상시 병기한다(예: "🟢 동기화됨 ▶ 나: YouTube"). US-406(투명성 원칙)의 혼합 모드 버전이다 — 상대가 무슨 서비스를 쓰는지는 몰라도 최소한 "나는 지금 무엇으로 듣고 있는가"는 항상 확인 가능해야 한다.
- **(2026-07-23 신규) 참여자 아바타 스택에 서비스 아이콘 병기**: 하단 참여자 아바타(선곡자 배지와 같은 컬러 링 원칙 재사용, `02-key-ui-patterns.md` 1.2절) 옆에 작은 서비스 배지(예: 초록 점=Spotify, 헤드폰 아이콘=YouTube — 실제 아이콘/색은 `01-style-guide.md` 확정 시 결정)를 추가로 붙여, "지은님은 Spotify로, 민준님은 YouTube로 듣고 있다"를 한눈에 파악하게 한다. 탭하면 참여자 목록(2.12)으로 드릴다운된다.
- **매칭 미확인/실패 상태와의 관계(중요)**: 만약 현재 재생 중인 곡이 "나"의 매칭이 아직 확인되지 않았거나(2.11b 확인 대기 중) 매칭 자체에 실패한 상태라면(2.11d), 이 화면의 영상/앨범아트 영역 자리에 그 상태를 알리는 카드가 대신 표시되는 것을 제안한다:
  - 확인 대기 중: "이 곡의 매칭을 아직 확인하지 않았어요 [확인하러 가기]" — 탭하면 2.11b로 이동.
  - 매칭 실패: "이 곡을 내 플랫폼(YouTube)에서 찾지 못했어요 [직접 검색하기]" — 탭하면 수동 검색(2.11/2.11c)으로 이동.
  - 이 두 경우 동기화 상태 배지도 다른 참여자들과 별개로 "나만" 재생이 멈춰 있는 상태이므로, 배지 문구를 "동기화됨"이 아니라 "내 매칭 확인 필요"처럼 개인화된 문구로 바꾸는 것을 제안한다(다른 참여자의 배지에는 영향 없음 — `02-key-ui-patterns.md` 2.3절 "세션 전체 vs 개인" 구분 원칙을 그대로 적용).
- 참여자별 매칭 상태(확정/대기/실패)를 참여자 목록(2.12)에서도 함께 노출하는 것을 제안한다(아래 2.12 갱신 참고).

### 2.11 곡 검색 및 추가 (바텀시트, US-301)

```
┌─────────────────────────┐
│  ✕   곡 검색               │
│  [ 🔍 곡, 아티스트 검색 ]   │
│                          │
│  ┌──────────────────┐   │
│  │[아트] 곡 이름           │   │
│  │      아티스트 · 3:12   │   │
│  │                  [+]  │   │
│  ├──────────────────┤   │
│  │[아트] 곡 이름 (이미 있음)│   │
│  │      아티스트 · 3:40   │   │
│  │              [담김✓]  │   │
│  └──────────────────┘   │
└─────────────────────────┘
```

- 검색은 디바운스 적용(연타 방지, Spotify Web API 호출량 관리 차원).
- "이미 있음" 표기는 04 문서 정책(기본 허용 + UI 표시)을 반영.
- 추가 시 짧은 토스트: "곡이 추가됐어요" + 선곡자 아바타가 리스트에 애니메이션으로 나타나는 것을 제안(선곡 행위 자체를 축하하는 듯한 마이크로 인터랙션 — 톤 문서 참고).

#### 혼합 모드에서의 확장 (2026-07-23 신규, US-309/US-310 — 이번 갱신의 핵심)

Spotify 전용/YouTube 전용 세션에서는 위 2.11 화면에서 검색 결과를 고르면 그대로 플레이리스트에 추가되고 끝난다. **혼합 세션에서는 여기서 끝나지 않는다** — 플랫폼 중립 식별자(제목/아티스트)로 곡이 플레이리스트에 등록되는 순간, **세션에 참여 중인 모든 참여자의 클라이언트가 각자 자신의 플랫폼에서 그 곡을 검색해 매칭을 시도**한다(곡을 실제로 추가한 사람뿐 아니라 다른 참여자들도 동일하게 매칭 대상이다 — `04-playlist.md` "혼합 모드 플레이리스트 구조" 절). 아래 2.11a~2.11d가 그 결과를 각 참여자에게 어떻게 보여주고 확인받을지를 다룬다. `02-key-ui-patterns.md` 5절에 이 패턴군을 컴포넌트 상세 스펙 수준으로 정리했다.

#### 2.11a 매칭 진행 중 (2026-07-23 신규)

- 매칭은 보통 짧게(수 초 이내로 기대) 끝나므로, 화면을 가로막는 전체 화면 로딩보다는 가벼운 표시를 제안한다: 플레이리스트 탭(2.10b)의 해당 곡 항목에 작은 스피너 + "내 플랫폼에서 찾는 중..." 텍스트를 임시로 얹는다. 매칭이 오래 걸리는 경우(네트워크 지연 등)를 대비해 일정 시간(정확한 값은 구현 단계) 초과 시 "찾는 데 시간이 걸려요" 안내로 전환하는 것을 제안한다.
- 곡을 직접 추가한 참여자 본인에게는 추가 직후 곧바로 2.11a → 2.11b(또는 2.11d)로 자동 진행하는 흐름을 기본으로 제안한다. 반면 **다른 참여자**들에게는 지금 보고 있는 화면(Now Playing이든 플레이리스트든)을 강제로 가로막지 않고, 아래 "매칭 확인 알림 배지" 방식으로 비강제 알림을 준다 — 전면 모달로 즉시 끼어들면 곡이 여러 개 연달아 추가될 때(예: 개인 플레이리스트 Import) 방해가 크다고 판단했다.
- **매칭 확인 알림 배지(제안)**: 플레이리스트 탭 상단과 "+곡 추가" 버튼 근처에 작은 배지로 "확인할 매칭 2개" 같은 카운트를 상시 노출한다. 탭하면 대기 중인 매칭을 하나씩 2.11b로 보여준다(여러 개면 다음/이전으로 넘기는 큐 형태). US-309/US-310의 "반드시 확인받아야 한다"는 요구사항을 지키면서도 매 곡마다 강제로 화면을 가로막지 않기 위한 디자인 절충안이다(확정 아님, 4절 후속 논의 참고).

#### 2.11b 매칭 확인 카드 (2026-07-23 신규, 핵심 화면 — US-309/US-310)

```
┌─────────────────────────┐
│  ✕      곡 매칭 확인        │
│                          │
│  "우리가 걷던 밤"을         │
│  당신의 YouTube에서        │
│  이렇게 찾았어요            │
│                          │
│  ┌──────────────────┐   │
│  │[썸네일]  우리가 걷던 밤(Live)│
│  │ 🎧 YouTube          │   │
│  │ 코스모스 - Topic     │   │
│  │ 3:52                │   │
│  │                     │   │
│  │  ✅ 일치율 92% · 높음  │   │
│  └──────────────────┘   │
│                          │
│  ⓘ 원곡(3:45)과 길이가 조금│
│  달라요 — 라이브 버전일 수   │

│                          │

└─────────────────────────┘
```

- **필수 표시 항목**(`04-playlist.md`/`09-cross-platform-mixed-mode.md` "결정 2" 근거): 매칭된 트랙의 썸네일, 제목, 아티스트/채널, 재생 길이, 매칭에 쓰인 서비스(내 플랫폼) 아이콘, 일치율(수치 또는 등급).
- 일치율 등급별 시각 처리(높음/중간/낮음)와 버튼 강조 방식의 상세는 `02-key-ui-patterns.md` 5절에서 다룬다(이 문서에서는 화면 배치까지만).
- **길이 오차 안내(ⓘ)**: 매칭된 트랙과 공통 식별자(원곡 정보)의 길이 차이가 일정 수준 이상이면(임계값은 구현 단계 확정) "라이브 버전/리믹스일 수 있어요" 같은 구체적 원인 추정 문구를 덧붙이는 것을 제안한다(`09` 문서 2절의 "길이 오차를 신뢰도 점수의 한 축으로 재사용" 아이디어를 사용자에게 보이는 카피로 번역한 것).
- **세 가지 액션**: 확정하기(그대로 채택) / 다른 결과 보기(2.11c로 이동) / 직접 검색하기(2.11 재사용).
- **참여자별 독립성(반드시 지킬 것)**: 이 카드는 항상 "나"의 화면에서 "내" 매칭 결과만 보여준다. 다른 참여자가 이미 확정했는지 여부는 이 카드의 판단에 영향을 주지 않는다(`09` 문서 결정 2-3).

- 각 후보 항목은 2.11b와 동일한 정보 밀도(썸네일/제목/아티스트/길이/일치율)를 유지해 일관성을 준다.
- 후보를 선택하면 2.11b로 돌아가되, 선택한 후보가 새로운 "매칭 결과"로 카드에 반영된 상태로 다시 확인시킨다(선택 즉시 확정 처리하지 않음 — 한 번 더 확인 기회를 준다, US-310 취지 존중).

#### 2.11d 매칭 실패 안내 (2026-07-23 신규)

```
┌─────────────────────────┐
│      [찾지 못함 아이콘]     │
│                          │
│  이 곡을 YouTube에서       │
│  찾지 못했어요              │
│                          │
│  "우리가 걷던 밤" - 코스모스 │
│  에 해당하는 결과를 당신의    │
│  YouTube에서 찾지 못했어요.  │
│                          │
│  [ 직접 검색해서 찾기 ]      │
│  [ 이 곡 없이 넘어가기 ]     │
└─────────────────────────┘
```

- 검색 결과가 아예 없거나, 있어도 신뢰도가 극히 낮아 "매칭"으로 간주할 수 없는 경우 이 상태를 보여준다(임계값은 구현 단계 결정).
- **[직접 검색해서 찾기]**: 참여자가 직접 키워드를 바꿔가며 검색(기존 2.11 화면 재사용)해 스스로 원하는 트랙을 지정할 수 있다.
- **[이 곡 없이 넘어가기]**: 이 참여자는 이 곡이 재생되는 동안 자신의 플랫폼에서는 재생하지 않고 대기 상태로 넘어간다(2.10d의 "매칭 실패" 상태와 연결). 다른 참여자의 재생에는 영향을 주지 않는다 — 혼합 모드가 애초에 참여자별로 독립적인 재생을 전제하기 때문에 성립하는 동작이다.
- 이 상태는 곡 전체에 대한 실패라기보다 **"이 참여자의 이 플랫폼"에 한정된 실패**임을 강조한다 — 같은 곡이라도 다른 참여자(다른 플랫폼)는 정상적으로 매칭됐을 수 있다.

### 2.12 참여자 목록 (바텀시트, US-203) (2026-07-24 갱신: 역할 배지·관리자 임명 진입점·Free 계정 표시 추가)

```
┌─────────────────────────┐
│  참여자 (5) · 재생 3명       │  ← (2026-07-24 신규) 참여/재생 인원 분리 표시(02문서 8절, 두 숫자가 같으면 "참여자 (N)"만 표시)
│                          │
│  [아바타]👑 지은(방장)  🟢 정상   ⋮│  ← ⋮ 메뉴(관리자 임명 등)는 방장 본인 화면에만 노출
│  [아바타]🛡 민준(관리자) 🟡 지연 1.2s ⋮│
│  [아바타] 나(수아)      🟢 정상    │  ← 일반사용자는 역할 배지 없음(02문서 6.2절)
│  [아바타] 준호  Free·재생불가 🟢 정상│  ← (2026-07-24 신규) Free 계정 표시(02문서 9절)

└─────────────────────────┘
```

- 참여자별 연결 상태 아이콘/색(정상/지연/끊김)을 여기서도 상세히 보여줌 — Now Playing 탭의 전체 요약 배지와 상호보완.
- **(2026-07-24 신규) 역할 배지**: 방장(👑)·관리자(🛡)는 이름 옆에 아이콘+라벨을 항상 병기하고, 일반사용자는 별도 배지를 붙이지 않는다(배지가 없는 것 자체가 "일반사용자" 상태). 색상/아이콘 상세는 `01-style-guide.md` 7절, 컴포넌트 스펙은 `02-key-ui-patterns.md` 6절 참고.
- **(2026-07-24 신규) 관리자 임명 진입점(UI 자리)**: 방장에게만 각 참여자 항목 우측에 오버플로우 메뉴(⋮)가 노출되고, "관리자로 임명"/"관리자 해제" 메뉴 항목을 담는다. **임명 세부 흐름(확정/취소 방식, 관리자 스스로 사임 가능 여부 등)은 `04-playlist.md` "권한 체계" 절 "확인 필요" 1번이 아직 미확정이므로, 이 문서는 진입점(메뉴 자리)만 확정하고 그 뒤에 이어질 정확한 다이얼로그 흐름은 확정하지 않는다.** 상세는 `02-key-ui-patterns.md` 6.4절 참고.
- **(2026-07-24 신규) Free 계정 표시**: Free 계정 참여자는 이름 옆에 "Free · 재생 불가" 보조 텍스트를 병기한다(9절 Free 계정 안내 UI와 연동). 이 표시는 해석 A(참여 허용, 재생만 제한)가 채택된 경우를 전제로 한 예시이며, 해석 B(참여 자체 제한)가 채택되면 애초에 이 목록에 Free 계정 참여자가 나타나지 않으므로 이 표시 자체가 불필요해진다 — `04-playlist.md` 확인 필요 사항이 정해지기 전까지는 두 경우 모두 이 컴포넌트 설계로 커버된다.

#### 혼합 세션에서의 확장 (2026-07-23 신규, US-105d)

```
┌─────────────────────────┐
│  참여자 (3) · 혼합 세션      │
│                          │
│  [아바타]🎧 지은(호스트) 🟢 정상│
│         YouTube          │
│  [아바타]🟢 민준        🟡 지연 1.2s│
│         Spotify          │
│  [아바타]🎧 나(수아)    🟢 정상│

└─────────────────────────┘
```

- **(2026-07-23 신규)** 혼합 세션에서는 참여자 이름 아래에 그 사람이 지금 어떤 플랫폼으로 참여 중인지(2.6c에서 선택한 값)를 작은 아이콘+텍스트로 병기한다(Spotify=초록 점, YouTube=헤드폰 아이콘 등 — 실제 아이콘/색상은 `01-style-guide.md`의 Spotify/YouTube 브랜드 컬러 사용 원칙 재사용).
- **(2026-07-23 신규)** 그 참여자에게 확인 대기 중인 매칭이 있으면(2.11a/2.11b) "매칭 대기 N건" 같은 보조 텍스트를 함께 보여줄 것을 제안한다 — 다른 참여자가 "저 사람은 아직 확인 안 했나 보다"를 짐작할 수 있게 해서, 재생이 어긋나 보일 때 원인을 이해하기 쉽게 한다(US-403/404가 강조하는 "왜 어긋났는지 이해 가능해야 한다"는 원칙의 혼합 모드 버전).
- 이 확장은 Spotify 전용/YouTube 전용 세션에는 적용되지 않는다 — 그 경우는 세션 전체가 하나의 서비스만 쓰므로 참여자별 서비스 표시 자체가 불필요하다.

### 2.13 세션 설정 / 나가기 (2026-07-23 갱신: 서비스 전환 항목 추가 / 2026-07-24 갱신: 역할 표시·전환 버튼 권한별 상태 반영)

```
┌─────────────────────────┐
│  ← 세션 설정               │
│                          │
│  내 역할: 방장 👑           │  ← (2026-07-24 신규) 02문서 6.3절
│                          │
│  🎧 음악 서비스: Spotify   │  ← (2026-07-23 신규) 현재 활성 서비스 표시 + 전환 진입점
│     [ 전환하기 ▸ ]         │
│                          │
│  초대 코드 다시 보기         │
│  Spotify 연동 상태 확인     │  ← 활성 서비스에 따라 라벨 동적 변경(YouTube면 "YouTube 연동 상태 확인")
│  [ 세션 나가기 ]            │
│  [ 세션 종료하기 ] (호스트만) │
└─────────────────────────┘
```

```
  (일반사용자 화면 예시, 2026-07-24 신규)
│  내 역할: 일반 참여자         │
│                          │
│  🎧 음악 서비스: Spotify   │
│     [ 전환하기 ▸ ] (비활성) │
│     ⓘ 방장 또는 관리자만    │
│     전환할 수 있어요        │
```

- **(2026-07-23 신규, US-105b)** "음악 서비스" 항목이 최상단에 추가됐다. 현재 활성 서비스를 아이콘+텍스트로 보여주고, "전환하기"를 누르면 2.13a(전환 확인 다이얼로그)로 진입한다.
- **(2026-07-24 갱신) 서비스 전환 권한**: US-208 확정에 따라 이 항목의 "전환하기" 버튼은 이제 **방장/관리자에게만 활성**이다. 일반사용자에게는 버튼이 비활성(회색 톤)으로 표시되고, 바로 아래 "방장 또는 관리자만 전환할 수 있어요" 안내 문구가 함께 노출된다(완전히 숨기지 않는다 — 숨기면 기능 자체를 모르게 될 수 있어 US-210의 역할 가시성 취지와 맞지 않는다고 판단). 같은 원칙이 플레이리스트 탭 상단의 서비스 칩(2.10b, 전환 단축 진입점)에도 동일하게 적용된다. 상세 컴포넌트 스펙은 `02-key-ui-patterns.md` 10절 참고.
- **(2026-07-24 신규, 구현 유의)** 이 비활성화는 **클라이언트 UI 표시일 뿐**이다 — `04-playlist.md` "제안" 절이 명시한 대로 실제 권한 검증은 서버(Cloud Functions) 측에서 반드시 강제해야 하며, 버튼을 숨기거나 비활성화하는 것만으로 권한 우회를 막을 수 없다.
- 옛 서술(대체됨, 이력 보존): ~~이 항목은 MVP에서는 방장/참여자 누구나 볼 수 있고, 실제로 전환을 실행하는 것도 "전원 허용"을 기본값으로 제안한다(US-405가 세부 권한 관리를 P2로 미뤘으므로 이와 동일한 기조 — 다만 "전환"은 "재생 중지"에 준하는 파급력이 있어 향후 권한 세분화 시 "방장만 전환 가능"으로 좁히는 옵션이 먼저 고려될 만하다는 점을 후속 논의로 남긴다, 4절 참고).~~ 이 서술은 US-208이 "전원 허용"을 "방장/관리자 전용"으로 구체화하기 전의 것이라 위 갱신 내용으로 대체한다.
- **(2026-07-23 신규, 혼합 세션 예외)** 혼합 세션에서는 이 "음악 서비스: 전환하기" 항목 자체가 노출되지 않는다 — `09-cross-platform-mixed-mode.md` "결정 3"이 명시한 대로 혼합 모드에는 세션 전체 차원의 "전환" 개념이 없다(참여자마다 이미 서로 다른 서비스가 동시에 활성 상태이므로 바꿀 대상이 없음). 대신 이 자리에는 "내가 참여 중인 플랫폼: YouTube"처럼 **읽기 전용 정보**만 표시하는 것을 제안한다. 참여자 본인이 이 개인 플랫폼 선택(2.6c) 자체를 세션 도중 바꿀 수 있는 기능은 이번 설계 범위에서 다루지 않았다(4절 후속 논의 참고).

#### 2.13a 서비스 전환 확인 다이얼로그 (2026-07-23 신규, US-105b/US-105c)

```
┌─────────────────────────┐
│   음악 서비스 전환         │
│                          │
│  Spotify → YouTube로      │
│  전환할까요?               │
│                          │
│  ⓘ 지금 재생 중인 곡이      │
│  멈춰요. 전환 후 YouTube    │
│  플레이리스트로 다시         │
│  동기화가 시작돼요.          │
│                          │
│  ⓘ Spotify 플레이리스트는  │
│  삭제되지 않고 그대로        │
│  저장돼 있어요 — 나중에      │
│  다시 Spotify로 돌아오면    │
│  이어서 쓸 수 있어요.        │
│                          │
│  [ 취소 ]    [ 전환하기 ]   │
└─────────────────────────┘
```

- 두 안내 문구를 의도적으로 분리했다: 첫 번째("재생이 멈춘다")는 즉각적인 행동 결과 예고(US-105b), 두 번째("플레이리스트는 보존된다")는 US-105c/US-308이 우려하는 오해 — "전환하면 지금까지 쌓은 곡이 사라지는 거 아닌가" — 를 정면으로 해소하기 위함이다. 이번 갱신에서 가장 중요한 카피라고 판단해 버튼 바로 위, 다이얼로그에서 가장 눈에 띄는 위치에 배치했다.
- 대상 서비스가 아직 사전 조건(로그인/앱 설치 등)을 충족하지 못한 경우, "전환하기"를 누르면 이 다이얼로그가 닫히며 해당 서비스의 온보딩 화면(Spotify→2.6a, YouTube→2.6b)으로 바로 분기한다. 조건 충족 후 자동으로 2.13b(전환 중 오버레이)로 이어진다.

#### 2.13b 전환 중 오버레이 (2026-07-23 신규)

```
┌─────────────────────────┐
│                          │
│      (반투명 오버레이)      │
│                          │
│   YouTube로 전환하는 중...  │
│         ⏳               │
│                          │
│  잠시 후 YouTube 플레이    │
│  리스트로 이어집니다        │
│                          │
└─────────────────────────┘
```

- 세션 대기실(2.9)과 톤을 맞춘 "무슨 일이 벌어지고 있는지 설명하는" 짧은 전환 화면 — 원칙 0-6/0-1(투명성 우선)의 연장이다.
- 내부적으로는 (a) 이전 서비스 재생 중단 → (b) 세션의 활성 서비스 플래그 전환 → (c) 새 서비스 플레이리스트 로드 → (d) late join과 동일한 로직으로 재생 위치 동기화, 순서로 진행되는 것을 개념 수준으로 전제한다(상세 프로토콜은 구현 단계 몫, `06-mvp-scope-and-tech-stack.md` "갱신된 MVP 범위 결정" 절 참고).
- 오버레이가 끝나면 세션 메인 화면(전환된 서비스 기준의 2.10a 또는 2.10c)으로 자동 복귀하며, 짧은 토스트를 함께 띄운다: "YouTube 플레이리스트로 전환됐어요. Spotify 플레이리스트는 그대로 저장돼 있어요." — 다이얼로그(2.13a)에서 예고한 내용을 전환 완료 시점에 한 번 더 확인시켜, 사용자가 전환 직후 "설마 지워진 건 아니겠지" 하고 불안해하지 않도록 한다.

### 2.14 예외/엣지 상태 화면 (오버레이 형태, 전체 화면 전환 아님)

- **재접속 중 오버레이(US-206)**: 반투명 오버레이 + "연결이 불안정해요, 다시 연결하는 중..." + 스피너. 일정 시간 초과 시 "세션에서 나가기" 옵션 노출.
- **호스트 마이그레이션 토스트(US-204)**: "호스트가 자리를 비웠어요. 지은님이 새 호스트가 되었어요." 짧은 토스트로만 처리, 별도 화면 전환 없음(세션 지속성을 사용자가 체감하게 하는 것이 목적).
- **드리프트 보정 표시(US-403)**: Now Playing 탭 하단 상태 배지가 "동기화됨" → "맞추는 중..."으로 짧게 전환 후 자동 복귀. 상세는 `02-key-ui-patterns.md`.

## 3. 내비게이션 구조 요약

```
스택 루트: 스플래시 → (온보딩) → (Spotify 로그인) → 홈
홈
 ├─ 세션 생성 → 앱설치유도(조건부) → 초대공유 → 세션메인
 ├─ 세션 참여 → 세션메인
 └─ 딥링크 진입 → (대기실) → 세션메인

세션메인 (스와이프 탭 2개, (2026-07-23 갱신) 활성 서비스에 따라 Now Playing 구성이 2.10a(Spotify)/2.10c(YouTube)로 갈림)
 ├─ Now Playing
 └─ 플레이리스트 (상단에 활성 서비스 칩 상시 노출 — 2.10b 갱신)
     ├─ (바텀시트) 곡 검색/추가
     ├─ (바텀시트) 참여자 목록
     └─ (스택) 세션 설정
         └─ (2026-07-23 신규) 서비스 전환 확인 다이얼로그(2.13a) → 전환 중 오버레이(2.13b) → 세션메인으로 복귀
```

- 하단 탭바(bottom tab bar)는 MVP 범위에서 불필요하다고 판단(세션 밖에서 상시 노출할 정보가 "홈" 하나뿐). 세션 내부만 2탭으로 가볍게 유지.
- 세션 밖(홈)과 세션 안(Now Playing/플레이리스트)의 시각적 구분을 명확히 해서, "지금 내가 누군가와 연결된 세션 안에 있는지"를 항상 인지할 수 있게 한다(예: 세션 안에서는 헤더에 상시 동기화 상태 배지 노출).
- **(2026-07-23 신규)** 서비스 전환 진입점은 두 곳이다: (1) 세션 설정(2.13, 정식 경로), (2) 플레이리스트 탭 상단 서비스 칩(2.10b, 단축 경로) — 둘 다 최종적으로 2.13a(확인 다이얼로그)로 모인다. **혼합 세션에는 이 진입점 자체가 없다.**
- **(2026-07-23 신규)** 혼합 세션 참여 플로우: 세션 생성/참여 시 "참여 플랫폼 선택(2.6c)"이 한 단계 추가되며, 세션메인 진입 후에는 "곡 검색/추가" 바텀시트 뒤에 매칭 확인 체인이 이어진다 — (바텀시트) 곡 검색/추가 → (혼합 세션인 경우) 매칭 진행 중(2.11a) → 매칭 확인 카드(2.11b) → [대체 후보(2.11c) | 매칭 실패(2.11d)] → 세션메인 복귀. 이 체인은 참여자 각자의 기기에서 서로 독립적으로 발생한다(한 사람의 확인이 다른 사람에게 영향을 주지 않음).

## 4. 후속 논의가 필요한 사항 (리더 보고용)

1. Free 계정 사용자를 완전히 차단할지, "듣기 전용"으로 강등할지 — `02-spotify-integration.md` 제약 2에서 미확정. 이 문서는 두 정책 모두 수용 가능한 화면 구조(2.4)로 설계했으나, 최종 정책 확정 시 카피/버튼만 조정하면 된다.
2. 초대 코드 자릿수/유효기간, 최대 참여 인원(US-205, P2) 등은 기획에서 확정되지 않은 값 — 디자인은 가변 길이를 수용하는 구조로만 잡아둠.
3. "재생 완료 곡은 순서 변경 불가"는 이 문서에서 새로 내린 UX 결정이다(04번 문서가 디자인 단계 위임). 구현/검증 단계에서 이견 있으면 조정 가능.
4. **(2026-07-23 신규)** 최초 온보딩에서 YouTube 계정을 함께 연동시킬지, 아니면 이 문서가 채택한 "지연 연동(lazy connect, 세션 생성/전환 시점에만 요구)" 방식을 유지할지 — 리더/기획 재확인이 필요하면 후속 논의 대상.
5. **(2026-07-23 신규)** 세션 도중 서비스 전환(2.13a)을 "전원 허용"할지 "방장만 허용"할지는 이 문서가 US-405와 같은 기조로 "전원 허용"을 기본값 제안했을 뿐 확정 정책이 아니다 — 전환은 재생 중단을 유발하는 파급력 있는 동작이라 권한을 좁히는 안이 먼저 논의될 여지가 있다.
6. **(2026-07-23 신규)** YouTube 광고 재생 중 상태를 기존 "맞추는 중" 배지에 보조 텍스트로 얹는 방식(`02-key-ui-patterns.md` 2.2절 갱신 참고)은 광고 상태를 신뢰성 있게 감지할 수 있다는 전제 위에 있다 — 실제 감지 신뢰도는 `03-youtube-integration.md` 8-3절이 명시한 대로 실기기 검증이 필요하며, 결과에 따라 이 디자인 판단이 조정될 수 있다.
7. **(2026-07-23 신규)** 혼합 세션에서 참여자가 자신의 개인 참여 플랫폼(2.6c에서 최초 선택한 값)을 세션 도중 바꿀 수 있게 할지는 이번 설계에서 다루지 않았다 — 필요하면 후속 논의 대상.
8. **(2026-07-23 신규)** 매칭 확인 알림을 "즉시 모달로 가로막기"가 아니라 "배지+큐 방식"(2.11a)으로 설계한 것은 디자인 단계의 절충 제안이다 — 특히 "지금 재생 중인 곡"의 매칭이 아직 미확인 상태로 남아 그 참여자만 재생이 안 되는 상황(2.10d)이 실제로 얼마나 자주/불편하게 발생할지는 실사용 검증이 필요하며, 결과에 따라 "재생 중인 곡만은 즉시 모달로 강제 확인시킨다"는 예외 규칙을 추가하는 안을 재검토할 수 있다.
9. **(2026-07-23 신규)** 매칭 신뢰도 등급(높음/중간/낮음)의 정확한 임계값·%, 그리고 낮음 등급일 때 "확정하기" 버튼을 완전히 막을지(현재 제안은 톤만 낮추고 막지는 않음, `02-key-ui-patterns.md` 5절) 여부는 실측 스파이크(`09-cross-platform-mixed-mode.md` "결정 4") 결과를 보고 재확인이 필요하다.
10. **(2026-07-23 신규)** "혼합 여부는 세션 생성 후 다른 유형으로 바꿀 수 없다"는 문구를 2.6에 노출할지 여부는 기획 단계에서 확정된 바 없어 이 문서는 잠정 보류했다 — 실제 정책(변경 가능 여부)이 확정되면 배너 문구만 조정하면 된다.
11. **(2026-07-24 신규)** 관리자 임명(2.12, `02-key-ui-patterns.md` 6.4절)의 정확한 흐름(즉시 반영 vs 확인 다이얼로그, 취소/해제 가능 여부, 관리자 스스로 사임 가능 여부, 관리자 인원 상한)은 `04-playlist.md` "권한 체계" 절 확인 필요 1·2번이 미확정이라 이 문서는 진입점(메뉴 자리)만 잡아뒀다 — 정책이 확정되면 후속 화면(임명 확인 다이얼로그 등)을 별도로 설계해야 한다.
12. **(2026-07-24 신규)** 세션 정원(2.6)의 기본값, 세션 생성 후 정원 변경 가능 여부, "정원"이 참여 인원과 재생 인원 중 무엇을 기준으로 하는지는 모두 `04-playlist.md` "세션 정원"/"Free 계정 처리" 절 확인 필요 항목이다 — 확정되면 2.6의 초기 노출 값과 라벨, 그리고 2.13(세션 설정)에 정원 변경 UI를 추가할지 여부를 재검토해야 한다.
13. **(2026-07-24 신규)** Free 계정 사용자의 세션 참여 자체 허용 여부(해석 A/B, `04-playlist.md` "Free 계정 처리" 절)가 확정되지 않아 2.4b는 두 형태(배너/배지 vs 모달)를 모두 설계해뒀다 — 정책이 확정되면 하나만 남기고 나머지는 제거하는 정리 작업이 필요하다.
14. **(2026-07-24 신규)** 호스트 마이그레이션(US-204) 발생 시 기존 관리자 목록이 그대로 유지되는지, 새 방장이 재구성할 수 있는지(`04-playlist.md` "권한 체계" 절 확인 필요 3번)가 미확정이라, 2.12의 역할 배지·관리자 메뉴는 "역할이 바뀌면 배지가 바뀐다"는 일반 원칙만 반영했고 마이그레이션 시점의 구체적 전환 애니메이션/안내 문구는 설계하지 않았다.
