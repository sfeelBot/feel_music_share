## 배경

방(세션)의 핵심 콘텐츠는 "함께 만들어가는 플레이리스트"다. CLAUDE.md 요구사항: 참여자 모두가 곡 추가/삭제/순서변경 가능, 각 곡을 누가 선곡했는지 표시. 이 문서는 이를 실제 기능 단위로 구체화한다. (데이터베이스 스키마·API 설계 등 구현 상세는 구현 에이전트 몫이며, 여기서는 기능 요구사항 수준까지만 다룬다.)

## 요구사항

### 플레이리스트 구조

- (2026-07-23 갱신) 플레이리스트는 **방(세션) + 서비스 타입의 조합에 종속**된다 — 방이 유지되는 동안 "Spotify 플레이리스트"와 "YouTube 플레이리스트"를 각각 독립적으로 갖는다(개념적으로 세션 1 : 서비스별 플레이리스트 N, 현재 N=2). 세션은 한 번에 하나의 서비스만 활성화되어 재생하지만(`01-user-stories.md` US-105), 사용자는 세션 도중 활성 서비스를 전환할 수 있고(US-105b) 이때 비활성화되는 쪽 플레이리스트는 삭제되지 않고 그대로 보존되어 나중에 다시 그 서비스로 돌아오면 이어서 쓸 수 있다(US-105c/US-308). 상세 데이터 모델(스키마)은 구현 단계 몫이나, 개념적으로는 "플레이리스트 엔터티가 세션 ID뿐 아니라 서비스 타입도 키로 갖는다" 정도로 이해하면 된다.
- 옛 서술(대체됨, 이력 보존): ~~플레이리스트는 방(세션)에 1:1로 종속되어 방이 유지되는 동안 하나의 플레이리스트만 공유한다.~~ 이 서술은 "세션 도중 서비스 전환 불가"를 전제로 했던 것이라 위 갱신 내용으로 대체한다.
- 곡 항목(entry)은 다음 정보를 포함한다 (Spotify 전용/YouTube 전용 세션 기준 — 혼합 세션의 곡 항목 구조는 아래 "혼합 모드 플레이리스트 구조" 절에서 별도로 다룬다):
  - 곡 메타데이터 (제목, 아티스트/채널, 썸네일, 길이, 서비스별 고유 ID — Spotify track URI 또는 YouTube videoId)
  - 추가한 사람(닉네임, 프로필 이미지)
  - 추가된 시각
  - 재생 여부(이미 재생됨/대기 중/현재 재생 중)

### 혼합 모드 플레이리스트 구조 (2026-07-23 추가 — 크로스플랫폼 혼합 모드 MVP 포함 결정 반영)

> 근거/결정 배경: `09-cross-platform-mixed-mode.md` "결정 갱신 (2026-07-23)" 절, `01-user-stories.md` US-105d/US-309/US-310.

혼합(Mixed) 세션은 위에서 서술한 "세션 + 서비스 타입 조합에 종속되는 플레이리스트"(세션 1 : 서비스별 플레이리스트 N) 구조와 **근본적으로 다른 구조**를 쓴다. 이유는 혼합 세션에는 애초에 "활성화된 서비스 하나"라는 개념이 없고, 참여자마다 서로 다른 서비스가 **동시에** 활성 상태이기 때문이다(구조적 차이의 상세 비교는 `09-cross-platform-mixed-mode.md` "결정 3" 절 참고).

- **플레이리스트는 세션당 하나뿐이다(세션 1 : 플레이리스트 1, 플랫폼 중립)** — Spotify용/YouTube용으로 나뉘지 않는다.
- **곡 항목(entry)의 구조**: 하나의 곡 항목은 두 계층으로 구성된다(개념 수준, 상세 스키마는 구현 단계 몫).
  1. **공통 식별자 계층** — 모든 참여자가 공유하는 플랫폼 중립 메타데이터: 제목, 아티스트, (참고용) 대표 썸네일, 대표 재생 길이, 추가한 사람, 추가된 시각. 이 계층은 특정 플랫폼의 트랙 ID를 갖지 않는다 — "무슨 곡인지"만 나타낸다.
  2. **참여자별 매칭 트랙 계층** — 같은 곡 항목 아래, 참여자 각자가 자신의 플랫폼에서 실제로 매칭된 트랙 정보를 별도로 갖는다: 매칭된 서비스(Spotify/YouTube), 서비스별 고유 ID(track URI 또는 videoId), 실제 제목/아티스트/썸네일/길이(공통 식별자와 다를 수 있음 — 매칭이 다른 에디션을 가리킬 가능성이 있기 때문, `09-cross-platform-mixed-mode.md` 2절), **일치율/신뢰도 값**, 참여자의 확인 상태(자동 매칭 대기/확정됨/수동 교체됨).
- **매칭 확인 UI 요구사항(필수, US-309/US-310)**: 곡이 플레이리스트에 추가되면 각 참여자의 클라이언트가 자신의 플랫폼에서 검색을 수행해 후보를 매칭하고, 그 결과(제목/아티스트/썸네일/길이 + 일치율/신뢰도)를 참여자에게 표시한다. 참여자는 이를 "확정" 또는 "직접 재검색해 수동 교체" 중 하나로 처리해야 하며, 이 확인 없이 자동 매칭 결과만으로 조용히 재생에 들어가는 흐름은 채택하지 않는다. 이 확인은 참여자별로 독립적으로 이뤄진다(한 참여자의 확인이 다른 참여자의 매칭에 영향을 주지 않음).
- **선곡자 표시와의 관계**: 공통 식별자 계층의 "추가한 사람"이 기존 "선곡자 표시" 정책(아래 "기능 목록" 4번)이 가리키는 대상과 동일하다 — 혼합 모드에서도 "누가 이 곡을 골랐는지"는 플랫폼과 무관하게 한 사람으로 표시된다. 참여자별 매칭/확인 상태는 별도의 UI 요소(예: "OO님이 확인함" 배지 등, 디자인 단계에서 다룰 것을 제안)로 구분해 표시하는 것을 제안한다.
- **재생 동기화와의 관계**: 서버는 여전히 공통 식별자 계층의 곡 항목과 "플랫폼 중립 기준 위치(경과 시간)"만을 단일 진실로 브로드캐스트한다(`05-sync-architecture.md` 모델 그대로 재사용). 각 참여자 클라이언트는 자신의 참여자별 매칭 트랙 계층에 있는 길이 정보를 기준으로 이 위치를 자신의 트랙 좌표로 환산해 seek한다.
- **혼합 모드에는 "서비스 전환"이 없다**: 기존 US-105b(세션 도중 Spotify↔YouTube 전환)는 혼합 세션에는 적용되지 않는다 — 혼합 세션은 세션 생성 시점부터 여러 서비스가 동시에 활성 상태이므로, "전환"이라는 개념 자체가 성립하지 않는다.

### 세션 정원 (2026-07-24 신규)

> 근거: 리더 전달 사용자 결정(2026-07-24). 기존 `01-user-stories.md` US-205(`[P2]` "최대 인원 제한/공개-비공개 설정")를 이 정책으로 구체화하고 MVP로 승격한다(상세는 `01-user-stories.md` US-207 참고).

- 세션(방)의 **최대 인원은 12명**이다.
- **방장이 세션 생성 시점에 정원을 12명 이하 범위에서 직접 설정**할 수 있다(예: 2~12명 사이 임의 값).
- **(2026-07-24 확정) 정원 기본값은 2명이다** — 방장이 별도로 값을 지정하지 않으면 세션은 2명 정원으로 생성된다. 방장은 여전히 2~12명 범위에서 원하는 값으로 직접 조정할 수 있으며, 최대 상한 12명은 기존과 동일하게 유지된다. (리더 전달 사용자 결정, 2026-07-24.) 이로써 아래 "확인 필요" 2번 항목은 해소되었다.
- **(2026-07-25 확정) 정원은 세션 생성 시점에만 설정 가능하며, 생성 이후에는 변경할 수 없다** — 방장이 세션 생성 화면에서 2~12명 범위의 값을 정하고 나면, 그 값은 세션이 유지되는 동안 고정된다. 늘리기/줄이기 모두 불가하다(리더 전달 사용자 결정, 2026-07-25). 이로써 아래 옛 "확인 필요" 1번 항목("생성 후 정원 변경 가능 여부 및 축소 시 처리")은 **질문 자체가 성립하지 않게 되어 해소**되었다 — 정원이 애초에 바뀌지 않으므로 "축소된 정원을 이미 참여 중인 인원이 초과할 때 어떻게 처리할지"라는 하위 질문도 함께 소멸한다.
- **(2026-07-25 검토) 이 결정이 아래 3번 항목("참여 인원 vs 재생 인원 기준")에 영향을 주는지**: 영향 없음으로 판단해 그대로 미결로 남긴다. "정원이 언제 고정되는가"(생성 시점)와 "정원이라는 숫자가 무엇을 세는 기준인가"(참여 인원 전체냐, Free 계정을 제외한 재생 가능 인원이냐)는 서로 독립적인 축이다 — 정원 값이 고정되더라도 그 값이 참여 인원을 세는지 재생 인원을 세는지는 별개로 결정돼야 하므로, 이번 결정으로 3번 항목의 답이 저절로 정해지지는 않는다.
- **확인 필요** (기획 단계에서 임의로 확정하지 않음):
  1. ~~세션 생성 후에도 정원을 변경(늘리기/줄이기)할 수 있는지, 가능하다면 이미 참여 중인 인원이 축소된 새 정원을 초과할 때 어떻게 처리할지.~~ (2026-07-25 확정 — 생성 후 변경 불가로 확정되어 질문 자체가 소멸, 위 항목 참고)

  3. "정원 12명"이 세션 참여 인원 전체를 가리키는지, 아니면 아래 "Free 계정 처리" 절의 "재생 인원"만 가리키는지 — Free 계정 참여자가 정원 카운트에 포함되는지 여부. (2026-07-25 검토 결과: 위 정원 고정 결정과는 무관한 별개 사안이므로 여전히 확인 필요 상태로 남는다.)

### 권한 체계 — 방장/관리자/일반사용자 3단계 (2026-07-24 신규)

> 근거: 리더 전달 사용자 결정(2026-07-24). 상세 사용자 스토리는 `01-user-stories.md` US-208~US-210 참고.

세션 참여자는 세 등급의 권한을 갖는다.

| 역할 | 인원 | 서비스 전환(Spotify↔YouTube) | 곡 추가/삭제/순서변경 |
|---|---|---|---|
| 방장 (host) | 세션당 1명 | 가능 | 가능 |
| 관리자 (admin) | N명(무제한, 2026-07-25 확정 — 아래 참고) | 가능 | 가능 |
| 일반사용자 (regular) | 나머지 전원 | **불가** | 가능 |

**기존 정책과의 정합성 (중요)**: 이번 3단계 권한 체계는 **오직 "서비스 전환" 기능에만 적용되는 신규 게이트**다. CLAUDE.md 및 위 "기능 목록"이 서술하는 "참여자 모두가 곡 추가/삭제/순서변경 가능"이라는 핵심 요구사항은 그대로 유지되며, **일반사용자도 방장·관리자와 동일하게 플레이리스트를 자유롭게 편집할 수 있다.** 즉 권한 체계 도입이 기존 협업 플레이리스트 정책을 축소하는 것이 아니라, "서비스 전환"이라는 새 축 하나에만 제한을 추가하는 것으로 이해해야 한다.

**서비스 전환 정책 갱신**: `06-mvp-scope-and-tech-stack.md` "세션-서비스 관계" 절과 `01-user-stories.md` US-105b(세션 도중 서비스 전환)는 애초에 권한 주체를 명시하지 않았으나, 이번 결정으로 **방장·관리자만 서비스 전환을 실행할 수 있는 것으로 구체화**된다(US-105b는 US-208로 보강). 일반사용자에게는 전환 UI를 숨기거나 비활성화하는 것을 제안하며, 세부 UX는 디자인 단계에서 다룬다(아래 "디자인 에이전트 전달 사항" 참고).

**(2026-07-24 확정) 관리자 임명 방식 — 임명권 주체**: **방장이 관리자 임명·해제 권한을 갖는다** — 방장이 참여자 목록에서 특정 참여자를 관리자로 임명하거나, 임명된 관리자를 해제할 수 있는 유일한 주체다(리더 전달 사용자 결정, 2026-07-24). 단, "누가 임명권을 갖는가"만 확정된 것이며, 임명 취소의 구체적 흐름(예: 즉시 해제 vs 확인 절차)이나 관리자 스스로 사임 가능 여부 등 더 세부적인 사항은 아래 "확인 필요" 1번으로 남아 있다.

**(2026-07-25 확정) 관리자 임명 취소·사임**: 방장은 자신이 임명한 관리자를 다시 해제(임명 취소)할 수 있다. 또한 **관리자 스스로도 사임(관리자 권한 반납)할 수 있다** — 방장의 조치 없이도 본인 의사로 일반사용자로 돌아갈 수 있다(리더 전달 사용자 결정, 2026-07-25). 다만 해제/사임 시 확인 다이얼로그 등 구체적 UX 절차는 이번 결정 범위 밖이며 디자인 단계에서 다룬다.

**(2026-07-25 확정) 관리자 인원 상한**: **무제한이다** — 세션당 관리자 수를 별도로 제한하지 않는다. 정원(최대 12명) 대비 비율이나 절대 인원 상한을 두지 않기로 확정됐다(리더 전달 사용자 결정, 2026-07-25).

**(2026-07-25 확정) 호스트 마이그레이션 시 권한 승계**: 방장이 세션을 나가 다른 참여자가 새 방장이 될 때, **기존 관리자 목록은 그대로 유지되는 것이 기본이다** — 마이그레이션 시점에 관리자 목록이 자동으로 초기화되지 않는다. 다만 새 방장은 이후 통상적인 임명권(위 "관리자 임명 방식" 참고)으로 이 목록을 얼마든지 변경(추가 임명/기존 관리자 해제)할 수 있다(리더 전달 사용자 결정, 2026-07-25).

**(2026-07-27 확정) 호스트 마이그레이션 시 새 방장 선출 규칙**: **기존 관리자 우선 승계** — 방장이 이탈하면 관리자 중 한 명이 새 방장이 된다(리더 전달 사용자 결정, 2026-07-27, 회의록: `docs/decision-log.md`). 세부 타이브레이크 규칙(관리자가 여러 명일 때 누가 승계되는지, 관리자가 아무도 없을 때 대체 규칙)은 사용자 결정에 포함되지 않아 리더가 합리적 기본값으로 제안한다 — **관리자가 여러 명이면 가장 먼저 임명된 관리자**, **관리자가 한 명도 없으면 세션 참여 순서 기준 최고참(가장 먼저 참여한 일반 참여자)**이 승계. 이 기본값 자체가 이상하다고 판단되면 언제든 재조정 가능(구현 착수 전 확정 필요 항목은 아니고, 구현 단계에서 그대로 반영해도 되는 세부 규칙 수준).

### 기능 목록

1. **곡 검색 및 추가**
   - 방에서 사용 중인 서비스(Spotify 또는 YouTube)의 검색 API로 곡을 검색한다.
   - 검색 결과에서 선택 시 플레이리스트 맨 뒤(또는 "다음 곡"으로 우선 추가하는 옵션)에 추가된다.
   - 중복 곡 추가 시 경고 또는 허용 여부는 방 설정으로 둔다(기본: 허용, 단 UI에서 "이미 있음" 표시).

2. **곡 삭제**
   - 참여자 누구나 삭제 가능(기본 정책). 현재 재생 중인 곡 삭제 시 다음 곡으로 자동 전환.
   - (2026-07-24 참고) 3단계 권한 체계(방장/관리자/일반사용자, 아래 "권한 체계" 절) 도입 이후에도 이 정책은 변경 없이 유지된다 — 권한 체계는 "서비스 전환" 기능에만 적용되고, 곡 삭제를 포함한 플레이리스트 편집 권한에는 영향을 주지 않는다.
   - 삭제 시 "누가 삭제했는지"는 굳이 노출하지 않아도 되나, 추후 신뢰 이슈 발생 시를 대비해 서버 로그에는 남긴다(제안, 확정 아님).

3. **순서 변경**
   - 드래그 앤 드롭 등으로 순서 변경. 변경 사항은 실시간으로 모든 참여자 화면에 반영.
   - 이미 재생 완료된 곡과 대기 중인 곡의 순서 변경 범위를 구분할지는 UX 결정 사항 (디자인 단계에서 다룰 것을 제안).

4. **선곡자 표시**
   - 각 곡 항목에 추가한 사람의 아바타/닉네임을 배지 형태로 표시.

5. **자동 다음 곡 재생**
   - 현재 곡이 끝나면 플레이리스트의 다음 곡으로 자동 전환하고, 이 전환도 동기화 대상이다(전원이 같은 순간에 다음 곡으로 넘어가야 함).

6. **플레이리스트 저장/재사용** `[P2]`
   - 방이 종료된 뒤에도 플레이리스트를 계정에 저장해 나중에 다시 불러오거나, Spotify/YouTube의 정식 플레이리스트로 내보내기(export)하는 기능.

7. **개인 플레이리스트 가져오기(Import)** `[P2]` (2026-07-23 조사 추가 — 우선순위는 제안일 뿐, 최종 확정은 사용자/리더 몫)
   - 참여자가 각 서비스에 이미 갖고 있는 자신의 개인 플레이리스트를 통째로 세션 플레이리스트에 가져오는 기능. 서비스별 가능 여부는 아래 "개인 플레이리스트 Import 가능 여부 조사" 절 참고.

### 동시 편집 처리

- 여러 사람이 동시에 곡을 추가/삭제/순서 변경할 수 있으므로, 서버가 **단일 진실 공급원(source of truth)** 역할을 하고 클라이언트는 실시간 채널(웹소켓 등)을 통해 변경 이벤트를 받아 반영하는 구조를 제안한다.
- 순서 변경 시 동시 충돌(예: 두 사람이 동시에 서로 다른 곡을 맨 위로 옮김) 처리 전략은 구현 단계에서 결정하되, 기획 단계에서는 최소 요구사항으로 "마지막 조작이 우선 적용되고, 다른 참여자 화면은 즉시 갱신되어 눈에 보이는 불일치가 없어야 한다"를 명시한다.

### 개인 플레이리스트 Import 가능 여부 조사 (2026-07-23 추가)

> 리서치 근거: Spotify Web API 공식 문서, YouTube Data API v3 공식 문서, `08-korean-services-melon-genie.md`(멜론/지니뮤직 조사 결과 재인용). (2026-07-23 기준 WebFetch로 확인)

각 참여자가 이미 갖고 있는 서비스별 개인 플레이리스트를 세션에 그대로 가져올 수 있는지 서비스별로 조사했다.

**Spotify — 가능 (확실성 높음, 공식 문서 확인)**

- `GET /v1/me/playlists` ("Get Current User's Playlists"): 로그인한 사용자가 소유하거나 팔로우하는 플레이리스트 목록을 페이지네이션으로 조회한다. 필요 스코프: `playlist-read-private`. 응답에는 각 플레이리스트의 ID/이름/설명/트랙 개수/공개 여부 등이 포함된다.
- `GET /v1/playlists/{playlist_id}/tracks` ("Get Playlist Items"): 특정 플레이리스트에 포함된 트랙 목록을 조회한다. 필요 스코프는 동일하게 `playlist-read-private`(비공개 플레이리스트 접근 시).
- 각 트랙 항목에는 이미 `external_ids.isrc`, 제목, 아티스트, 앨범, `duration_ms`, URI 등이 포함되어 있어(`02-spotify-integration.md`, `09-cross-platform-mixed-mode.md` 참고) 세션 플레이리스트 항목 스키마로 변환하는 데 추가 조회가 거의 필요 없다.

**YouTube — 가능하나 일부 시스템 재생목록은 제외됨 (확실성 높음, 공식 문서 확인)**

- `playlists.list`에 `mine=true` 파라미터를 지정하면(적절히 인증된 요청 필요) 로그인한 사용자 본인 소유의 재생목록만 반환한다. 이후 각 재생목록 ID로 `playlistItems.list`를 호출해 포함된 동영상 항목을 가져온다. 최소 필요 스코프는 읽기 전용 `https://www.googleapis.com/auth/youtube.readonly`로 충분하다.
- **주의**: "시청 기록(Watch History)"과 "나중에 볼 동영상(Watch Later)"은 YouTube가 시스템 관리 재생목록으로 취급해 API로 접근이 차단되어 있다(빈 목록 반환) — 이 두 재생목록은 Import 대상에서 원천적으로 제외된다. 반면 **"좋아요 표시한 동영상(Liked Videos)"은 예외적으로 접근 가능**하다 — `channels.list`로 얻는 `contentDetails.relatedPlaylists.likes` 재생목록 ID를 `playlistItems.list`에 넘기면 좋아요 목록을 가져올 수 있다.
- YouTube Data API의 일일 쿼터 제약(04 문서 기존 "제약/리스크" 절 참고)은 Import 시에도 그대로 적용된다. 큰 재생목록(수백 곡)을 여러 참여자가 동시에 Import하면 쿼터 소진 속도가 빨라질 수 있어, Import 1회당 가져올 수 있는 곡 수 상한을 두는 것을 제안한다(구체적 상한값은 쿼터 실측 후 결정).

**멜론/지니뮤직 — 불가능**

- `08-korean-services-melon-genie.md`에서 확인했듯 두 서비스 모두 서드파티용 공식 API 자체가 없으므로, 개인 플레이리스트 조회 기능도 당연히 제공되지 않는다. 별도 조사 없이 "불가능"으로 결론 내리는 것으로 충분하다.

**선곡자 표시 정책과의 관계**

- 기존 "선곡자 표시"(각 곡 항목에 추가한 사람의 아바타/닉네임 배지) 정책과 자연스럽게 어우러진다 — **Import로 가져온 곡들의 선곡자는 "Import를 실행한 참여자 본인"으로 표시하면 된다.** 이는 "누가 이 곡을 추가했는지"라는 기존 정책의 의미를 그대로 확장한 것뿐이라 별도의 새로운 규칙이 필요하지 않다. 다만 "곡 100개를 한 번에 Import"한 경우 배지가 화면을 도배하는 UX 문제는 있을 수 있어(예: "OO님이 플레이리스트를 가져왔습니다"라는 묶음 표시 등), 이는 디자인 단계에서 다룰 것을 제안한다.
- Import 시 중복 곡 처리(이미 세션 플레이리스트에 있는 곡을 다시 Import하는 경우)는 기존 "곡 검색 및 추가"의 중복 처리 정책(기본 허용 + "이미 있음" 표시)을 그대로 적용하는 것을 제안한다.

## 제약/리스크

- **서비스별 검색 API 제약**: Spotify Web API 검색(`/v1/search`)은 자유롭게 사용 가능하나, YouTube Data API 검색(`search.list`)은 **일일 쿼터(quota) 제한**이 있다(기본 할당량은 낮은 편으로 알려져 있으며, 검색 1회 호출이 다른 엔드포인트보다 쿼터를 많이 소모함 — 정확한 수치는 Google Cloud Console 등록 시점에 재확인 필요, **확인 필요**). 다인원이 동시에 검색을 남발하면 쿼터가 빠르게 소진될 수 있어 캐싱/디바운스 전략이 필요하다.
- **플레이리스트 곡 정보의 서비스 종속성**: Spotify 트랙과 YouTube 동영상은 같은 곡이어도 서로 다른 ID 체계를 쓰므로, 서비스 타입에 따라 플레이리스트 항목의 스키마가 갈린다. (2026-07-23 갱신) 옛 제안("MVP는 방-서비스 1:1 고정 전제로 단순화, 서비스 전환은 향후 검토 대상")은 사용자의 결정 변경으로 대체됨 — 이제 "같은 세션에서 서비스 전환"이 MVP 요구사항이 되었다(`01-user-stories.md` US-105b/US-105c/US-308). 따라서 곡 식별자/플레이리스트 항목 스키마는 처음부터 **서비스 타입별로 분리된 구조**(예: 세션당 서비스별 플레이리스트를 별도 레코드/컬렉션으로 관리하고, 두 서비스 간 곡 식별자를 억지로 통합·추상화하려 하지 않는 것)로 설계하는 편이 오히려 단순하다 — 애초에 곡 식별자 통합이 필요 없는 구조이기 때문이다. 상세 스키마 설계는 구현 단계 몫이다.
- **삭제 권한 남용**: 전원 삭제 허용 정책은 편리하지만 악의적 사용자가 플레이리스트를 비우는 상황이 가능하다. MVP에서는 소규모 지인 간 사용을 전제로 리스크를 감수하고, 추후 권한 세분화(`[P2]`)를 검토한다. (2026-07-24 참고) 이번에 도입된 3단계 권한 체계(방장/관리자/일반사용자)는 "서비스 전환" 기능만을 게이트하며 곡 삭제 권한 자체는 세분화하지 않으므로, 이 리스크는 여전히 해소되지 않은 채 남아 있다 — 곡 삭제 권한 세분화가 필요하다고 판단되면 별도로 재검토해야 한다.
- **(2026-07-24 신규) 권한 체계·세션 정원·Free 계정 정책의 미확정 세부사항**: 위 "권한 체계", "Free 계정 처리" 절에서 "확인 필요"로 남긴 항목들(관리자 임명 방식·인원 상한, 호스트 마이그레이션 시 권한 승계 규칙, Free 계정 사용자의 세션 참여 가능 여부 등)은 구현 착수 전 반드시 리더/사용자와 재확인해야 한다 — 특히 "Free 계정 사용자가 세션에 참여 자체를 못 하는지"는 데이터 모델(예: 세션 참여자 레코드에 재생 가능 여부 플래그를 둘지, 아예 별도 역할로 분리할지)에 영향을 주므로 구현 착수 전 확정이 필요하다. (2026-07-24 갱신) 이 중 관리자 임명권 주체(방장 보유), 세션 정원 기본값(2명), Free 계정 세션 참여 허용 여부(해석 A 확정) 3건은 리더 전달 사용자 결정으로 확정되어 이 리스크에서 해소되었다 — 남은 미확정 항목은 관리자 임명 세부 흐름·인원 상한, 호스트 마이그레이션 권한 승계 규칙뿐이다. (2026-07-25 갱신) 이후 관리자 임명 취소·사임 가능 여부, 관리자 인원 상한(무제한), 호스트 마이그레이션 시 기존 관리자 목록 유지, 세션 정원의 생성 후 변경 불가 4건이 추가로 확정되어 이 리스크에서 더 해소되었다 — 남은 미확정 항목은 ① 관리자 임명/해제 시 구체적 확인 절차(UX 세부), ② 호스트 마이그레이션 시 새 방장 선출 알고리즘, ③ 정원이 참여 인원/재생 인원 중 무엇을 기준으로 하는지, ④ 서비스 전환 외 다른 관리 기능에 3단계 체계를 적용할지 뿐이다.
- **(2026-07-23 추가) 혼합 모드 매칭 신뢰도 한계**: 혼합 세션의 참여자별 매칭 트랙은 YouTube가 ISRC 등 표준 식별자를 노출하지 않아 근본적으로 휴리스틱(제목 유사도+아티스트 일치+길이 오차) 매칭에 의존한다(`09-cross-platform-mixed-mode.md` 1·2절). "매칭 결과 고지 + 사용자 확인/수정 UI"(위 "혼합 모드 플레이리스트 구조" 절)로 리스크를 완화하지만 완전히 제거하지는 못한다 — 특히 "길이는 같으나 구조가 다른 편집판"은 UI 확인 단계에서도 참여자가 육안/청감으로 알아채지 못하면 걸러지지 않을 수 있다는 한계를 구현/검증 단계가 인지해야 한다.

## 제안

- MVP 기능 범위: 검색·추가·삭제·순서변경·선곡자 표시·자동 다음 곡 재생까지 포함. 저장/재사용, export, 좋아요/투표 기능은 P2로 미룬다.
- (2026-07-23 추가) MVP 범위가 Spotify+YouTube 동시 지원으로 갱신됨에 따라, 위 기능 범위는 **서비스별로 각각(플레이리스트가 두 벌 존재)** 구현되어야 하며, 세션 설정에서의 서비스 전환(US-105b) 시 활성 플레이리스트만 바뀌고 비활성 쪽 데이터는 보존되어야 한다(US-105c/US-308). 이 부분은 위 "플레이리스트 구조"/"제약·리스크" 절 갱신 내용과 함께 구현 착수 전 반드시 반영해야 하는 요구사항이다.
- 실시간 동기화 채널은 재생 상태 동기화(`05-sync-architecture.md`)와 동일한 실시간 인프라(예: WebSocket)를 공유하는 것을 제안한다 — 별도 폴링 API를 또 만들 필요 없이 "방 이벤트 스트림"에 플레이리스트 변경 이벤트도 함께 흘려보내는 설계. 서비스 전환 이벤트도 같은 스트림에서 "활성 서비스 변경" 이벤트로 흘려보내는 것을 제안한다.
- (2026-07-23 추가) 혼합 모드가 MVP로 포함됨에 따라, 위 기능 범위(검색·추가·삭제·순서변경·자동 다음 곡)는 혼합 세션에서도 동일하게 제공하되, "혼합 모드 플레이리스트 구조" 절의 이중 계층(공통 식별자 + 참여자별 매칭 트랙)과 매칭 확인 UI(US-309/US-310)를 함께 구현해야 한다. 혼합 세션의 플레이리스트 변경 이벤트(곡 추가/삭제/순서변경)와 "참여자별 매칭 확정/수동 교체" 이벤트는 서로 다른 종류의 이벤트로 구분해 같은 실시간 스트림에 흘려보내는 것을 제안한다(전자는 전원에게 영향, 후자는 해당 참여자 개인의 로컬 상태 변경).
- (2026-07-24 추가) 세션 정원(12명)·3단계 권한 체계·Free 계정 처리가 MVP 요구사항으로 신규 반영됨에 따라, 실시간 상태 모델(이제 Firebase 기반 — `06-mvp-scope-and-tech-stack.md` "확정 — 기술 스택 결정" 참고)에는 참여자별 역할(host/admin/regular)과 계정 등급(Free/Premium 등) 필드가 함께 관리되어야 한다. 서비스 전환 이벤트(기존 "활성 서비스 변경" 이벤트)는 방장/관리자 권한 검증을 서버(Cloud Functions) 측에서 반드시 강제해야 하며, 클라이언트 UI에서 버튼을 숨기는 것만으로는 권한 우회를 막을 수 없다는 점을 구현 단계가 유의해야 한다.

## 디자인 에이전트 전달 사항 (2026-07-24 신규, 2026-07-24 갱신 — 리더 전달 사용자 결정 3건 반영, 2026-07-25 갱신 — 리더 전달 사용자 결정 4건 추가 반영)

> 아래 항목은 이번에 신규 반영된 요구사항(세션 정원, 3단계 권한 체계, Free 계정 처리)에 따라 추가 디자인 작업이 필요한 목록이다. 리더가 디자인 에이전트에게 전달할 것을 제안한다. **2026-07-24 갱신**: 같은 날 사용자가 관리자 임명권 주체(방장)/정원 기본값(2명)/Free 계정 참여 허용(해석 A) 3건을 확정함에 따라, 아래 목록 중 일부는 "두 가지 시나리오를 동시에 대비"할 필요가 없어져 단순화됐다. 단순화된 항목은 표시를 달아 구분한다. **2026-07-25 갱신**: 관리자 임명 취소/사임 가능·관리자 인원 상한 없음·호스트 마이그레이션 시 관리자 목록 유지·세션 정원 생성 후 변경 불가 4건이 추가로 확정됨에 따라, 기존 2번·5번 항목을 갱신하고 신규 7·8번 항목을 추가했다(다음 라운드에 리더가 designer에게 전달할 것을 제안).

1. **역할 배지 UI**: 참여자 목록/곡 항목 등에서 방장/관리자/일반사용자를 구분하는 아이콘·색상·라벨 디자인이 필요하다.
2. **세션 생성 화면 — 정원 설정 UI**: 방장이 2~12명 범위에서 정원을 직접 지정하는 입력 컴포넌트(슬라이더/드롭다운/스테퍼 등)가 필요하다. **(2026-07-24 갱신, 단순화 가능)** 기본값이 2명으로 확정됐으므로, 입력 컴포넌트는 "값을 아예 지정하지 않은 초기 상태"를 별도로 설계할 필요 없이 처음부터 2명이 선택된 상태로 렌더링하면 된다(스테퍼/슬라이더 초기 위치를 2로 고정). **(2026-07-25 갱신, 추가 단순화)** 정원이 세션 생성 시점에만 설정되고 이후 변경 불가로 확정됐으므로, 이 스테퍼/슬라이더 컴포넌트는 **오직 "세션 생성" 화면 전용**이다 — "세션 설정"(00-ux-flow.md 2.13) 등 생성 이후 화면에는 정원 변경 UI를 별도로 설계할 필요가 없다(이전에는 생성 후 변경 가능 여부가 미정이라 재사용 가능성을 열어뒀으나, 이제는 그 가능성이 사라졌다). 세션 설정 화면에는 대신 "정원: 2명 (변경 불가)"처럼 읽기 전용으로만 표시하는 것을 제안한다.
3. **참여 인원 표시 UI**: "참여 인원"과 "재생 인원"(Free 계정 제외)을 구분해서 보여줘야 한다. **(2026-07-24 갱신, 단순화된 동시에 필수로 확정됨)** 이전에는 해석 A/B 중 어느 쪽이 채택될지 몰라 "두 숫자가 같을 수도, 다를 수도 있는" 유연한 레이아웃을 함께 대비해야 했으나, 이제 해석 A로 확정되어 **참여 인원 ≥ 재생 인원 상황이 항상 발생할 수 있는 것으로 확정**됐다 — 즉 "두 숫자가 다를 수 있는 케이스"에 대한 디자인만 준비하면 되고, "정원=Free 계정 참여 자체를 막는" 시나리오(해석 B)는 더 이상 대비할 필요가 없다.
4. **Free 계정 안내 UI**: Free 계정 사용자에게 "곡 재생(동기화 재생)에 참여할 수 없습니다"를 알리는 배너/모달/인라인 안내 디자인이 필요하다. **(2026-07-24 갱신, 단순화 가능)** 이전에는 "Free 계정이 세션에 아예 들어오지 못하는 경우(해석 B)"까지 대비해 진입 차단 화면(예: "Premium 계정만 참여 가능합니다" 같은 게이트 UI)을 함께 설계해둘 필요가 있었으나, 해석 A로 확정되어 **세션 진입 자체를 막는 화면은 더 이상 설계할 필요가 없다** — 세션 내부에서 재생 기능만 제한하는 배너/모달/인라인 안내 한 가지 형태로 좁혀 설계하면 된다. 또한 이 경고문은 **Spotify 세션에서만 노출**하고 **YouTube 세션에서는 노출하지 않는 것**으로 확정됐으므로, 컴포넌트 자체에 세션의 활성 서비스 타입에 따른 조건부 렌더링 로직(방장이 켜고 끄는 토글이 아니라 시스템이 서비스 타입으로 자동 판단)을 전제로 설계할 것을 제안한다.
5. **관리자 임명 UI**: 방장이 참여자 목록에서 특정 참여자를 관리자로 임명(및 해제)하는 흐름의 UI 슬롯이 필요하다. **(2026-07-24 갱신)** 임명권을 방장이 갖는다는 점은 확정됐으므로 "임명 버튼/메뉴가 방장에게만 노출된다"는 전제로 설계를 진행할 수 있다. 다만 임명 취소(해제) 시 확인 절차, 관리자 스스로 사임 가능 여부 등 세부 흐름은 여전히 "확인 필요" 상태이므로, 이 부분까지 세부 UX로 확정 짓지 말고 슬롯 수준에서만 다루는 것을 제안한다. **(2026-07-25 갱신)** "관리자 임명 취소(해제)가 가능하다"와 "관리자 스스로 사임할 수 있다"는 이제 둘 다 확정 사실이므로, UI에는 이 두 가지를 위한 자리가 각각 명시적으로 필요하다 — ① 방장 시점: 참여자 목록에서 이미 관리자인 사람에게는 "관리자로 임명" 대신 "관리자 해제" 메뉴 항목이 노출돼야 한다(현재 6.4절은 이를 이미 다루고 있어 구조 변경은 불필요). ② 관리자 본인 시점: 관리자 자신의 화면(예: 세션 설정 "내 역할" 영역, `00-ux-flow.md` 2.13)에 "관리자 사임하기" 같은 본인 조작 진입점이 신규로 필요하다 — 이는 기존 6.4절이 다루지 않던 "본인이 자기 권한을 반납하는" 흐름이라 별도 UI 슬롯을 추가해야 한다. 다만 확인 다이얼로그 문구 등 구체적 절차는 여전히 확정 전이므로 슬롯 수준에서만 다룰 것을 제안한다. 관리자 인원 상한이 무제한으로 확정됐으므로, "상한 도달 시 메뉴 비활성화" 같은 분기 UI는 설계할 필요가 없다(항상 임명 가능한 상태로 단순화).
6. **서비스 전환 버튼의 권한별 노출 상태**: 기존에 설계된 "서비스 전환" 항목(세션 설정 화면)이 이제 방장/관리자에게만 노출되거나, 일반사용자에게는 비활성화 + 안내 문구("방장 또는 관리자만 전환할 수 있어요" 등)로 표시되는 상태 디자인이 필요하다.
7. **(2026-07-25 신규) 호스트 마이그레이션 시 관리자 목록 유지 안내**: 방장이 이탈해 다른 참여자가 새 방장이 될 때, 기존 관리자 목록이 그대로 유지된다는 사실이 확정됐다(선출 규칙 자체는 여전히 미정). 마이그레이션 발생 토스트(`02-key-ui-patterns.md` 2.5절이 이미 다루는 "호스트가 바뀌었다" 토스트)에 "기존 관리자 권한은 그대로 유지됩니다" 같은 보조 문구를 추가할지, 아니면 별도 안내 없이 조용히 유지할지는 디자인 단계 판단에 맡긴다. 새 방장에게는 즉시 6.4절의 임명 메뉴 접근 권한이 부여되어야 하므로, 역할 배지·메뉴 노출 상태가 마이그레이션 시점에 실시간으로 갱신되는지 확인이 필요하다(구현 단계와 연계).
8. **(2026-07-25 신규) 세션 정원 표시의 "고정" 성격 반영**: 위 2번 항목과 연결 — 정원이 생성 후 고정된다는 사실이 확정됐으므로, 세션 설정 화면(`00-ux-flow.md` 2.13)이나 참여자 목록 헤더 등에서 정원을 노출할 때 "변경 가능한 설정값"이 아니라 "세션 생성 시 결정된 고정 값"이라는 인상을 주도록(예: 편집 아이콘 없이 텍스트로만 표시) 설계할 것을 제안한다. 정원이 가득 찼을 때의 안내(7.2절)는 기존 설계 그대로 유효하다 — 이번 결정으로 바뀌는 부분이 아니다.
