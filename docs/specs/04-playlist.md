# 04. 협업 플레이리스트 기능 명세

> 상태: 초안(v1) — 2026-07-23, 2026-07-23 갱신(MVP 범위 결정 변경 반영 — 서비스별 플레이리스트 독립 보존, `01-user-stories.md` US-105b/US-105c/US-308, `06-mvp-scope-and-tech-stack.md` "갱신된 MVP 범위 결정" 참고), 2026-07-23 추가(개인 플레이리스트 Import 가능 여부 조사 — Spotify/YouTube 공식 API 확인, 멜론/지니뮤직은 `08-korean-services-melon-genie.md` 결론에 따라 불가), 2026-07-23 추가(크로스플랫폼 혼합 모드 MVP 포함 결정 반영 — "혼합 모드 플레이리스트 구조" 절 신규, `09-cross-platform-mixed-mode.md` "결정 갱신" 절, `01-user-stories.md` US-105d/US-309/US-310 참고)

## 배경

방(세션)의 핵심 콘텐츠는 "함께 만들어가는 플레이리스트"다. CLAUDE.md 요구사항: 참여자 모두가 곡 추가/삭제/순서변경 가능, 각 곡을 누가 선곡했는지 표시. 이 문서는 이를 실제 기능 단위로 구체화한다. (데이터베이스 스키마·API 설계 등 구현 상세는 구현 에이전트 몫이며, 여기서는 기능 요구사항 수준까지만 다룬다.)

## 요구사항

### 플레이리스트 구조

- (2026-07-23 갱신) 플레이리스트는 **방(세션) + 서비스 타입의 조합에 종속**된다 — 방이 유지되는 동안 "Spotify 플레이리스트"와 "YouTube 플레이리스트"를 각각 독립적으로 갖는다(개념적으로 세션 1 : 서비스별 플레이리스트 N, 현재 N=2). 세션은 한 번에 하나의 서비스만 활성화되어 재생하지만(`01-user-stories.md` US-105), 사용자는 세션 도중 활성 서비스를 전환할 수 있고(US-105b) 이때 비활성화되는 쪽 플레이리스트는 삭제되지 않고 그대로 보존되어 나중에 다시 그 서비스로 돌아오면 이어서 쓸 수 있다(US-105c/US-308). 상세 데이터 모델(스키마)은 구현 단계 몫이나, 개념적으로는 "플레이리스트 엔터티가 세션 ID뿐 아니라 서비스 타입도 키로 갖는다" 정도로 이해하면 된다.
- 옛 서술(대체됨, 이력 보존): ~~플레이리스트는 방(세션)에 1:1로 종속되어 방이 유지되는 동안 하나의 플레이리스트만 공유한다.~~ 이 서술은 "세션 도중 서비스 전환 불가"를 전제로 했던 것이라 위 갱신 내용으로 대체한다.
- 곡 항목(entry)은 다음 정보를 포함한다 (Spotify 전용/YouTube 전용 세션 기준 — 혼합 세션의 곡 항목 구조는 아래 "혼합 모드 플레이리스트 구조" 절에서 별도로 다룬다):
  - 곡 메타데이터 (제목, 아티스트/채널, 썸네일, 길이, 서비스별 고유 ID — Spotify track URI 또는 YouTube videoId)
  - 추가한 사람(닉네임, 프로필 이미지)
  - 추가된 시각
  - 재생 여부(이미 재생됨/대기 중/현재 재생 중)

### 혼합 모드 플레이리스트 구조 (2026-07-23 추가 — 크로스플랫폼 혼합 모드 MVP 포함 결정 반영)

> 근거/결정 배경: `09-cross-platform-mixed-mode.md` "결정 갱신 (2026-07-23)" 절, `01-user-stories.md` US-105d/US-309/US-310.

혼합(Mixed) 세션은 위에서 서술한 "세션 + 서비스 타입 조합에 종속되는 플레이리스트"(세션 1 : 서비스별 플레이리스트 N) 구조와 **근본적으로 다른 구조**를 쓴다. 이유는 혼합 세션에는 애초에 "활성화된 서비스 하나"라는 개념이 없고, 참여자마다 서로 다른 서비스가 **동시에** 활성 상태이기 때문이다(구조적 차이의 상세 비교는 `09-cross-platform-mixed-mode.md` "결정 3" 절 참고).

- **플레이리스트는 세션당 하나뿐이다(세션 1 : 플레이리스트 1, 플랫폼 중립)** — Spotify용/YouTube용으로 나뉘지 않는다.
- **곡 항목(entry)의 구조**: 하나의 곡 항목은 두 계층으로 구성된다(개념 수준, 상세 스키마는 구현 단계 몫).
  1. **공통 식별자 계층** — 모든 참여자가 공유하는 플랫폼 중립 메타데이터: 제목, 아티스트, (참고용) 대표 썸네일, 대표 재생 길이, 추가한 사람, 추가된 시각. 이 계층은 특정 플랫폼의 트랙 ID를 갖지 않는다 — "무슨 곡인지"만 나타낸다.
  2. **참여자별 매칭 트랙 계층** — 같은 곡 항목 아래, 참여자 각자가 자신의 플랫폼에서 실제로 매칭된 트랙 정보를 별도로 갖는다: 매칭된 서비스(Spotify/YouTube), 서비스별 고유 ID(track URI 또는 videoId), 실제 제목/아티스트/썸네일/길이(공통 식별자와 다를 수 있음 — 매칭이 다른 에디션을 가리킬 가능성이 있기 때문, `09-cross-platform-mixed-mode.md` 2절), **일치율/신뢰도 값**, 참여자의 확인 상태(자동 매칭 대기/확정됨/수동 교체됨).
- **매칭 확인 UI 요구사항(필수, US-309/US-310)**: 곡이 플레이리스트에 추가되면 각 참여자의 클라이언트가 자신의 플랫폼에서 검색을 수행해 후보를 매칭하고, 그 결과(제목/아티스트/썸네일/길이 + 일치율/신뢰도)를 참여자에게 표시한다. 참여자는 이를 "확정" 또는 "직접 재검색해 수동 교체" 중 하나로 처리해야 하며, 이 확인 없이 자동 매칭 결과만으로 조용히 재생에 들어가는 흐름은 채택하지 않는다. 이 확인은 참여자별로 독립적으로 이뤄진다(한 참여자의 확인이 다른 참여자의 매칭에 영향을 주지 않음).
- **선곡자 표시와의 관계**: 공통 식별자 계층의 "추가한 사람"이 기존 "선곡자 표시" 정책(아래 "기능 목록" 4번)이 가리키는 대상과 동일하다 — 혼합 모드에서도 "누가 이 곡을 골랐는지"는 플랫폼과 무관하게 한 사람으로 표시된다. 참여자별 매칭/확인 상태는 별도의 UI 요소(예: "OO님이 확인함" 배지 등, 디자인 단계에서 다룰 것을 제안)로 구분해 표시하는 것을 제안한다.
- **재생 동기화와의 관계**: 서버는 여전히 공통 식별자 계층의 곡 항목과 "플랫폼 중립 기준 위치(경과 시간)"만을 단일 진실로 브로드캐스트한다(`05-sync-architecture.md` 모델 그대로 재사용). 각 참여자 클라이언트는 자신의 참여자별 매칭 트랙 계층에 있는 길이 정보를 기준으로 이 위치를 자신의 트랙 좌표로 환산해 seek한다.
- **혼합 모드에는 "서비스 전환"이 없다**: 기존 US-105b(세션 도중 Spotify↔YouTube 전환)는 혼합 세션에는 적용되지 않는다 — 혼합 세션은 세션 생성 시점부터 여러 서비스가 동시에 활성 상태이므로, "전환"이라는 개념 자체가 성립하지 않는다.

### 기능 목록

1. **곡 검색 및 추가**
   - 방에서 사용 중인 서비스(Spotify 또는 YouTube)의 검색 API로 곡을 검색한다.
   - 검색 결과에서 선택 시 플레이리스트 맨 뒤(또는 "다음 곡"으로 우선 추가하는 옵션)에 추가된다.
   - 중복 곡 추가 시 경고 또는 허용 여부는 방 설정으로 둔다(기본: 허용, 단 UI에서 "이미 있음" 표시).

2. **곡 삭제**
   - 참여자 누구나 삭제 가능(기본 정책). 현재 재생 중인 곡 삭제 시 다음 곡으로 자동 전환.
   - 삭제 시 "누가 삭제했는지"는 굳이 노출하지 않아도 되나, 추후 신뢰 이슈 발생 시를 대비해 서버 로그에는 남긴다(제안, 확정 아님).

3. **순서 변경**
   - 드래그 앤 드롭 등으로 순서 변경. 변경 사항은 실시간으로 모든 참여자 화면에 반영.
   - 이미 재생 완료된 곡과 대기 중인 곡의 순서 변경 범위를 구분할지는 UX 결정 사항 (디자인 단계에서 다룰 것을 제안).

4. **선곡자 표시**
   - 각 곡 항목에 추가한 사람의 아바타/닉네임을 배지 형태로 표시.

5. **자동 다음 곡 재생**
   - 현재 곡이 끝나면 플레이리스트의 다음 곡으로 자동 전환하고, 이 전환도 동기화 대상이다(전원이 같은 순간에 다음 곡으로 넘어가야 함).

6. **플레이리스트 저장/재사용** `[P2]`
   - 방이 종료된 뒤에도 플레이리스트를 계정에 저장해 나중에 다시 불러오거나, Spotify/YouTube의 정식 플레이리스트로 내보내기(export)하는 기능.

7. **개인 플레이리스트 가져오기(Import)** `[P2]` (2026-07-23 조사 추가 — 우선순위는 제안일 뿐, 최종 확정은 사용자/리더 몫)
   - 참여자가 각 서비스에 이미 갖고 있는 자신의 개인 플레이리스트를 통째로 세션 플레이리스트에 가져오는 기능. 서비스별 가능 여부는 아래 "개인 플레이리스트 Import 가능 여부 조사" 절 참고.

### 동시 편집 처리

- 여러 사람이 동시에 곡을 추가/삭제/순서 변경할 수 있으므로, 서버가 **단일 진실 공급원(source of truth)** 역할을 하고 클라이언트는 실시간 채널(웹소켓 등)을 통해 변경 이벤트를 받아 반영하는 구조를 제안한다.
- 순서 변경 시 동시 충돌(예: 두 사람이 동시에 서로 다른 곡을 맨 위로 옮김) 처리 전략은 구현 단계에서 결정하되, 기획 단계에서는 최소 요구사항으로 "마지막 조작이 우선 적용되고, 다른 참여자 화면은 즉시 갱신되어 눈에 보이는 불일치가 없어야 한다"를 명시한다.

### 개인 플레이리스트 Import 가능 여부 조사 (2026-07-23 추가)

> 리서치 근거: Spotify Web API 공식 문서, YouTube Data API v3 공식 문서, `08-korean-services-melon-genie.md`(멜론/지니뮤직 조사 결과 재인용). (2026-07-23 기준 WebFetch로 확인)

각 참여자가 이미 갖고 있는 서비스별 개인 플레이리스트를 세션에 그대로 가져올 수 있는지 서비스별로 조사했다.

**Spotify — 가능 (확실성 높음, 공식 문서 확인)**

- `GET /v1/me/playlists` ("Get Current User's Playlists"): 로그인한 사용자가 소유하거나 팔로우하는 플레이리스트 목록을 페이지네이션으로 조회한다. 필요 스코프: `playlist-read-private`. 응답에는 각 플레이리스트의 ID/이름/설명/트랙 개수/공개 여부 등이 포함된다.
- `GET /v1/playlists/{playlist_id}/tracks` ("Get Playlist Items"): 특정 플레이리스트에 포함된 트랙 목록을 조회한다. 필요 스코프는 동일하게 `playlist-read-private`(비공개 플레이리스트 접근 시).
- 각 트랙 항목에는 이미 `external_ids.isrc`, 제목, 아티스트, 앨범, `duration_ms`, URI 등이 포함되어 있어(`02-spotify-integration.md`, `09-cross-platform-mixed-mode.md` 참고) 세션 플레이리스트 항목 스키마로 변환하는 데 추가 조회가 거의 필요 없다.

**YouTube — 가능하나 일부 시스템 재생목록은 제외됨 (확실성 높음, 공식 문서 확인)**

- `playlists.list`에 `mine=true` 파라미터를 지정하면(적절히 인증된 요청 필요) 로그인한 사용자 본인 소유의 재생목록만 반환한다. 이후 각 재생목록 ID로 `playlistItems.list`를 호출해 포함된 동영상 항목을 가져온다. 최소 필요 스코프는 읽기 전용 `https://www.googleapis.com/auth/youtube.readonly`로 충분하다.
- **주의**: "시청 기록(Watch History)"과 "나중에 볼 동영상(Watch Later)"은 YouTube가 시스템 관리 재생목록으로 취급해 API로 접근이 차단되어 있다(빈 목록 반환) — 이 두 재생목록은 Import 대상에서 원천적으로 제외된다. 반면 **"좋아요 표시한 동영상(Liked Videos)"은 예외적으로 접근 가능**하다 — `channels.list`로 얻는 `contentDetails.relatedPlaylists.likes` 재생목록 ID를 `playlistItems.list`에 넘기면 좋아요 목록을 가져올 수 있다.
- YouTube Data API의 일일 쿼터 제약(04 문서 기존 "제약/리스크" 절 참고)은 Import 시에도 그대로 적용된다. 큰 재생목록(수백 곡)을 여러 참여자가 동시에 Import하면 쿼터 소진 속도가 빨라질 수 있어, Import 1회당 가져올 수 있는 곡 수 상한을 두는 것을 제안한다(구체적 상한값은 쿼터 실측 후 결정).

**멜론/지니뮤직 — 불가능**

- `08-korean-services-melon-genie.md`에서 확인했듯 두 서비스 모두 서드파티용 공식 API 자체가 없으므로, 개인 플레이리스트 조회 기능도 당연히 제공되지 않는다. 별도 조사 없이 "불가능"으로 결론 내리는 것으로 충분하다.

**선곡자 표시 정책과의 관계**

- 기존 "선곡자 표시"(각 곡 항목에 추가한 사람의 아바타/닉네임 배지) 정책과 자연스럽게 어우러진다 — **Import로 가져온 곡들의 선곡자는 "Import를 실행한 참여자 본인"으로 표시하면 된다.** 이는 "누가 이 곡을 추가했는지"라는 기존 정책의 의미를 그대로 확장한 것뿐이라 별도의 새로운 규칙이 필요하지 않다. 다만 "곡 100개를 한 번에 Import"한 경우 배지가 화면을 도배하는 UX 문제는 있을 수 있어(예: "OO님이 플레이리스트를 가져왔습니다"라는 묶음 표시 등), 이는 디자인 단계에서 다룰 것을 제안한다.
- Import 시 중복 곡 처리(이미 세션 플레이리스트에 있는 곡을 다시 Import하는 경우)는 기존 "곡 검색 및 추가"의 중복 처리 정책(기본 허용 + "이미 있음" 표시)을 그대로 적용하는 것을 제안한다.

## 제약/리스크

- **서비스별 검색 API 제약**: Spotify Web API 검색(`/v1/search`)은 자유롭게 사용 가능하나, YouTube Data API 검색(`search.list`)은 **일일 쿼터(quota) 제한**이 있다(기본 할당량은 낮은 편으로 알려져 있으며, 검색 1회 호출이 다른 엔드포인트보다 쿼터를 많이 소모함 — 정확한 수치는 Google Cloud Console 등록 시점에 재확인 필요, **확인 필요**). 다인원이 동시에 검색을 남발하면 쿼터가 빠르게 소진될 수 있어 캐싱/디바운스 전략이 필요하다.
- **플레이리스트 곡 정보의 서비스 종속성**: Spotify 트랙과 YouTube 동영상은 같은 곡이어도 서로 다른 ID 체계를 쓰므로, 서비스 타입에 따라 플레이리스트 항목의 스키마가 갈린다. (2026-07-23 갱신) 옛 제안("MVP는 방-서비스 1:1 고정 전제로 단순화, 서비스 전환은 향후 검토 대상")은 사용자의 결정 변경으로 대체됨 — 이제 "같은 세션에서 서비스 전환"이 MVP 요구사항이 되었다(`01-user-stories.md` US-105b/US-105c/US-308). 따라서 곡 식별자/플레이리스트 항목 스키마는 처음부터 **서비스 타입별로 분리된 구조**(예: 세션당 서비스별 플레이리스트를 별도 레코드/컬렉션으로 관리하고, 두 서비스 간 곡 식별자를 억지로 통합·추상화하려 하지 않는 것)로 설계하는 편이 오히려 단순하다 — 애초에 곡 식별자 통합이 필요 없는 구조이기 때문이다. 상세 스키마 설계는 구현 단계 몫이다.
- **삭제 권한 남용**: 전원 삭제 허용 정책은 편리하지만 악의적 사용자가 플레이리스트를 비우는 상황이 가능하다. MVP에서는 소규모 지인 간 사용을 전제로 리스크를 감수하고, 추후 권한 세분화(`[P2]`)를 검토한다.
- **(2026-07-23 추가) 혼합 모드 매칭 신뢰도 한계**: 혼합 세션의 참여자별 매칭 트랙은 YouTube가 ISRC 등 표준 식별자를 노출하지 않아 근본적으로 휴리스틱(제목 유사도+아티스트 일치+길이 오차) 매칭에 의존한다(`09-cross-platform-mixed-mode.md` 1·2절). "매칭 결과 고지 + 사용자 확인/수정 UI"(위 "혼합 모드 플레이리스트 구조" 절)로 리스크를 완화하지만 완전히 제거하지는 못한다 — 특히 "길이는 같으나 구조가 다른 편집판"은 UI 확인 단계에서도 참여자가 육안/청감으로 알아채지 못하면 걸러지지 않을 수 있다는 한계를 구현/검증 단계가 인지해야 한다.

## 제안

- MVP 기능 범위: 검색·추가·삭제·순서변경·선곡자 표시·자동 다음 곡 재생까지 포함. 저장/재사용, export, 좋아요/투표 기능은 P2로 미룬다.
- (2026-07-23 추가) MVP 범위가 Spotify+YouTube 동시 지원으로 갱신됨에 따라, 위 기능 범위는 **서비스별로 각각(플레이리스트가 두 벌 존재)** 구현되어야 하며, 세션 설정에서의 서비스 전환(US-105b) 시 활성 플레이리스트만 바뀌고 비활성 쪽 데이터는 보존되어야 한다(US-105c/US-308). 이 부분은 위 "플레이리스트 구조"/"제약·리스크" 절 갱신 내용과 함께 구현 착수 전 반드시 반영해야 하는 요구사항이다.
- 실시간 동기화 채널은 재생 상태 동기화(`05-sync-architecture.md`)와 동일한 실시간 인프라(예: WebSocket)를 공유하는 것을 제안한다 — 별도 폴링 API를 또 만들 필요 없이 "방 이벤트 스트림"에 플레이리스트 변경 이벤트도 함께 흘려보내는 설계. 서비스 전환 이벤트도 같은 스트림에서 "활성 서비스 변경" 이벤트로 흘려보내는 것을 제안한다.
- (2026-07-23 추가) 혼합 모드가 MVP로 포함됨에 따라, 위 기능 범위(검색·추가·삭제·순서변경·자동 다음 곡)는 혼합 세션에서도 동일하게 제공하되, "혼합 모드 플레이리스트 구조" 절의 이중 계층(공통 식별자 + 참여자별 매칭 트랙)과 매칭 확인 UI(US-309/US-310)를 함께 구현해야 한다. 혼합 세션의 플레이리스트 변경 이벤트(곡 추가/삭제/순서변경)와 "참여자별 매칭 확정/수동 교체" 이벤트는 서로 다른 종류의 이벤트로 구분해 같은 실시간 스트림에 흘려보내는 것을 제안한다(전자는 전원에게 영향, 후자는 해당 참여자 개인의 로컬 상태 변경).
