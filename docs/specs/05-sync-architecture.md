# 05. 재생 동기화(저지연) 아키텍처 — 초기 방향

> 상태: 초안(v1) — 2026-07-23
> 주의: 이 문서는 기획 단계에서 "실현 가능성 판단에 필요한 수준"까지만 다룬다. 상세 설계(구체적 프로토콜, 자료구조, 코드)는 구현 에이전트의 몫이다.

## 배경

CLAUDE.md의 핵심 비기능 요구사항은 "실시간성/저지연 최우선 (재생 동기화 오차 최소화)"다. `02`, `03` 문서의 리서치 결과, Spotify와 YouTube 둘 다 **"우리 서버가 오디오를 직접 스트리밍한다"는 구조를 쓸 수 없다** — Spotify는 각 참여자의 로컬 Spotify 앱이, YouTube는 각 참여자의 로컬 WebView 임베드 플레이어가 실제 오디오를 재생한다. 따라서 아키텍처의 본질은 "여러 개의 독립된 로컬 플레이어를, 네트워크로 최대한 같은 지점에서 재생되도록 계속 맞춰주는 것"이다.

이는 화상회의의 "동시 재생(watch party)" 서비스들이 공통적으로 쓰는 **호스트-팔로워(host-follower) 동기화 모델**과 본질적으로 같은 문제다.

## 요구사항 (동기화 관점)

1. 방 참여자 전원의 재생 위치 오차를 사람이 체감하기 어려운 수준으로 최소화한다.
2. 재생/일시정지/탐색(seek)/곡 전환 조작이 발생하면 다른 참여자에게 최대한 빠르게 전파된다.
3. 늦게 들어온 참여자(late join)는 현재 재생 중인 곡·위치로 즉시 맞춰진다.
4. 일시적 네트워크 지연/끊김 이후에도 자동으로 재동기화(드리프트 보정)된다.
5. 방장이 이탈해도 세션이 끊기지 않는다(호스트 마이그레이션).

## 제약/리스크

- **오디오 스트림 자체를 우리가 통제할 수 없다**는 전제 때문에, 완벽한 프레임 단위 동기화(예: 화상회의의 음성 동기화 수준)는 애초에 목표로 삼을 수 없다. 목표는 "밀리초 단위 완벽 일치"가 아니라 "사람이 어긋남을 인지하기 어려운 수준"으로 재정의해야 한다.
- 오차의 하한선은 다음 요인들이 좌우하며, 이는 서비스별로 다르다:
  - Spotify: App Remote SDK의 명령 전달 지연(우리 서버 → 참여자 기기 → App Remote → Spotify 앱), Spotify 앱 자체의 버퍼링/디코딩 지연. 정확한 수치는 공식 문서에 없어 프로토타입 실측이 필요하다(`02` 문서에서 이미 지적).
  - YouTube: WebView 내 IFrame Player의 seek 명령 반응 속도, 버퍼링 상태, (광고가 나온다면) 광고 재생 구간의 길이가 참여자마다 달라질 수 있다는 추가 변수.
  - 공통: 참여자 각자의 네트워크 지연(RTT), 우리 실시간 채널(WebSocket 등)의 서버 처리 지연.
- 두 서비스를 한 세션에서 **동시에** 혼용하면 동기화 기준 자체가 서비스마다 다른 지연 특성을 가지므로 복잡도가 크게 증가한다 — `01-user-stories.md` US-105에서 "한 세션은 한 번에 하나의 서비스로만 재생"을 제안한 이유다. (2026-07-23 갱신: 이는 "동시 혼용 금지"에 대한 근거이며, "세션 도중 서비스를 전환하는 것" 자체를 막는 근거는 아니다 — 전환은 US-105b로 MVP 범위에 포함되었고, 전환 시점에는 활성 플레이어가 바뀌므로 재생이 잠시 멈췄다가 새 서비스 기준으로 재동기화되는 것으로 처리한다. `06-mvp-scope-and-tech-stack.md` "갱신된 MVP 범위 결정" 절 참고.)

## 제안 — 초기 아키텍처 방향

### 1. 호스트-팔로워(또는 서버 기준 시계) 모델

두 가지 후보가 있으며, 최종 채택은 구현 단계에서 프로토타입 검증 후 결정할 것을 제안한다.

**모델 A: 서버를 기준 시계로 사용 (권장)**
- 서버가 "현재 곡, 재생 시작 기준 시각(server timestamp), 재생 중 여부"를 유일한 진실로 관리한다.
- 참여자 중 누구든 재생/일시정지/seek 조작을 하면 서버에 요청을 보내고, 서버가 상태를 갱신한 뒤 **모든 참여자(조작자 포함)에게** 새 상태를 브로드캐스트한다.
- 각 클라이언트는 수신한 "기준 시각 + 위치"와 자신의 로컬 시계 차이(clock offset, NTP 스타일 보정)를 계산해 자신의 로컬 플레이어가 있어야 할 위치를 산출하고 seek한다.
- 방장이 이탈해도 서버가 기준 시계를 들고 있으므로 세션이 끊기지 않는다(요구사항 5 자연 충족). 다만 "다음 곡 선택 우선권" 등 방장 고유 권한이 있다면 별도의 방장 재선출 로직이 필요하다.

**모델 B: 특정 참여자(호스트) 기기를 기준으로 삼음**
- 구현이 단순해 보이지만, 호스트 네트워크가 불안정하거나 호스트가 이탈하면 전체 동기화가 흔들린다. 요구사항 5(호스트 이탈 시에도 세션 유지)를 만족하려면 결국 "호스트 마이그레이션" 로직이 필요해 모델 A와 복잡도가 비슷해진다.
- → **모델 A(서버 기준 시계)를 기본 방향으로 제안**한다.

### 2. 실시간 전송 계층

- 상태 브로드캐스트(재생/일시정지/seek/곡전환/플레이리스트 변경) 전달에는 **양방향 저지연 채널(WebSocket 또는 이에 준하는 실시간 메시징)**이 필요하다. 오디오 자체를 우리가 실어나르지 않으므로 WebRTC의 미디어 트랙 기능은 필요 없고, WebRTC를 쓰더라도 데이터 채널(DataChannel) 용도로 국한된다.
- 클록 동기화(서버-클라이언트 시계 오프셋 계산)를 위한 간단한 ping-pong 프로토콜(NTP 알고리즘의 간소화 버전)을 병행해야 정확한 위치 계산이 가능하다.

### 3. 드리프트 보정

- 각 클라이언트는 주기적으로(예: 수 초 간격) 자신의 실제 재생 위치와 "서버 기준 계산 위치"를 비교하고, 차이가 임계값(예: 수백 ms, 정확한 값은 서비스별 실측 후 확정)을 넘으면 미세 seek로 보정한다.
- 임계값을 너무 낮게 잡으면 잦은 seek로 인해 오히려 끊김이 체감되고, 너무 높게 잡으면 어긋남이 체감된다 — 이 튜닝은 실측 기반으로 검증/구현 단계에서 정한다.

### 4. Late join / 재접속

- 참여자가 새로 들어오거나 재접속하면, 서버에 현재 상태를 요청해 "곡 ID + 서버기준 재생위치 + 재생여부"를 받아 즉시 그 위치로 로컬 플레이어를 맞춘다.

### 5. 서비스별 특이사항 반영

- Spotify 방: 서버 상태 변경 시 각 클라이언트가 자신의 App Remote SDK로 로컬 Spotify 앱에 재생/seek 명령을 내린다.
- YouTube 방: 서버 상태 변경 시 각 클라이언트가 자신의 WebView 내 IFrame Player에 JS 브릿지로 재생/seek 명령을 내린다. 광고가 개입되는 구간은 동기화 예외 처리가 필요할 수 있다(광고 종료 후 재동기화).

## 다음 단계 제안 (구현/검증 단계에 넘길 것)

- 목표 오차 수치(예: ±200ms, ±500ms 등)는 기획 단계에서 근거 없이 확정하지 않고, **Spotify App Remote 실측 프로토타입** 및 **YouTube WebView IFrame 실측 프로토타입**을 가장 먼저 만들어 확인할 것을 권고한다.
- 실시간 전송 계층의 구체적 기술(자체 WebSocket 서버 vs 관리형 서비스)은 `06-mvp-scope-and-tech-stack.md`에서 후보를 제시하되 최종 결정은 사용자 확인 후 진행한다.
