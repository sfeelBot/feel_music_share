# 06. Spotify vs YouTube 리스크 비교, MVP 범위 권고, 기술 스택 후보

> 상태: 초안(v1) — 2026-07-23
> 이 문서는 리더 보고 및 사용자 의사결정을 위한 요약/권고 문서다. 기술 스택은 **후보 제시**이며 최종 확정은 사용자 몫이다.

## 배경

CLAUDE.md는 Spotify와 YouTube를 모두 지원하되, YouTube 쪽의 리스크가 크다고 명시하고 기획 단계에서 조사를 요구했다. `02`, `03`, `05` 문서의 리서치를 바탕으로 두 서비스의 기술적 리스크를 정면으로 비교하고, MVP(1차 버전) 범위에 대한 권고안을 제시한다. 또한 기술 스택 후보(모바일 프레임워크, 백엔드/실시간 동기화 기술)를 정리한다.

## 요구사항 (의사결정이 필요한 지점)

1. MVP에서 Spotify/YouTube 중 무엇을 우선(또는 동시) 지원할지
2. 재생 동기화 목표 오차 수준을 어떻게 다룰지 (수치 확정은 실측 이후로 미룸에 동의하는지)
3. 방-서비스 1:1 고정 정책(한 방에서 서비스 혼용 금지)에 동의하는지
4. 모바일 프레임워크, 백엔드, 실시간 동기화 기술 후보 중 사용자의 선호나 팀 역량에 따른 선택

## 제약/리스크 — Spotify vs YouTube 비교

| 항목 | Spotify | YouTube(Premium) |
|---|---|---|
| 공식 재생 제어 SDK 존재 여부 | 있음 (App Remote SDK, iOS/Android 공식 지원) | 네이티브 전용 공식 SDK 없음(Android Player API·iOS Player Helper 모두 단종/아카이브). 대체 수단은 WebView + IFrame Player API(원래 웹임베드용) |
| 재생 위치가 실제로 위치하는 곳 | 참여자 기기의 **공식 Spotify 앱** | 참여자 기기의 **WebView 내 임베드 플레이어**(우리 앱 프로세스 내부) |
| 필수 설치물 | Spotify 공식 앱 설치 필요 | 별도 앱 설치 불필요(임베드로 대체) |
| 유료 등급 요건 | 전원 Premium 필수 (Free는 곡 지정 재생 불가) — 명확 | YouTube Premium이 있어도 임베드 환경에서 무광고가 보장되는지 **불확실**(확인 필요) |
| ToS 리스크 | 낮음 — 공식 SDK 용도 그대로 사용 | 중간~높음 — 임베드 정책(Required Minimum Functionality) 준수 필요, 광고 차단 시도는 명백한 위반으로 API/계정 정지 리스크 |
| 로그인/인증 리스크 | Spotify OAuth는 임베드 웹뷰 제약 이슈 보고 사례 있으나(포럼 이슈) 표준 OAuth 플로우로 처리 가능 | Google OAuth가 **임베디드 웹뷰에서 전면 차단**되어 있어(2023년부터), 로그인은 반드시 시스템 브라우저 경유 — 구현 복잡도/제약 추가 |
| API 성숙도/문서화 | 성숙, 공식 문서 풍부 | Data API는 성숙하나 "재생 제어" 자체는 애초에 문서화된 지원 대상이 아님(웹임베드 용도를 앱에 우회 적용하는 것) |
| 동기화 지연 예측 가능성 | App Remote push 구독으로 상대적으로 예측 가능(단 정확 수치는 실측 필요) | WebView 브릿지 + 광고 개입 변수까지 있어 지연 편차가 더 클 것으로 예상(실측 필요) |
| 종합 리스크 | **낮음** | **높음** |

### 종합 판단

Spotify는 "공식적으로 서드파티가 하라고 만들어준 일"을 하는 것에 가깝고, YouTube는 "원래 웹페이지 임베드용으로 만든 것을 모바일 앱에 우회 적용"하는 데다 가장 중요한 가치제안(무광고)이 기술적으로 보장되지 않을 위험까지 있다. 이 격차는 CLAUDE.md가 우려한 대로 실제로 큰 것으로 확인됐다.

## 제안 — MVP 범위 권고안

**권고: MVP는 Spotify만 지원하고, YouTube는 2차 단계로 미룬다.**

근거:
1. Spotify는 공식 SDK로 핵심 가치(재생 동기화)를 구현할 수 있는 명확한 경로가 있어 개발 리스크와 일정 예측이 가능하다.
2. YouTube는 핵심 가치 제안 중 하나인 "무광고 재생"이 임베드 환경에서 보장되는지가 불확실하다 — 이 불확실성을 실기기 실측으로 먼저 해소하지 않은 채 개발에 들어가면, 나중에 "광고가 낀 동기화 재생"이라는 예상 밖 제품이 될 위험이 있다.
3. YouTube의 ToS 준수 부담(광고 차단 시도 금지, 임베드 정책 준수, 웹뷰 로그인 불가로 인한 인증 플로우 추가 설계)은 개발 공수를 늘리고, 정책 위반 시 API/계정 정지라는 사업 연속성 리스크까지 수반한다.
4. 두 서비스를 동시에 1차 범위로 잡으면 검증(QA) 대상도 2배가 되어 "빠르게 핵심 가치(저지연 동기화)를 검증한다"는 MVP의 취지에 어긋난다.

**MVP 1차 범위 제안**
- 계정: Spotify OAuth 로그인, Premium 여부 확인
- 세션: 방 생성/초대/참여, 호스트 마이그레이션(서버 기준 시계 모델 채택 시 자연스럽게 해결)
- 플레이리스트: 검색/추가/삭제/순서변경/선곡자 표시/자동 다음 곡
- 동기화: 재생/일시정지/seek/late join/드리프트 보정 (Spotify App Remote 기반)
- 제외(2차, `[P2]`): YouTube 지원 전체, 채팅/리액션, 플레이리스트 저장·재사용/export, 세분화된 권한 관리

**YouTube 착수 전 선행 스파이크(2차 단계 진입 조건으로 제안)**
1. 실기기 + YouTube Premium 계정으로 WebView 임베드 플레이어에 광고가 뜨는지 직접 실측
2. WebView 내 IFrame Player의 seek/상태조회 응답 지연 실측
3. 위 결과를 바탕으로 "무광고 보장 불가 시 제품 카피/기대치를 어떻게 조정할지"를 사용자와 재논의

이 권고안은 어디까지나 기획 에이전트의 제안이며, 최종 MVP 범위 확정은 사용자(및 리더)의 결정 사항이다.

## 제안 — 기술 스택 후보 (미확정, 사용자 결정 필요)

아래는 후보 나열이며, 각 항목의 장단점을 정리했다. **최종 스택은 사용자가 결정한다.**

### 모바일 프레임워크

| 후보 | 장점 | 단점 |
|---|---|---|
| **React Native** | 크로스플랫폼 코드 공유로 iOS/Android 동시 개발 속도↑, Spotify/YouTube 커뮤니티 SDK 래퍼 존재, WebView 브릿지 작업에 익숙한 생태계 | 네이티브 SDK(App Remote, WebView 브릿지)와의 연동 시 네이티브 모듈 작성 필요, 저지연 실시간 처리에서 JS 브릿지 오버헤드 가능성 |
| **Flutter** | 크로스플랫폼, 성능이 RN보다 나은 경우 많음, UI 일관성 우수 | Spotify App Remote/YouTube WebView 연동용 커뮤니티 플러그인의 성숙도가 상대적으로 낮을 수 있음(확인 필요), 네이티브 브릿지(Platform Channel) 작성 필요는 동일 |
| **네이티브(Swift/Kotlin 각각)** | 공식 SDK(App Remote iOS/Android, WKWebView/Android WebView)와 가장 마찰 없이 통합, 저지연 요구사항에 가장 유리 | 두 플랫폼 별도 개발로 공수 2배, 일정/유지보수 부담 증가 |

### 백엔드 / 실시간 동기화 기술

| 후보 | 장점 | 단점 |
|---|---|---|
| **자체 WebSocket 서버 (Node.js/NestJS, Go 등)** | 동기화 로직(서버 기준 시계, 드리프트 보정 등)을 완전히 통제 가능, 커스터마이징 자유도 최고 | 인프라 운영 부담(스케일링, 재해복구)을 직접 져야 함 |
| **관리형 실시간 메시징 (Ably, Pusher 등)** | 인프라 운영 부담 없음, 빠른 초기 구축 | 커스텀 동기화 로직(클록 오프셋 계산 등)을 얹기에 다소 제약, 비용은 사용자/메시지량에 비례해 증가 |
| **Firebase (Realtime Database/Firestore + Cloud Functions)** | 빠른 프로토타이핑, 인증/DB/실시간을 한 번에 해결 | 초저지연 커스텀 동기화 프로토콜 구현 자유도가 상대적으로 낮음, 세밀한 지연 튜닝이 어려울 수 있음 |
| **Supabase (Postgres + Realtime)** | 오픈소스 기반, Firebase 대안, 관계형 DB로 플레이리스트 등 구조화 데이터 관리에 유리 | 초저지연 커스텀 프로토콜 구현 시 자체 서버와 병행 설계가 필요할 수 있음 |

### 클록 동기화/드리프트 보정 로직

- 이 부분은 특정 상용 서비스보다는 **자체 구현**(NTP 유사 알고리즘)이 되는 경우가 많다. 어떤 백엔드를 택하든 이 로직은 별도로 설계해야 한다(`05-sync-architecture.md` 참고).

### 제안 요약

- 저지연 동기화가 최우선 비기능 요구사항인 점을 감안하면, 실시간 계층은 커스터마이징 자유도가 높은 **자체 WebSocket 서버**(Node.js/NestJS 또는 Go) 쪽에 무게가 실리지만, 팀 규모/일정에 따라 관리형 서비스로 초기 MVP를 검증한 뒤 자체 서버로 전환하는 단계적 접근도 합리적인 대안이다.
- 모바일 프레임워크는 React Native/Flutter 모두 실현 가능하나, Spotify App Remote 및 YouTube WebView 브릿지 모두 결국 네이티브 모듈 작성이 필요하므로, "크로스플랫폼으로 얻는 이득"과 "네이티브 SDK 연동 마찰"을 사용자가 팀 상황에 맞춰 저울질해야 한다.
- 이 모든 후보는 제안일 뿐이며, 확정 시 CLAUDE.md의 "기술 스택: 미정" 섹션을 갱신하는 것을 제안한다(리더가 사용자 확인 후 처리).
