## 배경

지금까지의 세션 모델은 "방 하나 = 서비스 하나(Spotify 또는 YouTube)"였다(`01-user-stories.md` US-105, `06-mvp-scope-and-tech-stack.md`). 사용자가 제안한 세 번째 모드는 이 전제를 깨고, **참여자마다 서로 다른 플랫폼에 각자 로그인**할 수 있게 하자는 것이다(예: A는 Spotify, B는 YouTube, C는 멜론). 곡을 세션 플레이리스트에 추가할 때는 특정 플랫폼의 트랙 ID가 아니라 **"제목/아티스트 같은 플랫폼 중립적 식별자"**로 지정하고, 각 참여자의 기기가 자신의 플랫폼에서 그 곡을 검색해 찾은 뒤, 재생 시점(타임코드)을 서비스가 달라도 동일하게 맞추자는 아이디어다.

`05-sync-architecture.md`가 이미 확립한 아키텍처(서버가 "현재 곡 + 기준 시각 + 재생 여부"를 유일한 진실로 갖고, 각 클라이언트는 이를 받아 자신의 로컬 플레이어를 그 위치로 맞추는 "서버 기준 시계" 모델)는 애초에 "오디오 자체를 우리가 스트리밍하지 않는다"는 전제 위에 세워져 있어서, "모든 참여자가 같은 서비스를 쓴다"는 조건 하나만 깨는 것은 이론적으로는 그 연장선에 있다. 다만 이 확장이 실제로 성립하려면 아래 네 가지를 검증해야 한다.

## 요구사항 (검토 대상)

1. **곡 매칭 정확도**: "제목/아티스트"만으로 서로 다른 플랫폼에서 정확히 같은 음원을 특정할 수 있는가. ISRC 같은 업계 표준 식별자가 도움이 되는가.
2. **곡 길이/구조 불일치 시 동기화 파탄 가능성**: 매칭된 두 음원의 실제 재생 길이/구조가 다르면 "같은 시점"이라는 개념이 플랫폼마다 어긋나는데, 이를 감지/보정할 수 있는가.
3. **플랫폼별 재생 제어 재확인**: 이 모드에 참여하는 모든 플랫폼이 "제3자 앱이 그 사용자 인증 세션으로 특정 곡을 정확한 시점부터 재생/탐색"할 수 있어야 한다.
4. **종합 결론**: 기술적으로 실현 가능한지, 가능하다면 어떤 제약 하에서인지, MVP 포함 여부에 대한 권고.

## 조사 결과

### 1) 곡 매칭 정확도 — ISRC 노출 여부

**핵심 발견: Spotify와 YouTube의 ISRC 노출 여부가 비대칭적이다. 이는 이 모드 전체의 실현 가능성을 좌우하는 가장 중요한 사실이다.**

- **Spotify Web API**: Get Track 등 트랙 조회 엔드포인트의 응답에 `external_ids` 객체가 포함되며, 여기에 `isrc`(International Standard Recording Code), `ean`, `upc` 필드가 명시적으로 제공된다(확실성: 높음 — 공식 문서 직접 확인, `developer.spotify.com/documentation/web-api/reference/get-track`). 즉 Spotify 쪽에서는 검색 결과로 얻은 트랙의 ISRC를 프로그래밍적으로 얻을 수 있다.
- **YouTube Data API v3**: `videos` 리소스(및 그 하위 `contentDetails`, `topicDetails`, `snippet` 등 모든 공식 파트)를 대조한 결과, **ISRC나 이에 준하는 업계 표준 음원 식별자를 노출하는 필드는 존재하지 않는다**(확실성: 높음 — 공식 문서 직접 확인, `developers.google.com/youtube/v3/docs/videos`). YouTube가 제공하는 음악 관련 메타데이터는 `topicDetails`의 음악 토픽 ID(장르 수준의 매우 거친 분류)와 업로더가 직접 입력한 `snippet.tags`/제목/설명 텍스트뿐이다.
- 이 비대칭이 의미하는 것: **Spotify 쪽 곡은 ISRC를 정확히 알 수 있지만, YouTube 쪽 영상은 ISRC를 알 방법이 공식 API상 없다.** 따라서 "두 플랫폼에서 얻은 ISRC가 일치하면 같은 음원"이라는 검증 로직 자체를 세울 수 없다 — 비교 대상 중 한쪽의 값을 얻을 수 없기 때문이다.
- 대안으로 검토할 수 있는 것: MusicBrainz 같은 제3의 오픈 메타데이터 데이터베이스가 ISRC ↔ 녹음(recording) 매핑을 제공하지만, 이는 "이 ISRC가 어떤 곡인가"를 알려줄 뿐 "이 ISRC에 해당하는 YouTube 동영상 ID가 무엇인가"까지 알려주지는 않는다(YouTube 영상은 애초에 ISRC 태그를 공개적으로 노출하지 않으므로, 외부 DB와 대조할 "YouTube 쪽 ISRC 값" 자체가 없다). 즉 이 우회로도 근본적 한계를 해결하지 못한다(확인 필요 — MusicBrainz 등 제3 DB의 상세 스펙까지 조사하지는 않았으나, YouTube 쪽에 애초에 대조할 값이 없다는 점은 변하지 않는다).
- **결론**: ISRC는 Spotify↔Spotify 또는 Spotify를 포함하지 않는 두 서비스 간 비교에는 유용할 수 있으나(단, 나머지 서비스도 ISRC를 노출해야 함), **Spotify↔YouTube 조합에서는 ISRC 기반의 정확한 매칭이 원천적으로 불가능하다.** 결국 YouTube 쪽 매칭은 "제목 정규화(특수문자/괄호 표기 제거 등) + 아티스트명 유사도 + 재생 길이 근접도"에 의존하는 **휴리스틱(추정) 매칭**에 머물 수밖에 없다. 이는 사용자가 우려한 대로 "같은 곡이라도 다른 마스터링/에디션(리마스터, 라이브 버전, explicit vs clean, 리전별 인트로 길이 차이 등)"을 구별하지 못하고 잘못된 음원을 매칭할 위험을 그대로 안고 간다.
- 멜론/지니뮤직은 `08-korean-services-melon-genie.md`에서 확인했듯 공식 검색 API 자체가 없으므로, ISRC는커녕 제목/아티스트 메타데이터조차 프로그래밍적으로 얻을 공식 수단이 없다 — 애초에 이 모드에 참여할 방법이 없다(3절에서 재확인).

### 2) 곡 길이/구조 불일치 시 동기화 파탄 가능성

- 매칭 정확도가 근본적으로 휴리스틱에 의존한다는 1)의 결론 때문에, 두 참여자가 "같은 곡"이라고 서버가 판단한 트랙이라도 실제로는 다른 에디션(예: 스튜디오 버전 vs 라이브 버전, 3:45 vs 4:12 리믹스)일 가능성을 배제할 수 없다.
- **감지 가능한 수준의 안전장치**: Spotify는 `duration_ms`, YouTube는 `contentDetails.duration`(ISO 8601)으로 각각 재생 길이를 제공한다(둘 다 확실성 높음, 기존 공식 문서 기준 필드). 두 값의 차이가 임계값(예: 2~3초, 정확한 값은 실측 필요)을 넘으면 "다른 에디션일 가능성이 높다"고 판단해 매칭을 거부하거나 사용자에게 확인을 요구하는 최소한의 방어선을 세울 수 있다.
- **그러나 길이가 정확히 일치해도 구조가 다를 수 있다.** 예를 들어 인트로를 2초 잘라내고 아웃트로를 2초 늘린 편집판은 전체 길이는 같지만 "3분 지점"이 가리키는 실제 소절이 서로 다르다. 이런 경우는 길이 비교만으로는 감지할 수 없고, 오디오 핑거프린팅(예: Chromaprint/AcoustID 같은 기술) 수준의 검증이 필요한데, 이는 (a) 오디오 스트림 자체에 접근할 수 없는 이 프로젝트의 아키텍처(`05-sync-architecture.md`, "우리는 오디오를 직접 다루지 않는다"는 전제)와 정면으로 충돌하고, (b) 설령 접근한다 해도 별도의 대규모 기술 스택 투입이 필요해 MVP 범위를 크게 벗어난다.
- **결론**: 길이 비교는 "명백히 다른 곡/에디션"을 걸러내는 최소 방어선은 될 수 있지만, "길이는 같으나 구조가 미세하게 다른" 케이스까지 완전히 잡아낼 방법은 이 프로젝트의 기존 아키텍처 안에서는 없다. 즉 크로스플랫폼 혼합 모드는 **본질적으로 동일 플랫폼 모드보다 구조적으로 더 큰 동기화 오차 리스크를 안고 간다** — 이는 구현으로 없앨 수 있는 리스크가 아니라 두 개의 독립된 음원 파일을 다루는 데서 오는 근본적 한계다.

### 3) 플랫폼별 재생 제어 재확인

| 플랫폼 | 원격 재생 제어 가능 여부 | 근거 문서 |
|---|---|---|
| Spotify | 가능 (App Remote SDK, 전원 Premium 필요) | `02-spotify-integration.md` |
| YouTube | 가능 (WebView + IFrame Player API, 광고 노출 리스크는 별개 이슈) | `03-youtube-integration.md` |
| 멜론/지니뮤직 | **불가능** — 서드파티용 공식 재생 제어 API/SDK 자체가 없음(과거 멜론의 검색 API도 2018년 종료, 지니뮤직은 애초에 공식 API 없음) | `08-korean-services-melon-genie.md` |

- Spotify와 YouTube는 이미 각자 조사 완료된 대로 재생 제어 자체는 기술적으로 가능하다. 이 두 서비스만 놓고 보면 "플랫폼별 재생 제어"라는 전제조건은 충족된다.
- **멜론/지니뮤직은 이 모드에 참여할 수 없다** — 재생 제어 API가 없다는 것은 곧 "우리 앱이 그 사용자의 인증 세션으로 특정 곡을 특정 시점부터 재생시키는 것" 자체가 불가능하다는 뜻이다. 사용자가 예시로 든 "C는 멜론"이라는 시나리오는 08 문서의 결론에 따라 **현재는 성립할 수 없다.**
- 따라서 크로스플랫폼 혼합 모드가 지금 시점에 실제로 구성 가능한 조합은 **Spotify 참여자 + YouTube 참여자의 혼합뿐**이다. 멜론/지니가 참여하려면 08 문서의 결론(공식 연동 채널 자체 없음)이 먼저 바뀌어야 하며, 이는 이 프로젝트의 통제 밖에 있는 전제(멜론/지니의 정책 변경 또는 공식 파트너십 체결)에 달려 있다.

### 4) 종합 — 기술적 실현 가능성 판단

**결론: Spotify-YouTube 조합에 한해 "조건부로 기술적 실현 가능"하다고 판단한다. 다만 동일 플랫폼 모드 대비 매칭 정확도와 동기화 정밀도가 구조적으로 떨어지는 리스크를 안고 있다.**

성립 조건(권고, 확정 아님):
1. **참여 가능 플랫폼 조합은 현재 Spotify ↔ YouTube 두 가지뿐**이다. 멜론/지니는 08 문서 결론에 따라 제외한다.
2. 곡 매칭은 "제목/아티스트 유사도 매칭 + 재생 길이 오차 허용 임계값(예: ±2~3초, 실측 후 확정)" 조합으로 처리하되, **ISRC로 100% 검증하는 것은 Spotify↔YouTube 조합에서는 불가능하다**(YouTube가 ISRC를 노출하지 않으므로)는 한계를 제품적으로 인정해야 한다.
3. 매칭 신뢰도가 근본적으로 완전하지 않으므로, **각 참여자에게 "이 곡이 맞습니까?"라는 확인 단계를 최소 한 번은 거치게 하는 것을 권고**한다(자동 매칭 결과를 사용자가 검수하지 않고 그대로 재생에 들어가면, 잘못된 음원이 재생되는 사고가 발생했을 때 사용자가 원인을 이해하기 어렵다). 이 UX의 구체적 형태는 디자인 단계 몫이다.
4. 동기화 정밀도는 "완전히 같은 음원을 같은 플랫폼에서 재생하는" 기존 모델보다 태생적으로 더 나쁠 수 있다는 점을 제품 기대치 관리 차원에서 사용자에게 투명하게 고지해야 한다(기존 US-406의 "완전한 서버 스트리밍이 아니다"는 고지 원칙의 연장선으로 볼 수 있다).
5. 아키텍처 관점에서는 `05-sync-architecture.md`의 "서버 기준 시계" 모델을 그대로 재사용할 수 있다 — 서버는 "플랫폼 중립적 곡 식별자(제목/아티스트/길이 등 메타데이터 묶음)"를 플레이리스트 항목으로 갖고, 각 참여자의 클라이언트가 그 메타데이터로 자기 플랫폼에서 검색해 매칭된 트랙 ID를 로컬에 보관한 뒤, 서버가 브로드캐스트하는 "기준 위치"를 자신의 로컬 트랙 길이 기준으로 환산해 seek하면 된다. 즉 아키텍처를 근본적으로 새로 설계할 필요는 없으나, "플레이리스트 항목 = 플랫폼 중립 메타데이터"와 "참여자별 매칭된 플랫폼 트랙 ID"를 분리해서 관리하는 데이터 모델이 추가로 필요하다(개념 수준, 상세 스키마는 구현 단계 몫).

## 결정 갱신 (2026-07-23) — 사용자가 MVP 포함으로 결정, 위 옛 권고를 대체

> 위 "권고" 절(2026-07-23 최초 작성)은 "매칭 신뢰도가 원천적으로 불완전하다"는 리스크(1·2절)를 근거로 MVP 이후 스파이크로 미룰 것을 제안했다. **사용자는 이 권고를 검토한 뒤 뒤집고, 혼합 모드를 지금 MVP에 옵션으로 포함하기로 결정했다.** 단, 그 조건으로 "매칭 리스크를 없애는 것"이 아니라 **"매칭 리스크를 사용자에게 투명하게 고지하고, 사용자가 직접 확인/수정하게 한다"**는 처리 방식을 함께 결정했다. 즉 1·2절이 밝힌 "휴리스틱 매칭은 근본적으로 불완전하다"는 사실 자체는 부정되지 않았고, 그 불완전함을 제품이 감추지 않고 드러내는 방향으로 리스크 대응 전략이 정해진 것이다.

### 결정 1 — 세션 생성 시 세 번째 옵션으로 혼합 모드 포함

- 세션(방) 생성 화면에서 호스트는 다음 **세 가지 세션 유형 중 하나**를 선택한다 (기존 `06-mvp-scope-and-tech-stack.md`/`01-user-stories.md` US-105의 "Spotify 또는 YouTube 택1" 라디오 버튼에 세 번째 옵션이 추가되는 형태):
  1. **Spotify 전용** — 참여자 전원이 Spotify로 참여(기존 정책 유지, 전원 Premium 필요).
  2. **YouTube 전용** — 참여자 전원이 YouTube로 참여(기존 정책 유지).
  3. **혼합(Mixed)** `(신규, MVP)` — 참여자마다 각자 Spotify 또는 YouTube 중 자신이 로그인한 플랫폼으로 참여. 멜론/지니뮤직은 `08-korean-services-melon-genie.md` 결론(공식 연동 채널 자체 없음, 재검토 대상 아님)에 따라 여전히 참여 불가하므로, **혼합 모드는 실질적으로 "세션 안에 Spotify 참여자와 YouTube 참여자가 공존하는" 조합**을 의미한다.
- 혼합 모드에서 곡을 세션 플레이리스트에 추가할 때는 특정 플랫폼의 트랙 ID가 아니라 **"제목/아티스트"라는 플랫폼 중립적 식별자**로 등록된다(상세 구조는 `04-playlist.md` "혼합 모드 플레이리스트 구조" 절 참고). 각 참여자의 클라이언트는 이 식별자로 자신의 플랫폼에서 곡을 검색해 매칭하고, 매칭된 트랙으로 서버가 브로드캐스트하는 "기준 위치"에 맞춰 로컬 재생을 조율한다(5절에서 이미 정리한 아키텍처, 변경 없음).

### 결정 2 — 매칭 결과 명시적 고지 + 사용자 확인/수정 UI 필수 (기능 요구사항)

이 요구사항은 혼합 모드를 MVP에 포함하기 위한 **전제조건**이며, 생략 불가능한 기능으로 명시한다.

1. **매칭 자동 실행 후 조용히 재생하는 방식은 채택하지 않는다.** 참여자가 (자신이 직접 곡을 추가했든, 다른 참여자가 추가한 플랫폼 중립 곡 식별자를 자신의 플랫폼에서 매칭받든) 실제 재생에 들어가기 전에, 자신의 화면에서 "이 곡을 [플랫폼]에서 이렇게 찾았어요"라는 매칭 결과를 반드시 확인해야 한다.
2. **매칭 결과 표시 항목(개념 수준)**:
   - 매칭된 트랙의 제목/아티스트/앨범(또는 채널)/썸네일/재생 길이.
   - **일치율(신뢰도) 수치 또는 등급** — 예: "일치율 92%" 또는 "높음/중간/낮음" 같은 단순 등급. 정확한 계산 공식은 구현 단계 몫이나, 개념적으로는 다음 요소들의 조합으로 산출하는 방향을 제안한다:
     - 제목 문자열 유사도(정규화 후 편집 거리/토큰 유사도 등)
     - 아티스트명 일치 여부(가중치를 가장 높게 부여할 것을 제안 — 동명이곡 오매칭 방지에 특히 중요)
     - 재생 길이 오차(2절에서 다룬 "길이 임계값" 방어선을 신뢰도 점수의 한 축으로 재사용)
   - 일치율이 임계값(예: 낮음/불확실 등급) 이하인 경우, "확인 필요" 같은 경고 문구를 강조 표시해 사용자가 그냥 넘기지 않도록 유도하는 것을 제안한다(구체적 임계값/문구는 디자인 단계 몫).
3. **사용자 확인/수정 UI**: 참여자는 자동 매칭 결과를 다음 중 하나로 처리할 수 있어야 한다.
   - **확정(그대로 사용)** — 표시된 매칭 결과가 맞으면 그대로 승인.
   - **직접 재검색/재선택** — 자동 매칭이 틀렸다고 판단되면, 참여자가 직접 자신의 플랫폼에서 곡을 검색해 원하는 트랙으로 수동 교체할 수 있어야 한다(기존 "곡 검색 및 추가" 기능, `04-playlist.md`을 재사용).
   - 이 확인은 **참여자별로 각자 수행**한다 — 혼합 모드는 애초에 참여자마다 서로 다른 플랫폼/트랙을 매칭하므로, 한 사람이 확인했다고 다른 참여자의 매칭까지 자동 확정되지 않는다.
4. 이 요구사항은 `01-user-stories.md`에 신규 User Story(매칭 확인 UI)로, UI/UX 상세 설계는 디자인 에이전트 몫으로 넘긴다(기획 단계에서는 "무엇을 보여주고 무엇을 조작할 수 있어야 하는가"까지만 규정).
5. 2절에서 다룬 "길이는 같으나 구조가 다른 편집판" 같은, 신뢰도 점수로도 못 잡아내는 잔여 리스크는 이 확인 UI로도 100% 제거되지 않는다 — 다만 "사용자가 스스로 확인했다"는 사실 자체가, 잘못된 매칭이 재생됐을 때 "왜 이런 일이 생겼는지 이해할 수 없는" 상황을 막아주는 최소한의 신뢰 장치로 기능한다는 것이 이번 결정의 취지다.

### 결정 3 — 기존 "서비스별 플레이리스트 독립 보존"(택1 후 전환) 모델과의 관계 정리

`06-mvp-scope-and-tech-stack.md`/`01-user-stories.md`(US-105b/US-105c/US-308)/`04-playlist.md`가 이미 규정한 기존 모델과 혼합 모드는 **서로 다른 축의 기능이며, 구조적으로 다르다.** 혼동하지 않도록 명확히 구분한다.

| 구분 | 기존 모델("택1 후 전환", Spotify 전용/YouTube 전용 세션) | 혼합 모드(신규) |
|---|---|---|
| 한 세션에서 동시에 활성화되는 서비스 수 | **항상 1개** — Spotify 또는 YouTube 중 하나만 "현재 활성" 상태 | **참여자 수만큼 동시에 여러 개** — 같은 세션 안에서 Spotify 활성 참여자와 YouTube 활성 참여자가 **동시에** 존재 |
| 서비스 전환의 의미 | 세션 도중 활성 서비스를 A→B로 "바꾸는" 것(전환 순간 재생 중단, US-105b) | 전환 개념 자체가 없다 — 애초에 여러 서비스가 동시에 활성 상태이므로 "바꿀" 대상이 없음 |
| 플레이리스트 구조 | **세션 1 : 서비스별 플레이리스트 N(N=2)** — Spotify용/YouTube용 플레이리스트가 각각 독립적으로 존재하고, 비활성 쪽은 재생 동기화 대상에서 빠진 채 데이터만 보존됨 | **세션 1 : 플레이리스트 1(플랫폼 중립)** — 곡 항목이 "제목/아티스트"라는 공통 식별자를 갖고, 그 아래 참여자별로 실제 매칭된 플랫폼 트랙이 매핑되는 구조(상세는 `04-playlist.md` 참고). 플레이리스트 자체를 서비스별로 나눌 필요가 없다 — 하나의 목록을 모두가 공유하되, 각자 다른 플랫폼에서 재생할 뿐이다. |
| 곡 식별자 | 서비스별 고유 ID(Spotify track URI 또는 YouTube videoId)를 그대로 사용, 두 서비스 간 통합 시도하지 않음(`04-playlist.md` 제약/리스크 절, 2026-07-23 갱신 내용 참고) | 플랫폼 중립 메타데이터(제목/아티스트/길이 등)를 1차 식별자로 쓰고, 참여자별 매칭 트랙 ID는 그 아래 종속 정보로 관리 — **의도적으로 곡 식별자를 통합 추상화하는 유일한 케이스** |
| 동기화 기준 | 활성화된 하나의 서비스 기준으로만 동기화(비활성 서비스는 동기화 대상 아님) | 서버는 여전히 "플랫폼 중립 기준 위치(경과 시간)"만 브로드캐스트하고, 각 참여자 클라이언트가 이를 자신이 매칭한 트랙의 길이 기준으로 환산해 seek — 5절에서 정리한 아키텍처 그대로 |
| 세션 생성 시 선택 | Spotify 또는 YouTube 중 하나 | 혼합(세 번째 옵션) — 선택 시점에 특정 서비스로 고정하지 않음 |

- 요약하면, 기존 모델은 "한 번에 하나의 서비스, 다만 갈아탈 수 있다"는 **직렬(순차)** 구조이고, 혼합 모드는 "처음부터 여러 서비스가 동시에" 쓰이는 **병렬(동시)** 구조다. 두 모델은 상호 배타적인 세션 유형 선택지이며(결정 1의 세 옵션 중 하나만 고를 수 있음), 한 세션이 "택1 후 전환" 모드와 "혼합" 모드를 동시에 가질 수는 없다.
- 데이터 모델 관점에서도 두 모델은 서로 다른 스키마를 요구한다 — 기존 모델은 "세션+서비스 타입" 키로 플레이리스트를 복수 개 두지만, 혼합 모드는 플레이리스트는 하나이되 그 안의 각 곡 항목이 "참여자별 매칭 트랙 맵"이라는 하위 구조를 갖는다(상세는 `04-playlist.md` 참고, 스키마 자체는 구현 단계 몫).

### 결정 4 — 잔여 리스크 및 후속 권고 (기획 에이전트 의견)

- 1·2절의 조사 결론(YouTube ISRC 미노출로 인한 매칭 원천적 불완전성, 구조가 다른 편집판 감지 불가)은 사용자의 이번 결정으로 사라지지 않는다. 다만 이제는 "제품이 이 불완전성을 사용자에게 숨기지 않는다"는 방향으로 리스크를 다루기로 했으므로, 기술적 한계 자체는 여전히 존재한다는 점을 구현/디자인 단계에서도 계속 유의해야 한다.
- 매칭 신뢰도 점수 산출 알고리즘의 구체적 가중치·임계값은 근거 없이 확정하지 않는다 — 실측 스파이크(다양한 곡 표본으로 매칭 성공률/오매칭률 측정)를 구현 착수 전 또는 초기 스프린트에서 수행할 것을 다시 한번 권고한다(옛 권고에서 제안했던 실측 필요성은 MVP 포함 여부와 무관하게 여전히 유효하다).
- 혼합 모드는 세 세션 유형 중 하나로 추가되는 것이므로, 구현/검증 단계에서 QA 대상이 "Spotify 전용/YouTube 전용/혼합" 세 갈래로 늘어난다는 점을 검증 에이전트에게 미리 알릴 것을 리더에게 제안한다.
