# 매칭 신뢰도 가중치/임계값 벤치마크 (오프라인 합성 케이스 기반)

> 상태: v1 — 2026-07-26. `docs/roadmap.md` "매칭 신뢰도 가중치/임계값 실측 스파이크" 항목,
> `docs/specs/09-cross-platform-mixed-mode.md` "결정 4" 후속.
> **주의: 이 문서는 실제 Spotify/YouTube 라이브 API 데이터로 측정한 "실측"이 아니다.** 아래 "방법"
> 절에서 실측이 불가능했던 이유와, 대신 채택한 오프라인 합성 벤치마크 방법을 명확히 밝힌다.

## 배경 / 질문

혼합(Mixed) 세션의 곡 매칭 로직(`apps/mobile/src/services/matching/trackMatcher.ts`)은 제목 유사도
(Levenshtein, 정규화 후) × 0.35 + 아티스트 일치 × 0.45 + 길이 근접도 × 0.2 가중합으로 0~100점을 산출하고,
high(≥85)/medium(≥60)/low 세 등급으로 나눈다. 이 값들은 구현 당시 "실측 없이 합리적으로 보이는 기본값"으로
잠정 채택되었고(`docs/agents/implementation-log.md` 혼합 모드 구현 로그, 09문서 결정 4), 09문서는 "실측
스파이크 이후 확정"을 권고해두었다.

질문: 현재 가중치(0.35/0.45/0.2)와 임계값(high 85 / medium 60)이 09문서가 우려한 구체적 실패 케이스들
(동명이곡, 리마스터/라이브 버전, 표기 차이, 피처링 아티스트, 리믹스/에디트 등)에 대해 상식적으로 기대되는
등급을 산출하는가? 조정이 필요해 보이는 지점이 있는가?

## 방법

### 왜 실제 API 실측이 이 환경에서 불가능한가

- **Spotify**: `trackMatcher.ts`가 실제로 호출하는 `searchSpotifyTracks`는 Authorization Code + PKCE로 얻은
  사용자 accessToken이 필요하다(실기기 브라우저 로그인 플로우). 이 환경에는 그런 세션이 없다.
  대안으로 Client Credentials Flow(앱 전용 토큰, 로그인 불필요)를 시도해봤다 — 실제로
  `https://accounts.spotify.com/api/token`에 `grant_type=client_credentials`로 POST 요청을 보냈다:

  ```
  curl -s -X POST https://accounts.spotify.com/api/token \
    -d "grant_type=client_credentials&client_id=4b076092ea1b4f8e9d41b7eaec85920a"
  → {"error":"invalid_client"}  (HTTP 400)
  ```

  `apps/mobile/src/config/env.ts`/`.env.example`을 확인한 결과 이 프로젝트는 `SPOTIFY_CLIENT_ID`만 보유하고
  Client Secret은 애초에 발급/보관하지 않는다(PKCE 플로우는 Secret이 필요 없는 게 정상이라 의도된 설계다).
  Client Credentials Flow는 Secret이 필수라 위 요청은 예상대로 `invalid_client`로 거부됐다 — **이 환경에서
  Spotify 라이브 검색 API를 어떤 방식으로도 호출할 수 없음을 실제로 확인했다.**
- **YouTube**: `searchYoutubeTracksMock`(`apps/mobile/src/services/youtube/youtubeMockSearch.ts`)은 정적 목업
  카탈로그 5곡뿐이라 "동명이곡", "리마스터", "피처링 표기 차이" 같은 다양한 실패 케이스 표본을 구성할 수
  없다. YouTube Data API v3 실키 연동도 이번 라운드 범위 밖으로 이미 보류돼 있다(목업 파일 주석 참고).

결론: 09문서가 원래 의도한 "다양한 곡 표본으로 실제 검색 API 매칭 성공률/오매칭률을 측정"하는 실측은 이
환경에서 불가능하다. **실측을 재개하려면 (a) Spotify는 실기기/브라우저에서 PKCE 로그인으로 사용자
accessToken을 발급받거나, (b) YouTube는 Data API v3 키를 발급받아 `youtubeMockSearch.ts`를 실제 검색으로
교체해야 한다.** 둘 다 계정/키 발급이라는 사용자 액션이 선행돼야 하는 항목이다.

### 대신 채택한 방법 — 오프라인 합성 벤치마크

`trackMatcher.ts`의 순수 함수(정규화, Levenshtein, 아티스트 일치, 길이 점수, 가중합)를 **코드 변경 없이
그대로 복사**한 스크립트(`scratchpad/benchmark.js`, 이 세션의 임시 파일 — 프로덕션 코드 아님)를 만들어,
09문서가 명시한 실패 케이스 카테고리별로 "원본 vs 변형" 쌍 20건을 합성해 실제로 점수를 계산했다.

이 방법의 명확한 한계:
- 실제 Spotify/YouTube 검색 결과 텍스트가 아니라 사람이 손으로 구성한 예시라, 실제 플랫폼들이 제목/아티스트
  필드를 어떻게 포맷하는지의 통계적 분포(예: "몇 %가 대시로 에디션을 표기하는지")를 반영하지 못한다.
- 표본 수(20건)가 통계적 유의성을 가질 만큼 크지 않다 — "성공률/오매칭률" 같은 수치가 아니라 "카테고리별
  대표 사례가 상식과 부합하는가"만 확인할 수 있다.
- 따라서 이 문서의 결과는 **"현재 알고리즘의 동작을 코드 수준에서 검증했다"**는 의미이지, **"실제 사용자
  환경에서 매칭이 몇 % 성공한다"**는 의미가 아니다.

## 관찰 (기존 단위 테스트와 겹치지 않는 새 발견 중심)

1. **괄호 밖 대시(` - `) 표기의 에디션 접미사는 정규화되지 않는다.** `normalizeTitle`은
   `[[({][^\])}]*[\])}]` 정규식으로 **괄호/대괄호/중괄호 안의 내용만** 제거한다. `"Sunset Drive -
   Remastered"`처럼 대시로 구분된 접미사는 그대로 남아 title 유사도가 1.00 → 0.52로 크게 떨어진다. YouTube
   업로드는 `"곡명 - Remastered"`, `"곡명 - Live"`, `"곡명 - Radio Edit"`처럼 괄호 없이 대시를 쓰는 관행이
   드물지 않아(채널마다 다르지만), 이 경우 원래 high로 잡혔어야 할 완전 동일곡이 medium(78/70점)으로
   떨어질 수 있다. 기존 단위 테스트(`trackMatcher.test.ts`)는 `"(Live)"`/`"- Topic"`(아티스트 쪽)만 다뤄서
   **제목 쪽 대시 접미사 케이스는 커버되지 않았다.**

2. **길이 차이가 작은 라이브 버전은 구분이 안 된 채 high로 분류된다.** `"(Live)"` 태그가 괄호 안에 있으면
   제목에서 완전히 지워지므로, 실제로는 다른 레코딩(라이브 vs 스튜디오)인데도 길이가 우연히 비슷하면(이
   케이스는 3초 차이) title 1.0 + artist 1.0 + duration 0.75(≤5초 구간) = 95점으로 **high** 등급을 받는다.
   `DURATION_MISMATCH_NOTICE_THRESHOLD_SEC`(5초)보다도 짧은 차이라 "길이가 조금 달라요" 안내 배너도 뜨지
   않는다 — 즉 사용자에게 "이건 라이브 버전일 수 있다"는 신호가 점수로도, 안내 문구로도 전혀 전달되지
   않는다. 이는 09문서 2절이 이미 원론적으로 지적한 "길이는 같은데 구조가 다른 편집판은 못 잡는다"는
   한계의 구체적 발현 사례다 — 라이브 버전 태그 자체가 정규화 과정에서 지워지기 때문에, 애초에 "제목에
   Live라는 신호가 있었다"는 정보 자체가 점수 계산에 전달되지 않는다.

3. **피처링/협업 표기 차이는 기대보다 낮은 medium(82점)에 머문다.** 09문서가 "동명이곡 오매칭 방지"를
   위해 아티스트 가중치를 가장 높게 두라고 권고한 것은 타당하지만, 그 결과로 부분 일치(0.6)가 발생하는
   feat./`&` 협업 표기 차이 — 실제로는 "같은 곡"일 확률이 매우 높은 흔한 케이스 — 가 100×0.35 + 60×0.45 +
   100×0.2 = 82점으로, high 임계값(85)에 3점 못 미쳐 medium으로 분류된다. 사용자 입장에서는 "제목도
   완벽히 같고 아티스트도 사실상 같은데 왜 medium이지?"라고 느낄 수 있는 케이스다. medium이어도 매칭
   결과 자체는 후보 목록에 오르고 사용자가 확인 UI에서 승인하면 되므로 기능이 막히는 것은 아니지만
   ("확인 필수" 정책, 09문서 결정 2), 등급 표시가 실제 신뢰도보다 낮게 느껴질 수 있다는 점은 UX 관점에서
   참고할 만하다.

4. **핵심 안전장치(동명이곡 + 완전히 다른 아티스트)는 잘 작동한다.** 제목·길이가 완벽히 같아도 아티스트가
   전혀 겹치지 않으면(부분 포함도 없음) 100×0.35 + 0 + 100×0.2 = 55점으로, medium 임계값(60)보다 낮은
   low로 확실히 떨어진다. 이는 "아티스트가 0점이면 제목·길이가 만점이어도 medium 문턱을 절대 넘지
   못하도록" 하는 여유(60 - 55 = 5점)가 현재 가중치 조합에 실제로 내장돼 있다는 뜻이며, 09문서가 가장
   우려한 "동명이곡 오매칭" 시나리오에 대한 방어가 수치적으로 확인됐다. **이 부분은 조정 불필요, 현재
   가중치 유지를 권장한다.**

5. **아티스트 부분 일치(`includes()`) 로직은 짧은 이름의 우연한 substring에도 관대하다.** `artistMatchScore`는
   한쪽 문자열이 다른 쪽에 포함되면 무조건 0.6을 준다. `"Neon"`이 `"Neon Bay"`의 부분 문자열이라는 이유만으로
   (실제로 동일 아티스트의 축약 표기일 수도, 우연히 겹치는 전혀 다른 아티스트일 수도 있음을 구분하지 못한 채)
   0.6이 부여돼, 동명 제목과 결합하면 82점(medium)까지 올라간다. 관찰 4의 "안전 마진(5점)"은 아티스트가
   완전히 0점일 때만 유효하고, 부분 일치(0.6)가 발생하면 그 마진이 사라진다. 다만 이 위험은 09문서 결정
   2("모든 매칭은 사용자가 최종 확인")로 제품 차원에서 어느 정도 상쇄된다는 점도 함께 기록해둔다.

6. **길이가 극단적으로 다른 리믹스/에디트도 duration 가중치(0.2)만으로는 medium 밑으로 떨어지지 않는다.**
   `(Extended Mix)`처럼 150초나 차이 나 duration 점수가 0이 되어도, title·artist가 만점이면 100×0.35 +
   100×0.45 + 0 = 80점으로 여전히 medium을 유지한다. 이는 "duration 가중치가 낮아서 문제"라기보다 애초에
   "제목·아티스트가 같으면 에디션이 달라도 넓은 의미에서 매칭 후보로는 보여준다"는 설계 의도(사용자가 직접
   확인/재검색하게 함)와 부합하는 결과로 볼 수 있다. 다만 이 케이스들은 전부
   `shouldShowDurationMismatchNotice`(≥5초)의 안내 배너가 함께 뜨므로, "점수만 보면 medium인데 별도 경고
   문구로 보완된다"는 점이 함께 작동하고 있음을 확인했다 — 관찰 2(라이브, 3초 차이)와 대비되는 지점이다.

## 참고용 권고 (결정 아님 — 리더/사용자 검토 대상)

- **현재 가중치(artist 0.45 / title 0.35 / duration 0.2)의 핵심 설계 의도(아티스트 최우선, 동명이곡 방어)는
  이 벤치마크에서 유효하게 검증됐다** — 아티스트 완전 불일치 시 55점으로 medium 문턱 아래 확실히 떨어진다.
  이 부분은 조정 없이 유지를 권장한다.
- **관찰 1(대시 접미사 미정규화)**: `normalizeTitle`에 "괄호 밖" 흔한 에디션 키워드(`remaster`, `remastered`,
  `live`, `acoustic`, `radio edit`, `deluxe`, `mono`, `stereo`, `remix`, `version`, `edit` 등)를 대시/파이프
  구분자 뒤에서도 제거하는 보조 정규화 단계를 추가하는 방향을 검토해볼 만하다. 다만 이 목록 자체가 "무엇을
  같은 곡으로 볼지"에 대한 제품적 판단(관찰 2와 직결)이 필요해, 알고리즘만 손보기 전에 "라이브/리믹스도
  같은 곡으로 취급할 것인가"라는 09문서 결정 4의 미해결 질문을 먼저 정리하는 게 순서상 맞아 보인다.
- **관찰 2(라이브 버전이 high로 분류되는 문제)**: 이건 가중치 조정만으로 해결되지 않는다 — "라이브"라는
  신호 자체가 정규화 단계에서 지워지기 때문이다. 만약 "라이브/리믹스 등은 스튜디오 버전과 구분해서 낮은
  등급으로 보여줘야 한다"는 제품 방향이 맞다면, 정규화에서 에디션 키워드를 지우기 전에 "감지된 키워드가
  있었다"는 사실 자체를 별도 페널티(예: duration 근접도와 무관하게 -10~15점, 또는 별도 배지 표시)로
  남기는 구조 변경이 필요하다 — 이는 가중치 숫자 조정이 아니라 알고리즘 구조 변경에 가까운 제안이라, 채택
  여부는 리더/사용자 판단에 맡긴다.
- **관찰 3(feat./협업 표기가 medium에 머무는 문제)**: high 임계값을 85→80 정도로 낮추거나, 아티스트 부분
  일치 점수를 0.6→0.7 정도로 올리는 두 가지 대안이 있다. 다만 두 대안 모두 관찰 5(우연한 substring
  오탐)의 위험을 함께 키운다는 트레이드오프가 있어, 어느 쪽이든 "확인 UI가 이미 있으니 medium도 충분하다"는
  현상 유지 판단과 병행 검토가 필요하다. 스파이커 관점에서는 셋 중 어느 것이 맞다고 단정하지 않는다.
- **관찰 5(substring 부분 일치의 오탐 위험)**: `includes()` 기반 부분 일치를 토큰 단위 비교로 바꾸는 것만으로는
  근본 해결이 안 된다("Neon"은 "Neon Bay"의 실제 토큰이기도 하다). 문자열 휴리스틱만으로는 "축약 표기"와
  "우연한 겹침"을 구분할 수 없다는 게 이 벤치마크의 결론이다 — 09문서 결정 2가 이미 채택한 "사용자 최종
  확인" UX가 이 잔여 리스크의 실질적 방어선이라는 점을 재확인했을 뿐, 알고리즘 자체의 조정 여지는 제한적이다.
- **관찰 6(극단적 길이 차이의 duration 가중치)**: 현재 동작(title/artist 만점이면 duration 0이어도 medium
  유지 + 별도 안내 배너)이 "매칭 후보는 보여주되 경고로 보완한다"는 09문서 결정 2의 설계 의도와 부합해
  보여, **조정 불필요 의견**을 제시한다.
- 종합하면 이번 벤치마크에서는 "가중치 숫자를 당장 바꿔야 한다"는 강한 근거는 나오지 않았고(관찰 4·6은
  오히려 현재 값이 잘 작동함을 뒷받침), 대신 **정규화 로직의 사각지대(대시 접미사, substring 부분 일치)와
  구조적 한계(라이브 버전 신호 손실)**가 더 명확한 개선 지점으로 드러났다. 이 스파이크의 최종 권고는
  "가중치는 우선 유지하되, 관찰 1·2를 반영한 정규화 로직 보강을 다음 구현 라운드에서 검토할 것을
  제안한다"는 쪽이다 — 다만 최종 채택 여부는 리더/사용자 결정 사항이다.

## 실측 API 데이터로 재검증이 필요한 이유와 방법

이 벤치마크는 사람이 상상해 만든 예시일 뿐, 실제 Spotify/YouTube 검색 결과가 제목/아티스트를 어떻게
포맷하는지의 실제 분포를 반영하지 않는다. 특히 다음은 합성 케이스로는 확인할 수 없다:

- 실제 YouTube 업로드 제목에서 "대시 접미사"(관찰 1) 패턴이 얼마나 흔한지(추정으로만 "드물지 않다"고 썼을
  뿐 비율을 모른다).
- Spotify 검색 API가 feat. 아티스트를 `artists` 배열 여러 항목으로 분리해 반환하는지, 아니면 문자열에
  합쳐서 반환하는지(`artist.map(a => a.name).join(', ')` 코드가 있는 것으로 보아 쉼표로 합쳐 반환하는 것으로
  보이나, 실제 응답 예시로 확인한 것은 아니다) — 이에 따라 관찰 3의 실제 발생 빈도가 달라진다.
- 실제 오매칭(false positive) 사례가 관찰 5 같은 substring 케이스에서 실제로 몇 % 빈도로 발생하는지.

재검증하려면:
1. **Spotify**: 실기기(iOS/Android)에서 앱을 통해 실제 사용자 계정으로 PKCE 로그인해 accessToken을 발급받고,
   `searchSpotifyTracks`를 다양한 쿼리(동명이곡이 실제로 존재하는 아티스트 목록 등)로 호출해 응답 포맷을
   수집한다. 계정 로그인이라는 사용자 액션이 선행 조건이다.
2. **YouTube**: Google Cloud Console에서 YouTube Data API v3 키를 발급받아 `youtubeMockSearch.ts`를 실제
   `search.list` + `videos.list` 호출로 교체(이미 파일 내 TODO로 명시돼 있음)한 뒤, 같은 쿼리 세트로 응답
   포맷을 수집한다. API 키 발급이 선행 조건이다.
3. 두 플랫폼에서 같은 곡 20~50개(동명이곡 포함, 리마스터/라이브 있는 곡 포함)를 검색해 실제 응답을 이
   벤치마크 스크립트에 입력하고, 카테고리별 점수 분포를 다시 관찰한다.
4. 이 실측이 가능해지면 관찰 1·3의 "실제 빈도"를 확인해 정규화 로직/가중치 조정의 우선순위를 정할 수 있다.
