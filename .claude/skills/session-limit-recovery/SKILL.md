# session-limit-recovery

## 왜 이 스킬이 필요한가 (한계 인정)

**계정 API 세션(사용량) 한도는 사전 경고 없이 갑자기 걸린다** — Claude Code 훅(hook) 시스템에는 "사용량 N% 도달" 같은 이벤트가 없다(`PreToolUse`/`PostToolUse`/`PreCompact`/`Stop` 등은 전부 다른 종류의 이벤트다). 그래서 "한도의 95%에서 미리 멈춘다"는 건 기술적으로 불가능하다 — 할 수 있는 건 **한도에 걸려서 에이전트가 죽은 뒤, 그 실패를 빠르고 정확하게 수습하는 것**뿐이다. 이 스킬은 그 사후 대응 루틴이다.

## 트리거

다음 중 하나를 감지하면 이 스킬을 따른다:
1. 백그라운드 서브에이전트의 `<task-notification>`에서 `status: "failed"`이고, summary/result에 `session limit`, `rate limit`, `사용량 한도`, `hit your session limit` 등 한도 관련 문구가 있을 때.
2. 리더(메인 세션) 자신이 도구 호출 중 비슷한 한도 오류를 직접 받았을 때.

## 절차

1. **새 작업 분배를 잠시 멈춘다** — 같은 한도를 공유하는 다른 서브에이전트를 새로 dispatch하지 않는다(거의 확실히 같이 실패한다). 이미 실행 중인 다른 백그라운드 에이전트는 그대로 둬도 된다(별도로 각자 실패/성공할 것).
2. **`git status --short`로 워킹트리를 확인한다** — 죽은 에이전트가 파일을 실제로 얼마나 썼는지 확인한다(도구 호출로 이미 디스크에 쓰인 내용은 에이전트가 죽어도 남아있다 — 텍스트 응답만 끊긴 것).
3. **커밋 가능한 부분은 즉시 커밋한다**:
   - 파일이 완결된 상태로 보이면(예: 문서 전체 작성 완료, 코드가 정적 검증을 통과할 만큼 완결됨) 평소처럼 리뷰 후 정상 커밋한다.
   - 파일이 명백히 미완성 상태면(예: 절반만 쓰인 코드) 무리해서 커밋하지 않는다 — 대신 무엇이 어디까지 됐는지 다음 단계(4)에 정확히 기록한다. 미완성 코드를 그냥 두는 것과 어설프게 커밋하는 것 중 후자가 항상 나은 건 아니다(빌드를 깨뜨릴 수 있음) — 판단해라.
4. **로그에 재개 지점을 정확히 남긴다** — `docs/agents/leader-log.md`의 "현재 상황 요약" 절(살아있는 요약, 덮어쓰기)에 최소한 다음을 포함해서 갱신한다:
   - 어떤 작업이 한도로 중단됐는지(에이전트 이름/역할, 원래 지시 내용 요약)
   - 중단 시점까지 실제로 완료된 것 vs 안 된 것(파일 기준으로 구체적으로 — "조사는 끝났고 파일 작성 직전에 죽음" 같은 수준)
   - 재개 방법: 같은 에이전트를 `SendMessage`로 재개할 수 있으면 그 방법을, 처음부터 다시 지시해야 하면 그것도 명시
   - 한도가 언제 풀리는지 안다면(예: notification에 "resets 5:20pm" 같은 문구) 그것도 기록해 다음 세션이 언제 재시도 가능한지 알 수 있게 한다
5. **가능하면 그 자리에서 바로 재개를 시도한다** — 한도가 이미 풀렸을 수도 있으니, `SendMessage`로 죽은 에이전트에게 이어서 하라고 보내본다(트랜스크립트에서 재개됨). 다시 같은 한도 오류가 나면 4번에서 남긴 기록에 의존해 다음 세션/나중 시점으로 넘긴다.
6. **사용자에게 상황을 짧게 알린다** — 어떤 작업이 중단됐고 어떻게 처리했는지(재개 시도 중 / 다음 기회에 재시도 예정).

## 하지 않는 것

- "95%에서 미리 멈춘다"는 원래 요청을 문자 그대로 구현했다고 주장하지 않는다 — 이건 사전 감지가 아니라 사후 복구다, 이 차이를 사용자에게 숨기지 않는다.
- 죽은 에이전트가 실제로 아무것도 안 쓴 상태(예: 조사만 하고 파일 작성 전)인데도 억지로 커밋할 거리를 만들지 않는다 — 남길 게 없으면 로그 기록만으로 충분하다.
